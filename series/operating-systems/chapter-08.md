# 운영체제 8장

## 메모리 경영

- 일반적으로 컴파일과 링킹을 거쳐 만들어진 수행가능한 exe파일 (또는 loadable 파일) 내의 모든 주소는 논리주소
  - EXE 파일에는 명령어와 데이터가 논리주소 기준으로 적혀 있음
  - 이 말은, 프로그램의 함수, 변수 등에 대해 할당되는 주소가 가상의 주소, 즉, 논리주소라는 거임
  - cpu 가 레지스터에 주소를 올릴 때 논리주소로 올린다는 거
  - 메인메모리에 탑재된 후에도 주소는 논리주소로 존재
  - 그래서 실제로 프로그램이 수행될 때에는 논리주소가 물리주소로 변환되어야 실행이 가능함
    - 왜냐면 실제로 명령어가 저장된 메모리(ram) 의 주소를 알아야 동작이 가능하니까
- 그래서 수행시점에는 논리주소를 물리주소로 변환해야함
  - 이걸 주소 결속(address binding 이라고 함)
- <b>Q. 그럼 왜 처음부터 물리주소로 안 올리나??</b>
  - 논리주소를 사용하면 유연하고 안전한 메모리 관리가 가능해짐
    - 물리주소를 사용한다면, 서로 다른 프로그램이 같은 주소를 참조할 때 보안 문제가 발생할 수 있음. 이를 논리주소로 해결 가능
    - dll, so 처럼 동적으로 로드되는 코드는 매번 메모리의 다른 위치에 올라갈 수 있음. 물리주소를 처음부터 올리면 의존성이 생겨 충돌이나 재컴파일이 필요해지나(서로 너무 알게 됨. 마치 의존성 주입이 없는 것처럼), 논리주소를 사용하는 경우에는 매핑되는 주소만 변경해주면 되기 때문에 유연한 대처 가능
  - 참고로, 매핑되는 물리 주소는 운영체제가 page table 에 저장하고 관리하고 있음
    - page table 은 프로세스마다 각각 생성됨
- 물리주소의 시작 주소를 알면, 모든 논리 주소에 시작 주소를 더해 물리 주소의 위치를 계산할 수 잇음
  - 근데 이건 외부 의존성 없는 단일 프로그램에서만 가능함
  - dll 같은 거 사용하는 경우에는 이 방식을 사용할 수 없음
- 그래서 명령어 하나가 실행될 때마다 하드웨어 지원을 받아 논리주소를 물리주소로 변환함
  - 대표적으로 MMU 의 재배치 레지스터를 사용
    - MMU 는 현재 프로세스의 페이지 테이블 사용해 주소 매핑함

## 주소결속 시점의 다양성

### 컴파일시점 결속

- 컴파일러가 물리주소를 직접 생성하는 것
  - e.g. 프로세스가 물리주소 R 번지부터 시작하는 것을 아는 경우
- 하지만 이식성이 떨어짐. R 이 변경되면 다시 컴파일 해야함

### 적재시점 결속

- 적재 시점에 물리적 시작주소가 확정되면 로더가 최초 1회 “시작 주소 + 오프셋” 방식으로 물리주소를 계산함
- 시작 주소가 변경되면 다시 로딩하면 됨.
- 단, dll 지원이 가능한 실행시점 결속보다는 유연하지 않음
  - 런타임에 새 모듈을 붙이기 어렵다는 뜻!
  - 실제로는 load-time + run-time 메커니즘을 섞어 DLL을 지원함

### 실행시점 결속

- 먼저 논리주소로 적재된 후, 실행 중에 물리주소 확정
- 명령어가 실행될 때마다 물리주소 매핑이 발생함
- 이 경우에는 dll, so(리눅스 dll) 처럼 프로세스 실행 후 로드하거나, 프로그램 전부 혹은 일부롤 재배치를 할 수 있어서 유용함
  - 가상 메모리를 사용해서 동적 재배치 + 지연 로딩이 가능하다는 거!
    - 프로세스가 현시점에 필요로 하는 부분만을 올릴 수 있다는 거임

### 적재시점 주소결속 시에는 적재 후 재배치가 불가하지만, 실행시점 주소결속 시에는 재배치 및 부분적재 가능

### 분할 방법

- 여러 개의 프로그램을 적재하기 위해 메모리 공간을 여러 개로 분할
- 분할의 수는 다중 프로그래밍의 정도가 됨
- 고정분할과 가변분할 방법이 있음

### 고정분할

- 고정 분할에서는 분할의 수와 각각의 크기가 고정
- 현재는 거의 사용	되지 않음
- 각 영역마다 별도의 큐를 두어 프로그램이 들어오면 해당 큐에 고정적으로 배정
- 단점 ) 분할 크기보다 크면 수행이 불가능하고, 분할마다 남는 공간이 발생해 메모리 효율적이지 못함
  - 그래서 분할을 통합적으로 운영하여 비어 있는 분할의 크기에 가장 잘 맞는 프로그램을 먼저 할당하는 방법이 필요
  - 그게 <b>가변분할</b> 임

### 가변분할

- 메모리를 고정 분할
- 다중 프로그래밍의 정도만 결정하고, 메모리 전체를 하나의 연속된 공간으로 보고 <b>적절한 빈 공간</b>에 프로그램을 적재
- 여기서 <b>‘적절한 빈 공간’</b> 을 찾는 방식에는 세 가지가 있음
  1. first fit
     <ol markdown="1">
     <li markdown="1">
     처음으로 발견한 사용 가능한 빈 공간에 프로세스 할당
     </li>
     <li markdown="1"></li>
     </ol>
  2. best fit
     1. 사용 가능한 공간 중에서 가장 작은 거 선택
        1. 프로세스가 사용하고 남는 공간이 작기 때문에 다른 프로세스가 사용하지 못함 → 단편화 발생 up
     2. sort 되어있지 않다면 집합 전체를 검색해야함
  3. worst fit
     1. 가장 큰 공간을 선택하는 것
        1. 프로세스가 사용하고 남는 공간이 크기 때문에 다른 프로세스를 위해 유용하게 사용할 수 있음 → 단편이 크기 때문에 다음 프로세스가 사용 가능함 → 단편화 발생 down
- 시뮬레이션 결과 최초 적합과 최적적합 모두 시간과 메모리 이용 효율 측면에서 최악 적합보다는 좋다는 게 입증됨
  - 최초적합과 최적적합의 경우 메모리 공간 효율성 측면에서는 어느 것이 좋다고 판명할 수는 없지만, 최초적합이 속도가 더 빠름

### 가변분할 방식에서의 주소결속

- 실행시간 주소결속
  - 논리주소에 대해 상한(limit) 레지스터 값으로 영역을 체크 → 분할 영역의 보호 실현
- 재배치 레지스터 값을 더하여 물리주소로 매핑

![운영체제 8장 이미지 2]({{ '/series/operating-systems/assets/os-09-002.png' | relative_url }})

- limit register 는 논리 주소가 해당 영역을 벗어나지 않도록 함
- 재배치 레지스터에는 각 프로세스에 할당된 공간의 base 주소를 기록해 압축 기법을 통해 프로그램이 이동하더라도 값을 수정해 프로그램 이동이 원할하게 이뤄지도록함

### 단편화

- 외부 단편화
  - 프로세스와 프로세스 사이에 생기는 단편
  - 연속된 공간이 아니기 때문에 활용도 down
- 내부 단편화
  - 프로세스 내부에서 발생하는 단편
  - 페이징 기법 사용할 때 발생하는 단편
- <b>50% 규칙 : 이론적으로 N 개의 불록이 할당되었을 때 .5N 개의 블록이 단편화 때문에 사용할 수 없게 됨</b>

### 압축

- 외부 단편을 하나로 모아서 큰 공간을 만드는 거임!
- 프로그램을 이동하고 재배치 레지스터 값을 변경
  - 그래서 프로그램이 이동하더라도 주소 결속이 원할하게 이뤄지도록 하게 함
- 단점 ) 주소 결속이 실행시간 주소결속이 아니면 안됨
- 압축 비용
  - 압축을 위해 움직여야 하는 프로그램 크기의 합

### Q. 꼭 연속된 공간에 프로세스를 할당해야 하나?

- 이거 해결하는 게 페이징 기법

## 페이징

- 분할 방법에서는 단편화 문제가 있었음
  - 이를 해결하기 위한 압축 방식도 비용이 발생햇음
- 단편화가 문제가 되는 이유는 <b>“프로세스가 연속된 메모리를 차지해야 하는 것”</b> 때문임
  - 그럼 이걸 해결하면 되겠다!
  - 그래서 페이징 기법이 등장
- 페이징 기법은 연속된 물리공간을 필요로 하지 않으면서도 실행시간 주소결속이 가능한 방식 중 하나
- 물리적 공간은 프레임
- 논리적 공간은 같은 페이지로 나누고
- 페이지 테이블을 사용해 페이지를 프레임에 대응(매핑) 시킴
  - 얘는 일종의 주소 변환 테이블 역할
  - 임의 페이지에 해당하는 프레임의 번호를 가지고 있음

1. 전체 공간을 같은 크기의 프레임으로 나눔
2. 논리적 공간도 프레임이랑 같은 크기로 나눔
3. 페이지 테이블을 사용해 페이지를 프레임에 매핑시킴
   ![운영체제 8장 이미지 3]({{ '/series/operating-systems/assets/os-09-003.png' | relative_url }})

- 논리적 공간과 물리적 공간이 페이지 테이블을 통해 연결되어 있음
- 페이지 테이블이 마치 ‘가상적으로 연결된 메모리인 것 처럼’ 만들어줌

### 페이지 테이블과 주소 결속

- 모든 논리 주소는 P 와 D 로 나눠짐
  - P 는 페이지 번호, 페이지 테이블의 인덱스
  - D 는 페이지 내의 offset

![운영체제 8장 이미지 4]({{ '/series/operating-systems/assets/os-09-004.png' | relative_url }})

- 16 bit 주소체계 시스템에서
- P 를 위해 4bit, D 를 위해 12 bit 사용하면
  - 논리주소는 이렇게 생김
    - e.g. 1111 0000 1111 1010 → 앞의 4 bit 인 1111(2) 페이지에 0000 1111 1010(2) 번 위치 를 가리키는 것
  - 페이지 테이블에서 f 값으로 4 bit 의 p 값을 대체하고, 나머지 12 bit d 를 내비둠
    - 그럼 그게 f 와 d 로 이뤄진 물리주소가 됨
    - 이 뜻은, f 와 d 로 이뤄진 물리주소는 f 번쩨 프레임의 시작번지는 0xf000 이며, 그로부터 d 번째 주소가 해당 물리주소라는 것
- 결국 논리적 공간의 페이지 주소가 프레임의 물리주소로 변환되며 주소 결속이 이뤄짐
- 각 프로세스마다 p 가 4 bit, d 가 12 bit  이므로, 한 프로세스는 최대 16개의 페이지를 가질 수 있고, 각 페이지는 2\^12 바이트임

### 주소 표현

- 논리적 주소
  - p : 페이지 번호
  - d : 페이지 내의 상대주소(offset)
- 물리적 주소
  - f \* s + d
    - f 는 페이지 p 에 해당하는 프레임 번호
    - s 는 페이지 크기이자 프레임의 크기
    - d 의 크기는 페이지 크기와 같은 s 가 되는 것이므로 s 를 표현하기 위한 비트 수와 동일한 비트 수가 필요함
      $$
      log_2S
      $$

### 페이징 기법에서의 단편화

- 페이징 기법에서는 외부단편화가 일어나지 않음
- 약간의 내부 단편화는 일어남
  - 모든 프로세스의 크기가 S 의 정수배로 구성되지 않기 때문에, 페이지 크기대로 프로세스를 자르면 맨 마지막에는 페이지 크기보다 조금 작게 나옴
  - 그래서 단편화가 발생하는 것

### free frame list

- 운영체제는 새로운 프레임 할당을 위해 가용 프레임을 free frame 리스트로 운용함
  - 프레임 별 할당 상황(할당 여부, 할당 프로세스 등) 은 프레임 테이블로 관리

## 페이지 테이블 개선

- 주소결속까지 걸리는 속도
- 페이지 테이블 용량
  ### 페이지 테이블의 속도 개선

  - 페이지 테이블을 들러야 주소 결속이 가능
  - 그래서 페이지 테이블은 초창기에는 별도의 레지스터로 구성됨
    - 이 때는 페이지 테이블이 작은 경우
  - 지금은 메인 메모리에 저장함.
    - 그래서 PTBR (page-table base register) 이 필요함
      - 페이지 테이블의 시작 주소를 기록해둬야 메모리의 어느 부분에 페이지 테이블이 있는지 아니까
    - 결과적으로 모든 논리주소는 2 번의 메모리 접근이 필요
      1. 페이지 테이블 한 번 들러서 물리 주소 확인하고
      2. 물리 주소에 들러야 함
    - 이 방식에서는 레지스터나 메모리 들러야 하는 횟수 증가해서 속도 저하됨
  - 해결책
    1. TLB (translation look-aside buffers) 를 이용
       1. 16\~32개의 속도 빠른 연관 레지스터(Associative Register) 사용
          1. 연관 레지스터는 key-value 를 저장한 다음에 key 를 이용해 빠르게 검색하는 방식
          2. key 를 이용해 동시에 탐색하기 때문에, 주소를 이용해 순차적으로 방문하는 메인 메모리보다 빠름
       2. 논리 주소 p 와 프레임 번호 f 의 쌍인 맵핑 정보를 기록하고,
       3. 메모리 접근이 필요하면 TLB 에서 맵핑 정보 찾고, 없으면 메모리 상의 페이지 테이블에서 찾음
          1. 메모리에서 결과값 찾았다면 TLB 에 기록
          2. 업데이트는 FIFO 방식으로 이뤄짐
             1. 어느 한 영역을 접근하면, 계속 그 영역을 접근하기 때문에 적합한 방식으로 업데이트 되는 것!

       <b>Q. TLB 는 페이지 테이블의 캐시인가?</b>

       - 목적은 유사하나 조금은 다름!
       - 일반적으로 캐시는 데이터 접근 단계에서 메모리 접근 속도를 높이기 위해 사용하는 거임
       - TLB cpu 가 논리적 주소를 물리적 주소로 주소 결속할 때의 속도를 높이기 위해 사용하는 것
       - 즉, TLB 를 거치고 캐시를 거치게 됨

  ### 페이지 공유

  - 페이징 기법을 사용하면 페이지 공유가 용이함
  - 한 프로세스의 사용자 문맥 중 변경이 되면 안되는 부분 : text 문맥(code)
    - 그래서 이 부분은 한 프로세스에 의해 먼저 탑재되었다면 다른 프로세스에서 공유해도 됨
    - 페이지 테이블을 사용하면 이걸 효과적으로 사용할 수 있음
    - 페이지 테이블에 공유하려는 부분을 같게 기록해두면 됨
  - 이 경우, 데이터는 다른 프레임에 페이징하고, 코드만 공유하는 것!

  ### 메모리 보호

  - 페이지 테이블에 보호 비트를 넣어서 구현함
    - 페이지 테이블에 valid, invalid 를 구분하는 bit 를 넣어둠
    - 주소 변환 과정에서 MMU 가 이를 확인해 요청된 접근(읽기/쓰기/실행) 이 보호 비트와 일치하는지 검사
      - 일치하면 접근 허용
      - 일치하지 않으면 페이지 보호 예외 발생
  - 페이지에 접근할 수 있도록 하는 권한은 페이지 테이블 엔트리 (page table entry, pte) 에 기록되고, 페이지 테이블과 pte 는 커널에서 관리하기 때문에 임의로 수정이 불가능함

  ### 페이징의 장단점

  - 단점 ) 페이지 테이블 사용으로 분할 방식에 비해 주소결속에 따른 오버헤드 발생
    - 이거 해결하려면 TLB 같은 거 사용해야 함
    - 페이지 테이블을 저장하기 위한 별도의 공간이 필요함
  - 장점
    - 단편화 문제 해결 가능
    - 페이지 공유 가능
    - 페이지 보호 가능

## 페이지 테이블의 구조

- 페이지 테이블의 속도 측면의 성능과 아울러 페이지 테이블의 크기도 중요한 이슈
- 페이지 테이블을 연속된 메인메모리 공간에 탑재하기 보다는 분할하여 운영하는 구조적 접근이 필요함
- 세 가지 방법이 있음
  1. 계층적 페이징
     1. forward-mapped page table 이라고 하기도 함
     2. 논리 주소를 구성하는 페이지 번호 영역인 p 를 분할하는 것
     3. 2 단계 페이징이라면 p 를 절반으로 쪼개서
        1. 상위 비트는 outer page table 사용
           1. 여기는 2\^p1 만큼 페이지가 존재함
           2. 각 페이지의 엔트리에는 inner page table 의 주소가 있음
              1. <b>주의 ) ‘테이블’ 자체의 주소가 있는 거임!</b>
           3. 그래서 2\^p1 개의 innter page table 주소 저장 가능
        2. 하위 비트는 inner page table 사용
           1. 여기서도 2\^p2 개의 주소 저장 가능

     - 그래서 총 2\^(p1 + p2) 개의 페이지, 2\^(p1 + p2) \* d 개 의 주소를 관리할 수 있다!
     - 이 방식을 사용하면 페이지 테이블에 필요한 메모리 공간을 줄일 수 있음!
       - 연속된 테이블로 관리 안해도 되니까!
     - 이 방식을 사용하면 단계가 늘어날 수록 메모리 접근 비용이 발생함
  2. 해시 페이지 테이블
     <ol markdown="1">
     <li markdown="1">
     32bit 로 어드레싱 하기 어려운 큰 주소공간 다루기 위해 해쉬 페이지 테이블 사용함
     </li>
     <li markdown="1">
     논리 주소에 대한 해쉬값을 통해 물리 주소를 찾아감

     1. 해쉬 값을 가상 페이지 번호로 활용하고 해쉬 테이블의 각 항목에 해쉬충돌(collision) 해결을 위한 연결리스트 구비
     </li>
     <li markdown="1">
     해쉬 테이블은 적어도 다음과 같은 3가지의 정보를 갖는 필드를 구비하게 됨

     1. 가상 페이지 번호 - 논리주소상의 페이지 번호
     2. 사상되는 페이지 프레임 번호 - 물리주소상의 프레임 번호
     3. 연결리스트 상의 다음 원소 포인터
     </li>
     <li markdown="1">
     해쉬 테이블 운영 방법

     1. 가상 페이지 번호(논리 주소 값)가 들어오면 해시 함수 통해 해싱함
     2. 그 다음, 그 값으로 해시 페이지 테이블의 항목을 찾아서 연결리스트를 따라가며 가상페이지 번호와 비교
        1. 일치하면 변환
        2. 일치하지 않는다면 연결리스트 따라가며 비교 반복
     </li>
     <li markdown="1">
      64 bit 를 사용하는 경우에 이득이 큼

     1. 주소공간이 아무리 크더라도 해시 함수 통해 변환 가능하고, 인덱싱도 바로 되기 때문
     2. 그래서 64 비트 시스템은 클러스터 페이지 테이블을 사용함
        1. 클러스터 페이지 테이블의 한 항목은 여러 페이지를 가리킴. 즉, 페이지를 묶는 단위가 커진 것
     </li>
     </ol>
  3. 역 페이지 테이블
     1. 페이지 테이블이 프로세스마다 존재해서 많은 메모리 용량이 필요함
     2. 그래서 역페이지 테이블 방식에서는 메인메모리의 각 프레임마다 페이지 테이블의 한 항목씩 할당
        1. 그니까, 기존 방식은 논리 주소 주면서 페이지 테이블한테 이거 어딧어 ? 하는 방식이엇다면, 이 방식은 메인 메모리에 있는 거를 페이지 테이블에 기록해두고 찾는 거임
        2. 페이지 테이블의 각 항목에는 해당 프레임에 올라온 프로세스의 pid 와 페이지 번호를 기록함
        3. 즉, 프로세스 정보를 페이지 테이블에 포함시켜서 프로세스마다 각각의 페이지 테이블이 존재해야 하는 이유를 없앤 것
     3. 결과적으로 하나의 페이지 테이블만 남아 적은 용량을 필요로 하게 됨
     4. but ) 주소변환을 할 때마다 페이지 테이블을 탐색해야함
        1. 일반 페이지 테이블은 TLB 먼저 보기 때문에 TLB miss 날 때만 탐색하는데,
        2. 얘는 그냥 무조건임
     5. 그래서 이걸 해결하기 위해 해시 테이블 사용함

## 세그먼테이션

- 페이징 기법은 메모리 공간을 동일한 크기의 프레임으로 나누는 것
- 세그먼트
  - 논리적으로 관련 있는 코드나 데이터 블록을 하나의 단위로 묶은 것
- 세그멘테이션
  - 프로그래머가 가진 메모리에 대한 관점을 지원해주는 메모리 경영 방식
  - 페이지 테이블 대신 세그먼트 테이블을 이용함
    - 여기에는 각 세그먼트의 시작 주소와 크기 정보가 적혀 있음
      - 크기가 적힌 이유는, 세그먼트 크기가 가변적이기 때문
- 컴파일러가 세그먼트 생성
  - 프로세스 사용자 문맥을 구성하는 요소와 유사
  - e.g. 코드, 전역변수, heap, 스택, 표준c라이브러리, 컴파일 타임에 링크되는 라이브러리(정적 라이브러리, static libray)
- 로더가 세그먼트 받아서 세그먼트마다 번호 새김
- 세그먼테이션에서의 주소 결속은 페이징기법과 비슷
  - 주소를 s 와 d 로 나눔
    - s 는 세그먼트 번호
    - d 는 세그먼트 내에서의 offset 값
  - s 를 가지고 세그먼트 테이블의 해당 항목을 찾아감
    - 거기에는 한계값과 기준값이 기록되어 있음
      - 한계값은 세그먼트 크기(가변적이기 때문에 필요)
      - 기준값은 세그먼트 시작 주소 (base 주소)
    - d 값이 한계값을 벗어나지 않는다면 base 주소에 d 를 더해서 물리 주소를 구함
- 세그먼트 기법 사용하면 세그먼트 공유가 가능해져 메모리 효율 증가
- 세그먼테이션 방법에서는 외부 단편화 문제가 발생함
  - 왜냐면 세그먼트 크기가 가변적이기 때문임
  - 그래서 paged segmentation 을 사용함
    - 이건 세그먼트 내에서는 페이지 테이블 사용하는 방식
    - 그니까 세그먼트를 페이지처럼 고정 크기 블록으로 자르고 메모리에 적재하는 거임
    - 세그먼트 테이블 내의 각 항목이 그 세그먼트를 위한 페이지 테이블의 시작 주소를 알려주면 됨
