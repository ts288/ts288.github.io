## 실시간 시스템 - 9주차 강의 듣기(여기 문제 풀이 나옴. 시험에 나옴)

- 자연계의 순환 구조를 모방
- 제어 주기가 일정해야함
  - 한 번 순환의 deadline 이 있음

### 경성, 연성 실시간 시스템

- 연성 실시간 시스템
  - 순환의 deadline 을 지키려고 노력하는 시스템
  - 실시간이 아닌 프로세스들에 비해 <b>우선권</b>을 가진다는 것만 보장
  - 실시간 프로세스가 스케줄 되는 시점에 아무런 보장을 하지 않음
- 경성 실시간 시스템
  - 순환의 deadline 을 무조건 맞추는 시스템
  - 엄격한 요구조건이 있음. 태스크는 반드시 마감시간까지 서비스를 받아야 함
  - 마감 시간 이후에 서비스 받는 것은 서비스를 전혀 못받은 것과 동일함
- 문제 ) 태스크가 여러 개인 경우, 실시간 프로세스와 일반 프로세스를 잘 컨트롤 하는 것이 어려움!

### 지연 시간 최소화

- 시스템은 일반적으로 실시간으로 발생하는 사건(event) 를 기다림
- 인터럽트가 들어와도 바로 ISR 을 실행하지 않음
- 그래야 주기를 보장할 수 있음
- 사건이 발생하면, 시스템은 가능한 빨리 응답을 하고 동작을 수행해야 함
- <b>사건지연 시간</b>
  - 사건이 발생해서 그에 맞는 서비스가 수행될 때까지의 시간
  - 지연을 구성하는 요인
    1. 인터럽트 지연시간
       1. cpu 에 인터럽트가 발생한 시점부터 해당 인터럽트 처리 루틴이 시작하기까지 걸린 시간
          1. 즉, ISR 로 진입하기까지 걸린 시간
       2. 인터럽트가 발생하면 운영체제는 우선 수행중인 명령어 완수하고 발생한 <b>인터럽트 종류</b>를 결정
       3. 해당 ISR 사용해 인터럽트 처리하기 전에 수행 중인 프로세스 문맥 보존
          1. 보존은 pcb 에 한다.
    2. 디스패치 지연시간
       1. 하나의 프로세스를 중지시키고 다른 프로세스를 시작하게 하는데 걸리는 시간
          1. ISR 을 수행하는 시간도 포함
       2. 충돌 두 요소
          1. 커널에서 수행중인 프로세스를 선점할 수 없는 경우(비선점 커널 사용 시)
             1. 한 번 시작하면 끝까지 실행해야 하는 프로그램을 수행하고 있는 경우
             2. 선점형 커널 사용으로 최소화할 수 있다.
          2. 높은 우선순위의 프로세스가 필요로 하는 자원을 낮은 우선순위 프로세스가 선점하는 경우 릴리즈 시까지 대기
             1. 이를 우선순위 역전이라고 함

          ### 우선순위 역전 해결 방법

          <ul markdown="1">
          <li markdown="1">
          우선순위 역전은 선점 시스템에서도 발생할 수 있음. 예를 들어, lock 을 걸고 사용해야 하는 공유 자원을 우선순위가 낮은 프로세스가 사용하는 경우가 있을 수 있으니까.
          </li>
          <li markdown="1">
          이걸 해결하기 위해서는 프로세스들이 자원을 사용할 때에 자발적으로 lock 을 푸는 게 필요함. 

          1. lock 을 걸고
          2. 자발적으로 lock 을 풀고
          3. 자신보다 우선순위가 높은 프로세스가 있는지 체크 → 있으면 양보, 없으면 실행
          </li>
          </ul>

## 실시간 스케줄링

- 동시에 여러 개의 실시간 태스크들이 존재할 경우, 각 태스크 간 작업의 수행 순서를 정하는 것
  - 여러 프로그램이 실시간성을 요구할 때, 알고리즘을 작성하기가 복잡함

### RM(Rate Monotonic) Scheduling

- Mono 는 변하지 않는다느 뜻!
- 즉, rate (주기) 가 변하지 않는다는 것이당
- 주기를 먼저 받고, 이로써 우선순위를 정해 프로그램을 돌리는 것
- <b>선점 가능한 정적 우선순위 스케줄링 방법임!</b>
  - 주기에 의해 우선순위가 정해지고, 스케줄링 동안 충돌이 발생하면 우선순위 높은 애가 가져가서 → 선점 가능한 정적 우선순위 스케줄링이다.
- 짧은 주기의 프로그램에게 높은 우선순위를 부여한다!
  ![운영체제 5강 이미지 2]({{ '/series/operating-systems/assets/os-04-002.png' | relative_url }})

  - 주기가 짧은 p1 이 우선순위를 갖게 됨
  - p1 이 20 동안 돌고, p2 가 돌기 시작
  - p1 의 주기가 50이기 때문에, 50에는 p1 이 돌게 됨(p1 이 우선순위 높음 → 선점)
  - 그다음에 70에서 p2 를 남은 5만큼 돌려줌
  - <b>모든 프로세스를 돌렸는데도 주기가 남을 때는 주기 마다 같은 스케줄링이 반복됨</b>
  - 주어진 스케줄러 set 이 스케줄링이 가능한가? 를 판단하기 위해 연구함! → <b>Utilization Bound</b>

  ### Utilization Bound

  - CPU 사용률의 총합이 어떤 임계값(경계) 이하라면, 해당 스케줄링 알고리즘이 모든 태스크의 마감기한 (deadline) 을 항상 만족시킬 수 있다고 보장할 수 있는 값
    - 단, 이 값은 충분조건이지 필요조건이 아니기 때문에, 이를 Utilization Bound 를 만족한다고 해서 무조건 마감이 보장되는 것은 아님
  - RM 을 사용하는 실시간 시스템은 유틸리티가 아래의 관계를 만족하면 스케줄링이 가능
    ![운영체제 5강 이미지 3]({{ '/series/operating-systems/assets/os-04-003.png' | relative_url }})

  ```kotlin
  ∑Ui ≤ n * (2^(1/n)-1) // n 은 태스크 개수
  ```

  <ul markdown="1">
  <li markdown="1">
  각 태스크의 utilization ( = 1/p ) 합이 n \* (2\^(1/n)-1) 보다 작으면 같거나 가능! 
  </li>
  <li markdown="1">
  이 식을 만족하지 못하는 경우에는 deadline missing 이 발생하게 됨
  </li>
  <li markdown="1">
  참고로 n 을 아무리 많이 늘려도 utilization 이 0.69 를 넘기지 못한다.

  ![운영체제 5강 이미지 4]({{ '/series/operating-systems/assets/os-04-004.png' | relative_url }})

  - 즉, n 을 무한정 늘릴 수는 없다.
  </li>
  </ul>

### <span color="red">EDF(Earliest Deadline First) Scheduling - 5강 4번째 영상 보면서 공부하기. 아래 예제 보면서</span>

- 선점형 동적 우선순위 스케줄링 방법
  - UB 와 다르게 우선순위가 동적임!
  - 즉, 상황에 따라서 우선순위가 변할 수 있음!
- deadline 까지 남은 시간이 짧은 태스크의 작업이 높은 우선순위를 갖게 됨
  ![운영체제 5강 이미지 5]({{ '/series/operating-systems/assets/os-04-005.png' | relative_url }})

  - p1 이 25 만큼 돌게 됨. 끝나는 시점은 25
  - p2 가 돌게 됨. 끝나는 시점은 60
  - p1 의 다음 deadline 은 100, p2 의 다음 deadline 은 105
  - 그래서 p1 이 먼저 돌게 됨
- 아래의 관계를 만족하면 EDF 에서 스케줄링이 가능
  ![운영체제 5강 이미지 6]({{ '/series/operating-systems/assets/os-04-006.png' | relative_url }})
- 과부하 시에 Domino Effect 가 발생할 수 있음
  - 하나가 망가지면 전부 다 망가짐

### RM vs EDF

- RM 스케줄링
  - 구현이 상대적으로 단순
  - 우선순위가 높은 태스크의 <b>예측성</b>이 좋음
    - 주기가 짧은 태스크에서는 예측성이 좋음
      - 왜냐면 EDF 와 달리 동적 계산 없이 우선순위가 고정되기 때문임
        - RM 은 주기 짧은 애한테 무조건 우선순위 주는데, EDF 는 deadline 까지 남은 시간 보고 우선순위 동적으로 결정함
    - 그래서 주기 짧은 거에 중요한 프로세스를 넣어둠
  - 처리기 이용률이 높지 않음
- EDF
  - <b>이론적</b>으로 최적 - 처리기 이용률이 100% (utilization 이 1 이하이기 때문에!)
    - 단 실제로는 프로세스 사이 또는 인터럽트 핸들링 시의 문맥교환 비용으로 100% 는 이론적인 수치임. 실제로는 불가
  - 과부하 발생 시에 도미노 현상 문제 발생
- 알고리즘 측면에서는 EDF 가 좋으나, 현실적으로는 구현의 단순성 및 예측성 때문에 RM 도 무시하지 못함!

## POSIX Real-time API

- 경성 실시간 시스템이 필요한 곳에 사용되는 os
  - 경성 실시간 os : VxWorks 가 널리 사용됨
- POSIX 에서도 연성 실시간을 지원하긴 함

### POSIX

- 실시간 스레드를 위해 두 개의 스케줄링 클래스를 정의
  - SCHED\_FIFO
    - FIFO 큐에 먼저 들어온 것을 먼저 서비스
      - FIFO 큐의 앞에 있는 가장 높은 우선순위의 실시간 스레드를 타임슬라이스 적용 안하고, 블록되거나 종료될 때까지 cpu 할당 보장
  - SCHED\_RR(라운드로빈)
    - 같은 우선순위의 스레드에게 시간 할당량 제공
  - SCHED\_DEADLINE
    - EDF 스케줄링을 사용하는 방식
    - 일반 사용자는 사용 불가능
      - 왜냐면 이게 적용된 프로세는 cpu 선점이 가능해지기 때문
      - 그리고 이거 잘못 설정하면 도미노 현상이 발생할 수도 있어짐
  - 이렇게 설정할 수 있음

  ```kotlin
  • Pthread_attr_getschedpolicy(pthread_attr_t *attr, int *policy)
  • pthread_attr_setschedpolicy(pthread_attr_t *attr, int policy)
  ```
