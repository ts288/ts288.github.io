# 운영체제 9강 (가상 메모리)

## 가상 메모리란?

- 페이지 테이블을 통해 valid, invalid 체크가 가능
- 이걸 확장하면, 페이지 테이블에 잇는 valid, invalid bit 를 ‘적재가 되어있는가, 되어있지 않는가’ 에 대한 표시로 활용할 수 있음
  - 하나의 프로그램에 여러 페이지가 있을 때, 이 프로그램은 하드디스크의 어딘가 저장되어 잇음.
  - 물리적 메모리에 올릴때 는 이 중 일부만 올리는 거임
  - 그리고 올라간 부분을 페이지 테이블의 valid 로 표시함
    ![운영체제 9강 (가상 메모리) 이미지 1]({{ '/series/operating-systems/assets/os-10-001.png' | relative_url }})
  - 그런데 일부만 올라간 경우에는 프로그램이 제대로 동작하지 않을 수 있음 (A 다음에 B 를 읽어야 하는데, B 가 아직 안 올라와있을 수 있으니까)

## 요구 페이징 및 부분적재의 타당성 (가장 중요한 개념)

### 요구 페이징

- 그래서 요구 페이징 (demand paging) 을 사용함
  - 페이징은 페이지 테이블에 valid, invalid 기록하는 것
- cpu 가 해당 페이지를 요구할 때까지 그 페이지를 메모리에  올리지 않음
- 메모리에 필요한 페이지가 올라가 있지 않은 페이지 부재 (page fault) 가 발생한 경우, 그 때 트랩을 걸어 해당 페이지를 적재
  - 페이지를 가져와서 메인 메모리의 빈 공간에 적재
  - 이후에 페이지 테이블 업데이트 (valid)

### 문제

- <b>Q. 물리 메모리에 빈 공간이 없다면?</b>
  - 희생될 페이지를 찾아 페이지 대치를 수행
  - <b>Q. 그럼 어떤 페이지를 희생시키나?</b>
    - 알고리즘에 따라 다름. 오랜된 페이지를 날릴 수도 있고, 방금 사용한 페이지를 날릴 수도 있고..
- <b>Q. 가상 메모리를 사용하면 요구 페이징이 많이 발생하고, 이건 트랩 발생으로 이어지니까 성능 저하가 있을 것 같음</b>
  - 프로그램이 실제로 수행될 때, 한 페이지를 집중적으로 참고하다가 시간이 지나면 다른 페이지에서 머물다가를 반복함.
    - 이걸 <b>Locality of Reference (국지성)</b> 이라고 함
  - 즉, 많은 경우 한 번에 전체 프로그램이 메모리에 올라가 있을 필요가 없음

### 전체를 메모리에 올리는 방식에 비해, 부분 적재가 성능이 저하되는 것은 사실임

- 요구 페이징 기법을 사용하면 트랩이 발생하기 때문!
- 그래서 최대한 page fault 가 발생하지 않도록 알고리즘을 짜야 함

### 부분 적재의 이점

- 프로그램 크기가 물리적인 메모리 크기와 무관함
- 더 많은 프로그램이 메모리를 공유해 cpu 사용률과 처리율이 향상함
- 주소 결속을 실행 시간에 할 수 있음

<b><span color="blue">결국, page fault rate 를 낮추어 성능을 높이는 것이 중요!</span></b>

## 페이지 대치 알고리즘

### 최적 대치 알고리즘

- 존재하지 않는 알고리즘
  - 가장 좋은 최상의 결과를 이론적으로 정의한 것
  - 아무리 좋은 알고리즘이라도 이 이상으로는 안된다! 하는 것
- <b>belady (밸러디)</b> 알고리즘 또는 B0 알고리즘
- “<b><span color="blue">앞으로 가장 오랫동안 사용되지 않을</span></b> 페이지를 찾아서 교체” 하는 알고리즘
- Lookahed 알고리즘으로 실현이 어려움
  - 미래를 예측해야 하기 때문에 실현이 어려운 것
- 그래서 이 알고리즘이 페이지 대치 알고리즘의 상한선
  ![운영체제 9강 (가상 메모리) 이미지 2]({{ '/series/operating-systems/assets/os-10-002.png' | relative_url }})
- 위 그림에서, 4번을 demad 했을 때 3번을 대치하는 이유는, 3이 다른 페이지에 비해 가장 마지막에 필요하기 때문임
- 1은 1번, 5번 / 2는 2번, 6번 이지만, 3은 3번 10번임

### 최악 대치 알고리즘

- 기존에 올라간 페이지 중에 랜덤하게 하나 선택해 대치하는 알고리즘
- 페이지 대치 알고리즘의 하한선

### FIFO

- 메모리에 올라온 지 가장 오래된 페이지를 대치하는 알고리즘
- <b>밸러디 변이 발생</b> - 페이지 오류율이 주어진 프레임이 수가 증가함에도 오히려 증가할 수 있음 (무조건 가장 오래된 걸 대치하기 때문. 오래된 것과 오래 사용되지 않은 것은 의미가 서로 다름)

### LRU

- Lest Recently Used
- <b><span color="blue">가장 오랫동안 사용되지 않은</span></b> 페이지를 대치
- 스택 알고리즘의 일종
- ‘언제 사용되었는지’ 를 체크하기 위해, 페이지마다 타임 스탬프나 포인터 같은 추가 메타데이터가 필요함. 즉, 다른 알고리즘에 비해 공간 복잡도가 증가함.
- 미래를 예측하는 게 불가능하므로, 가까운 미래의 근사값으로 가장 최근의 과거를 사용함. 즉, 가장 오랜 기간 사용되지 않을 페이지 대신 가장 오랜 기간 사용되지 않은 페이지를 대치함
  ![운영체제 9강 (가상 메모리) 이미지 3]({{ '/series/operating-systems/assets/os-10-003.png' | relative_url }})
- <b>중요 ) 사용될 때마다 스택의 맨 아래로 내리면, 페이지 대치가 필요할 때 맨 위에 있는 값을 날리면 됨!</b>
  - 왜냐면 가장 최근에 사용된 건 맨 밑으로 가게 되기 때문임!

## 참조비트

### 참조바이트

- 페이지마다 참조바이트 하나씩을 마련
- 약간의 시간 \<\< 이걸 타이머 인터럽트로 일정하게 결정
  - 타이머 인터럽트로 일정 간격마다 참조바이트를 우측으로 1bit shift 하고 참조비트를 맨 왼쪽 최고위 비트(MSB) 에 복사
  - 그런 후 0 으로 리셋
  - 이렇게 하면 값의 크기를 비교했을 때 참조바이트 값이 가장 큰 페이지가 가장 최근 것이고, 가장 작은 페이지가 가장 오래된 것임.
  - 이걸 다 비교해서 가장 작은 페이지를 대치함
- 결국 참조바이트가 최근의 8회 인터럽트 기간 동안 해당 페이지의 참조기록을 간직함
- 단, 8회 이전의 참조상황은 비교할 수 없다는 한계가 있음.

## <b><span color="red">2차 기회 알고리즘 (\*\*이거 시험)</span></b>

- 만약에 쉬프트 레지스터 없이 참조비트만 제공된다면?
  - 이 때는 2차 기회 알고리즘을 사용해야함
- LRU 와 근접한 것으로 판명된 알고리즘
- 페이지 순서대로 참조비트 검사를 계속하면서, 만약 해당 참조비트가
  - 0 이면 그 프레임의 페이지를 대치
    - 페이지 대치 후에 프레임에 0 기록
  - 1 이면 0으로 변경하여 다시 한 번 기회를 부여하고 계속 진행
    ![운영체제 9강 (가상 메모리) 이미지 4]({{ '/series/operating-systems/assets/os-10-004.png' | relative_url }})

  ### Q. 근데 새로 교체된 것도 0 으로 표기되고, 참조되었던 것도 0 으로 표기한 상태에서 0 인 걸 대치한다면, 페이지 대치 후에 참조되지 않은 것도 대치될 수 있는 거 아닌가?

### 개선된 2차 기회 알고리즘

- LRU 에 근사한 clock policy 알고리즘은 사용 비트 수가 증가함에 따라 보다 강력해짐
  - 참조비트와 오염비트 조합을 통해 개선 가능
- 프레임을 할당 받은 어느 페이지든 다음의 4개 등급 중 하나에 속하게 됨(used, modified)
  - (0, 0) : 참조 x, 변경 x
  - (0, 1) : 참조 x, 변경 o
  - (1, 0) : 참조 o, 변경 x
  - (1, 1) : 참조 o, 변경 o
- 등급번호가 가장 낮은 것(작은 것) 이 희생자가 됨

## 사전 대치

- 페이지 부재 발생은 많은 오버헤드 야기
- 페이지 대치 알고리즘을 <b>“사전에”</b> 실행
  - <b>항상 빈 프레임을 갖고 있으면</b> 페이지 부재 발생 시에 페이지 대치 알고리즘까지 수행하여야 하는 것을 방지할 수 있음.
  - 미리 선정된 희생자를 디스크로 내보내는 출력작업은 cpu 와 병행할 수 있으므로 더욱 효과적임

## 사전 적재

- 미리 여러 페이지를 적재해두는 방법도 있음!
- 페이지 참조에 대한예측이 필요함
  - 다양한 정보 활용 가능.
    - 함수, 행렬이 참조되는 경우 연관 페이지 모두 적재
    - 컴파일러에 의해 필요한 정보가 제공될 수도 있음

## 프레임 개수와 페이지 폴트 발생률

- 페이지 폴트 발생률(페이지 부재율) 과 프레임 개수는 반비례 관계
- 페이지 크기가 고정되어 있을 때, 프로세스가 사용 가능한 프레임 개수가 많을 수록 페이지 폴트 발생률은 일반적으로 낮아짐
- 단, 페이지 대치 알고리즘에 따라서 <b>일시적으로 밸러디 변이가 일어날 수 있음</b>
  - e.g. FIFO 알고리즘을 사용하는 경우에 밸러디 변이 일어날 수도 있음

## 페이지 크기

- 보통 4k
- 일반적으로 같은 크기 메모리 영역을 사용한다고 할 때, 페이지 크기가
  - 작아지면 <b>필요한 페이지 수가 많으나</b>, 어느 정도 <b>시간이 지나면 locality 에 의해 인접부분을 모두 포함</b>하게 되어 <b>페이지 폴트 발생이 낮아지게 됨</b>
  - 커질 수록 <b>개별 페이지들은 최근 참조로부터 멀어지게 되어</b> <b>locality 효과가 약화되어 페이지 폴트가 증가</b>
    ![운영체제 9강 (가상 메모리) 이미지 9]({{ '/series/operating-systems/assets/os-10-009.png' | relative_url }})
  - 위 사진은 큰 페이지 하나를 사용하는 경우와 작은 페이지 두 개를 사용하는 경우
  - 작은 페이지를 사용할 수록 프레임 개수가 많아지니 locality 부분을 모두 포함할 수 있음
  - 큰 페이지를 사용하면 프레임 개수가 적어서 locality 부분을 모두 포함하지 못함
- 그러나 페이지 크기 설정에 대해 정답은 없다! 각각의 장단점이 있기 때문

## 쓰래싱

- 발생 원인
  - 프로세스가 많아짐 → 각 프로세스에 할당되는 프레임 수가 적어짐 → 페이지 폴트가 자주 일어남
  - 그래서 프로세스가 페이징 기다리는 동안 cpu 이용률이 떨어짐 → cpu 스케줄러는 cpu 사용률 높이려고 프로세스 수를 더 늘리는 악순환이 반복됨
  - 결국 프로세스들이 실제로 cpu 에 의해 실행되는 시간보다 페이지를 교체하는 데에 더 많은 시간이 소요되는 현상이 발생함
  - 이걸 쓰레싱이라고 함
- 이걸 방지하기 위해 작업 세트 모델을 사용함

## 작업 세트(work set) 모델

- 쓰레싱 방지하기 위해 도입
  - work set
    - 가장 최근의 N 개 페이지 참조에 들어 있는 서로 다른 페이지의 집합(여기서 N 은 작업세트 윈도우)
    - 현재 타임 윈도우 내에서 서로 다른 페이지가 몇 개 사용되는지 보면 됩니다!
      ![운영체제 9강 (가상 메모리) 이미지 10]({{ '/series/operating-systems/assets/os-10-010.png' | relative_url }})

      - 이걸 볼 수 있으면 이 타임 내에 페이지 폴트가 얼마나 일어나는지 확인할 수 있음!
      - 참고로 페이지 폴트가 오르락 내리락 하는 이유는 locality 때문임. locality 가 이전하는 경우에는 페이지 폴트가 오르락 내리락
        ![운영체제 9강 (가상 메모리) 이미지 11]({{ '/series/operating-systems/assets/os-10-011.png' | relative_url }})
      - 그래서 이렇게 한 타임 윈도우 내에 페이지 몇 개를 사용하는지 확인할 수 있음.
        - 중복되지 않는 페이지 번호의 개수를 세면 됨
    - 쓰레싱 방지하려면
      - 각 프로세스가 필요로 하는 최소한의 프레임 개수를 보장해야함
      - 이를 위해 프로세스가 현시점에서 필요로 하는 최소한의 프레임 개수를 알 수 잇는 방법이 필요함
- locality model 에 근거한 작업 세트 모델 활용
- 작업 세트 크기의 동적 변화 패턴
  ![운영체제 9강 (가상 메모리) 이미지 12]({{ '/series/operating-systems/assets/os-10-012.png' | relative_url }})

  - 처음에 페이지 폴트 왕창 일어나다가 안정되엇다가 왕창 요구하다가 안정되엇다를 반복함
  - 안정기 → 과도기 로 변화도리 때, locality 가 변화되어 요구 페이지 개수와 종류가 달라짐#

  ### 쓰레싱 감시에 작업 세트 활용

  - 각 프로세스의 작업세트를 감시
    - 각 프로세스에게 작업세트 크기에 맞는 충분한 프레임 할당
    - 여분의 프레임 있다면 다른 프로세스도 수행
  - 쓰레싱 발생 감지
    - 각 작업 세트 크기의 총합이 유효 프레임 수보다 큰 경우
      ![운영체제 9강 (가상 메모리) 이미지 13]({{ '/series/operating-systems/assets/os-10-013.png' | relative_url }})
    - 이걸 계산해서 스레싱이 감지되면 해당 프로세스 중지 등을 통해 쓰레싱을 예방함

  ### 작업 세트 모델의 구현

  - 작업 집합을 추적하는 작업이 필요함
    - 메모리 참조마다 한 쪽에서는 새로운 페이지들이 추가되고 다른 쪽에서는 가장 오래된 참조부<br />터 제외
    - 작업 집합 창 내의 어디에서라도 참조되는 페이지는 작업 집합에 유지
    - 근데 이걸 그대로 만들면 오버헤드가 심함
    - 그래서 근사치를 활용
  - 일정 간격 타이머 인터럽트와 참조 비트를 사용하면 어느 정도 <b>근사할 수 있음</b>
    - 타이머 인터럽트 걸릴 때마다 각 페이지의 현재 참조 비트 값 저장 & 참조 비트는 0으로 재설정
    - e.g. 페이지 폴트 발생 시 바로 앞 현재 참조 비트와 앞서 저장된 2개의 참조 비트 값을 검사
    - 셋 중 어느 한 비트라도 1인 페이지는 작업 집합에 유지, 그렇지 않은 것은 제외

## 페이지 부재 빈도

- 쓰레싱은 결국 페이지 폴트 <b><span color="green">빈도</span></b> (PFF, Page-fault frequency) 문제
- 페이지 폴트는 한 번만 일어나는 게 아님.
  - 시스템 전체적으로 보면 페이지 폴트가 많이 발생하지만, 프로세스 하나의 관점에서 보면 많이 일어날 때랑 일어나지 않을 때가 나뉘어져 있음
- 임의 프로세스에 대해 원하는 페이지 오류율의 상한선과 하한선을 정하고,
  - 상한선 넘으면 더 많은 프레임 할당하고
  - 하한선 넘으면 프레임 회수
  - 이 방식으로 프로세스마다 사용하는 페이지를 효율적으로 배정해 페이지 폴트 빈도를 낮춤

## 커널 메모리 할당 (kernal memory allocation)

- 커널 메모리는 사용자 모드 프로세스에게 할당해 주는 프레임 리스트와 “별도”의 메모리 풀에서 할당
  - 커널의 자료 구조는 페이지 크기보다 작은 크기를 갖음
  - 단편화에 의한 낭비를 최소할 할 필요가 있음
  - 물리 메모리에 직접 접근하는 특정 하드웨어 장치는 물리적으로 연속적인 메모리를 필요로 하는 경우가 있음
- 버디 시스템
  - 물리적으로 연속된 페이지(프레임) 들로 이루어진 고정된 크기의 세그먼트로부터 메모리 할당
  - 할당 시 2의 거듭제곱 단위로 할당함
    - e.g. 33KB 가 필요하면 256 → 128 → 64 로 쪼개서 64 써라 \~ 함
    - e.g. 31KB 가 필요하면 32 까지 쪼개서 32 써라 \~ 함
    - 즉, 최소의 맞는 공간이 만들어 질 때까지 2(buddy)로 나눔
      - 여기서 buddy 는 친구라는 뜻으로, 2로 나누기 때문에 이렇게 말함
  - 반납 시 하나의 큰 세그먼트로 합병
  - 장점 ) 속도가 빠르다
  - 단점 ) 단편화가 발생한다.
    - e.g. 33KB 가 필요한 경우에는 64 를 줘야 함. 그래서 남는 부분이 발생(단편화가 발생) 함. 즉, 메모리 효율성이 떨어짐
  - <b>Q. 그럼 단편화를 없애려면?</b>
    - 슬랩 할당 사용
- 슬랩 할당
  - 같은 크기의 객체들을 위한 메모리 풀(Slab Cache) 을 미리 만들어두고, 그 안에서 객체를 재사용하는 방식
    - 참고로, 메모리 풀은 미리 만들어두지만 실제로 오브젝트는 요청이 들어와야 생성되는 방식임(lazy creation)
    - 그래서 실제로 메모리 낭비가 발생하지는 않음 (미리 만들어뒀는데 안 쓰면 어케? 하는 걱정을 안 해도 됨)

    ![운영체제 9강 (가상 메모리) 이미지 14]({{ '/series/operating-systems/assets/os-10-014.png' | relative_url }})

    - 커널 오브젝트는 운영체제가 관리하는 구조체
    - 캐시는 같은 타입의 오브젝트들을 위해 사용
      - e.g. 모든 3kb 오브젝트를 위한 캐시, 모든 7kb 오브젝트를 위한 캐시
    - 슬랩은 연속된 페이지로 이뤄짐
      - 하나의 슬랩에는 여러 개의 캐시 담을 수 있음
      - 슬랩 안에서 어떤 건 할당되어있고, 어떤 건 비어있음
    - 캐시가 생성되면 free 로 표시된 커널 객체들을 캐시 내에 미리 마련해 놓음
    - 커널 수행 중 커널 객체 가 요청되면, 해당 캐시의 free 객체들 중에서 하나를 할당하고, 할당한 객체를 used 로 표시함
    - 캐시에 할당된 슬랩은 full(모든 객체가 used), empty(모든 객체가 free), partial(used, free 혼재) 중 하나의 상태
    - 커널에서 객체 할당 요청이 오면
      - 먼저 partial 슬랩의 free 이용해 할당
      - 없다면 empty 슬랩의 free 할당
      - <b>없다면 새로운 슬랩 하나를 캐시에 할당</b>
  - 단편화를 줄이고 성능을 향상시킬 수 있음
    - 객체가 미리 생성되어 있기 때문에 빨라. 그래서 성능 향상이 됨
  - 특히 작고 빈번하게 할당/해제되는 객체들 (e.g. 커널 오브젝트) 등에 적합함
  - 슬랩 : 하나 또는 그 이상의 연속된 페이지
    - 그냥 페이지라고 생각해도 무방함
  - 캐시 : 하나 또는 그 이상의 슬랩들로 구성
  - 같은 타입의 커널 객체는 같은 크기. 이들은 같은 캐시에만 할당됨
    - e.g. PCB, 파일 객체 등 커널 내 주요 자료구조
