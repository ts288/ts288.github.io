### 참고 ) 콜스택 프레임

- 구성
  - 파라미터
  - 지역변수
  - return address
    - 호출되는 함수 종료 후 돌아가야 할 주
  - <b>frame point</b>
    - 스택 상의 프레임 시작 주소
    - 하나의 프레임의 크기가 일정하다면, 굳이 이거 없어도 현재 실행 중인 프로그램 끝나면 위치 계산해서 바로 이전 프레임으로 jump 할 수 있음
    - 근데 프레임 크기가 다 달라서 이전 프레임으로 돌아가기 위해 이게 필요함

      - 매개변수 전달 방식 (인자가 스택에 저장될 때도 있고, 레지스터로 전달될 때도 있어서 다를 수 잇음)
      - 등등 때문에 프레임 크기가 다를 수 있음
  - stack pointer
    - 콜 스택의 최상위 메모리 주소

### 커널 수준 문맥

- 저장하는 것들
  - cpu 내의 특수 레지스터 내용
    - 프로그램 카운터 : PC
      - 다음 수행할 명령어 주소 담고 있음
      - 시분할 시스템에서 다른 프로세스로 전환이 되었을 때 이 PC 를 기억하고 있어야, 다음 슬라이스에서 프로세스로 돌아올 때 다음 명령어를 수행할 수 있음
    - 스택 포인터 : SP
      - 스택 관리 위해 사용
    - cpu 상태 레지스터 : PSR (program status register)
      - e.g. 모드 비트, zero flag
      - and 연산을 수행한 다음에 프로세스가 전환되면, 연산 결과를 저장하고 있어야 함. 이걸 zero flag 에 저장했다가, 속개 시에 값을 가져와서 사용
  - cpu 내의 범용 레지스터 내용
    - 일반 계산용 레지스터
  - 프로세스의 현재 자원 사용 정보
  - 커널의 프로세스 관리 정보
- 어디에 저장하는가?
  - PCB 에 저장해둠! 여기다가 save 와 restore 를 반복함!

### 문맥 교환

- cpu 를 다른 프로세스로 넘기는 것
  - cpu 가 현재 프로세스를 종료하고 다른 프로세스를 실행하는 작업
  - 커널 메모리 영역 내에 저장된 pcb 에 현재 실행 중이던 프로세스의 문맥을 저장하고, 다음 실행될 프로세스의 문맥을 가져오는 것
- 실행이 정지되는 프로세스의 문맥은 보존하고, 새로 실행하는 프로세스의 문맥을 가져와야 함
- 사용자 수준의 문맥은 원래 메모리에 잇었기 때문에 그대로 두면 보존됨
- 커널 수준의 문맥 중에서 pc, sp, psr 의 특수 레지서터와 범용 레지스터는 반드시 저장되어야 함.

- 시점
  - 비자발적 문맥교환
    - 시분할 시스템에서 이 일어나는 시점(타임 슬라이스 소진)

  - 자발적 문맥교환
    - 프로세스 스스로가 입출력 요청할 때
      - 입출력 요청하면 cpu 가 현재 프로세스의 상태를 blocked 로 전환함 (당분간은 안 써도 되겠네\~ 하고)
      - 그리고 cpu 는 다른 프로세스 돌리게 됨 (놀지 않기 위해서)
    - 프로세스 스스로 다른 프로세스가 보낸 시그널에 대한 대기를 할 때

### 프로세스 상태

- 생성(new)
  - 프로세스가 생성된 상태
  - pcb 와 메모리 상의 주소 공간이 마련된 상태
- 준비(ready)
  - cpu 의 배정을 기다리는 상태
  - 준비 리스트나 준비 큐에서 스케줄링을 대기하는 상태
    - 이건 커널 메모리에 있음!
    - 커널 메모리에는 준비 큐(리스트) 랑 pcb 가 있고, 준비 큐에는 pcb 의 주소가 저장되어 잇음!
  - 스케줄링에 의해 언제든지 실행이 될 수 있는 상태
  - 준비 상태로 천이되는 경우
    1. 생성에서 들어올 때
    2. 비자발적 문맥교환이 발생할 때
    3. 자발적 문맥교환이 발생할 때
- 실행(running)
  - 프로세스가 cpu 에 의해 실행되는 상태
  - 사용자 모드로 실행되다가 입출력 요청하거나 다른 프로그램에서 들어오는 시그널에 의해 대기 상태로 전환을 요청하게 되면, 시스템 호출(트랩 과정)을 거쳐서 커널 모드로 진입
    - 그러다 입출력이나 대기 요청하면 준비 상태로 천이
  - 프로그램이 끝나거나 exit() 이 호출되면 종료 상태로 천이됨
- 대기(blocked)
  - 프로세스가 사건의 발생을 기다리는 상태 (e.g. 입출력 완료 또는 사건의 접수)
  - blocked 된 기간 동안은 프로세스가 사건 별로 구성된 대기 리스트로 이동해 대기함
  - 대기하던 사건이 완료되면 다시 준비 상태로 천이함
  - <b>대기 상태가 존재한다는 것은 입출력과 cpu 가 동시에 동작하여 overlap 할 수 있는 기반이 됨</b>
    - 대기 상태에서 수행중이던 프로세스의 입출력 처리와, 다음 프로세스의 실행이 병렬적으로 가능하다는 것!
    - 입출력 요청 시에 바로 준비 상태로 천이하게 되면, 입출력 이벤트가 수행되었는지 체크할 수 없어서 cpu 에 다시 할당되는 등의 자원 낭비가 발생할 수 있고, 정확한 처리를 할 수 없음
- 종료(terminated)
  - 프로세스의 실행과정을 마치고 종료된 상태
  - exit() 이 호출되어 커널에 자신의 종료를 요청하는 경우
    - 바로 종료되지 않음. 왜냐면 exit code 가 있어서 exit 의 상태(e.g. 정상 처리, 에러 등) 를 코드로 exit(-1) 이렇게 부모에게 알려주어야 하기 때문!
      - exit code 는 pcb 에 저장됨!
    - 그래서 exit 될 때 wait() 상에 있는 부모 프로세스에게 종료를 알림
    - <b>만약! 부모가 대기 상태에 있지 않다면, 자식 프로세스의 주소 공간과 할당 자원은 없어지지만 pcb 는 유지됨!(exit code 를 부모에게 알려주어야 하니까!) 이걸 </b><b><span color="orange">좀비상태</span></b><b> 라고 함</b>
    - 이 상태는 exit code 를 부모가 가져갈 때까지 유지됨!
  - abort() 는 다른 프로세스의 종료를 요청하는 것
    - 주로 부모 프로세스만이 할 수 있음
      - e.g. 쉘에서 응답 없으면 ctrl + c 해서 강제 종료하는 거
      - 이를 위해서 fork() 의 리턴값으로 자식 프로세스의 pid 를 알려줌

- <b><span color="blue">프로세스 상태 천이도 (중요)</span></b>
  ![운영체제 3장 이미지 3]({{ '/series/operating-systems/assets/os-03-003.png' | relative_url }})

  - 비자발적 문맥교환이 발생하면 바로 준비 상태로 천이
  - 자발적 문맥교환이 발생하면 대기 상태로 천이했다가, 입출력 완료나 사건이 완료되면 준비 상태로 천이
  - <b>어떠한 경우이든 실행 상태로 천이되기 위해서는 준비 상태를 거쳐야 한다!</b>
  - 상태 천이도를 볼 때 스케줄링이란?
    - 준비 리스트나 준비 큐에 있는 것을 선택해 cpu 가 실행할 수 있도록 타임 슬라이스 배정하는 것

### 프로세스 제어 블록 (PCB)

- process controll block
- 문맥이랑 상태는 어디에 저장되나? → pcb!!
- 프로세스의 일생 동안 프로세스의 모든 정적, 동적인 정보 저장
  - 일종의 저장소!
- 커널이 프로세스 관리하기 위한 실체
- 리눅스에서는 이걸 task struct 라고 부름!
- <b>상태 천이도의 준비 리스트나 준비 큐는 사실 pcb 의 리스트였음!!</b>
- <b>실행상태는 프로세스가 실행된다는 사실임! 그냥 표시임! 그래서 준비 리스트에 있는 pcb 에 running 이라고 상태를 표시하는 것! pcb 는 준비 리스트 안에 존재하면서, cpu 는 실행 표시된 프로세스를 실행시키는 것</b>
- pcb 가 저장하는 정보
  - 프로세스 상태
  - 레지스터 문맥
  - 자원할당 및 사용 정보
  - pid
  - cpu 스케줄링 정보
  - 등등

### <span color="blue">시스템 호출, 문맥 교환, 인터럽트 (이거 중요할 듯! 기억. 3장 5번 영상)</span>

- read() 함수가 호출되면
  1. 커널 모드 실행으로 전환된다
     1. 응용 모드가 불러오기 원하는 파일의 위치를 찾아야 함
     2. 그래서 이걸 버퍼 캐시에 있는지 확인하고, 있다면 복사해서 return 함
     3. 없다면 디스크 I/O request block 을 생성하고, 디스크 I/O 큐에 입력
  2. 디스크 제어기에 I/O 명령을 내려 작동을 지시한다
     1. 이 시점부터 현 프로세는 cpu 를 반납하고 대기 상태로 전환
  3. 이를 위해 sleep\_on 함수를 호출 → 대기 상태로 진입
     1. 현 프로세스 pcb의 상태 정보를 <b>blocked</b> 로 변경 (running → blocked)
     2. 현 프로세스 pcb를 준비 리스트에서 삭제 후에, 사건 종류별 대기 큐에 삽입
        1. <b>중요 ) pcb 가 실행 상태이더라도, 준비 리스트에 있을 수밖에 없고, 준비 리스트에서 실행중이라고 표기되는 것임!</b>
  4. 준비 리스트에서 우선순위가 가장 높은 pcb 선정 (스케줄링)
     1. context\_switch 함수 호출해 현재 프로세스 문맥을 해당 pcb 에 보존, 새 프로세스 pcb 에 저장된 정보를 cpu 에 reload
     2. 그럼 로드된 정보에 pc 가 있기 때문에 jump 가 가능함
  5. 입출력 요구한 프로세스(sleep\_on 된 프로세스) 의 pcb 를 대기 큐에서 제거햐여 준비 리스트에 삽입
     1. 다시 프로세스 속개하기 위한 준비
     2. 사건이 끝났으니, 사건이 끝난 프로세스를 깨운다는 뜻 (wakeup\_process)
  6. 인터럽트로부터 복귀
     1. disk I/O 큐 상의 다음 디스크 I/O 요청 블록에 해당하는 정보로 디스크 제어기에 명령 내려 다음 입출력 시작
     2. 그리고 복귀하는데, 준비 리스트에 변화가 있었으니 스케줄러와 문맥교환이 동작함
        1. wakeup 된 프로세스가 당장 실행되지 않을 수도 있음!
  7. 이 사이에 I/O 가 처리되고, 처리가 완료되면 sleep\_on 에서 return 됨
     1. 리턴되는 지점은 ‘그럼 로드된 정보에 pc 가 있기 때문에 jump 가 가능함’ 이거 이후 지점!
     2. 여기로 복귀되었다는 것은 , 이미 대키 큐를 빠져 나와서 준비 상태를 거쳐 스케줄링 결과로 실행 상태로 되었다는 것!
     3. 그래서 상태는 blocked 에서 running 이 된 상태일 거임!
     4. 그 다음 응용 프로그램에서 return 다음 줄이 실행됨

### 프로세스의 생성

- fork()
  - 부모는 단 하나
  - fork() 는 프로세스를 복제하는 시스템 콜이다.
  - fork() 의 리턴은 부모 프로세스와 자식 프로세스 두 곳으로 리턴이 일어남
    - 근데 값은 상이함 → 한 프로그램으로 부모 프로세스와 자식 프로세스가 다른 로직 수행하게 하기 위함
    - 부모한테 리턴되는 값은 자식 프로세스의 pid
    - 자식한테 리턴되는 겂은 0
  - fork() 를 수행하는 순간 가상적인 cpu 가 하나 만들어져, 동일한 프로그램을 따로 시작하게 된 것임
  - 자식이 부모 pid 얻으려면 getppid() 사용해야함
  - fork() 이후에 사용자 문맥의 text 는 공유하되, data, stack 공간은 별도로 생성됨
    - 엄밀히 말하자면, 가상 공간은 분리되지만, 실제 물리적인 메모리 공간은 부모와 공유함
    - 그러다가 자식 프로세스에서 변수를 수정하려고 할 때 그 때 스택이 복제되어 자식 전용 물리 메모리가 생성됨
    - <b>cf ) 변수 하나만 고쳐도 페이지 단위 전체가 복사됨</b>
    - 이걸 <b>게으른 복사 (cow; copy on write)</b> 라고 함
      - text 는 게으른 복사 이후에도 부모 걸 씀
      - data 랑 stack 만 복제되는 것!
    - pcb 는 fork() 직후에 바로 물리적으로 새로 생성됨
  - fork() 로 생성된 자식 프로세스는, fork() 이후의 코드 실행
    - pcb 에 부모 pc 가 담긴다는 거죠\~
  - fork() 에 의해 커널 내부에서 일어나는 일
    - pcb 가 새로 생성됨
    - 부모 pcb 에서 복제해옴 (Cloning) == 자원 상속
      - 완전히 똑같지는 않음! pid 같은 건 달라야 함
      - 부모가 open 한 파일, 동기화 자원, 우선순위 정보 등
    - 레지스터 문맥 복제
      - 부모 프로세스의 특수레지스터 및 범용레지스터 값도 자식 프로세스의 초기값으로 복제되나, 각자 수행되는 즉시 값들은 달라짐
    - 사용자 수준 문맥 복제
      - text 영역은 부모와 자식 프로세스가 공유
      - data(bss 포함), heap, stack 영역은 복사되어 별도 할당
- exec family

  - exec 는 다른 프로세스를 실행시키는 함수
    - 이거 실행하면 프로세스의 exec 이 실행하고자 하는 프로세스에 맞게 pcb 를 덮어씀
    - pid 는 원래 걸 그대로 씀

      <li markdown="1">
      pcb 공간도 원래 걸 그대로 씀

  - fork() 다음에 자식 프로세스에서는 exec() 해주면 부모와 다른 프로세스를 실행할 수 있음

### 정리

- 사용자 문맥(text, data, stack) 은 메모리에 저장됨
  - 연산이 필요하면 메모리에서 레지스터로 가져와서 연산을 함
- pcb 는 커널 메모리에 저장됨
  - 여기에는 커널 문맥과 사용자 문맥이 있음
  - 커널 문맥 (레지스터) 는 실제 값이 저장되어 있고, 사용자 문맥은 실제 값은 다른 주소에 위치하고, pcb 는 그 주소 공간의 값만 가지고 있음
- fork() 가 호출되면
  - 현재 레지스터에 있는 값을 그대로 부모 pcb 에 옮김
  - 부모 pcb 에서 일부 값을 복제해서 새로운 자식 pcb 를 만듦
  - 처음에 수행될 때는 자식 pcb 가 부모의 pcb 가 가리키는 사용자 문맥의 주소를 똑같이 가리킴
    - 이걸 자식으로 사용자 문맥이 복제된다고 봐도 됨. 어차피 주소 공간을 같이 가리키는 거니까
    - <b>근데 복제되는 게 주소 공간이 값으로 복제되는 거지, 실제 값이 값으로 복제되는 건 아닌 것만 기억!</b>
  - 그러다 자식 프로세스에서 변수의 수정이 일어나면, 일단 부모 pcb 가 가리키는 주소의 값을 복제해서 새로운 메모리 공간에 할당하고, 그 주소 공간의 위치를 자식 pcb 에게 전달 (이게 cow)
- 참고로, 커널 문맥은 pcb 에 그대로 값을 가져가기 때문에 cow 가 불가능함

### 쓰레드

- 전통적 프로세스(heavy weight process)
  - 전역변수 담는 영역을 프로세스마다 각각 가지고 있어서, 프로세스 간의 공유 변수를 갖기 어렵다
    - 운영체제가 제공하는 특수 구조체나 공유 파일을 사용해야 한다.
  - fork() 시 text 만 공유하고 나머지 영역 모두를 복사해 생성 → 시간적 오버헤드와 메모리 낭비 초래
- 쓰레드(light weight process)
  - <b>text 뿐만 아니라 data 영역까지 공유함</b>
    - <b>data 영역이 공유되어, 각 스레드가 전역 변수 영역에 접근할 수 잇어서, 모든 스레드가 데이터 공유 가능</b>
  - <b>스택만 따로 가짐!</b>
  - 한 프로세스 내에 여러 개의 스레드 구성 가능
  - 생성이 빠르고 자원 점유가 적음
  - 프로세스는 단 하나의 수행 flow 만 갖고 있기 때문에 제한적임
    - 이를 해결하기 위해 fork() 를 사용. 근데 이것도 문제가 있음
    - <b>그래서 이를 해결하기 위해 ! 프로세스 내부에 작은 실행수단을 만들어서 각각이 별도의 수행 flow 를 가지면 좋겠다 ! 생각해서 쓰레드를 만듦</b>!
    - 쓰레드 하나하나가 실행 flow 임! <b>가상 혹은 실제의 cpu</b> 가 할당된다고 생각하면 좋음
  - 스레드 별로 각각의 프로그램 카운터(pc) 를 갖고 있음

      - 각 스레드가 커널에 의해 따로 관리되기 때문에 타임 슬라이스를 각각 받음
      - <b>한 스레드가 입출력 요청해도 다른 프로세스까지 대기 상태로 들어가지 않음 (장점 : 간섭이 없음) - 하나하나 커널이 관리해주니까</b>
      - <b>생성과 관리가 느리다 (단점)</b>

      - 사용자 스레드는 프로세스가 받은 타임 슬라이스를 스레드 라이브러리가 다시 스레드로 분배함
      - 커널은 프로세스만 알고 스레드는 모름
      - <b>한 스레드가 입출력을 요청하면 프로세스 전체가 대기 상태로 들어감 (단점 : 간섭이 있음) - 뭉탱이(한 프로세스)로 커널은 알고 관리하니까</b>
      - <b>커널에 의해 관리될 필요가 없어 생성과 관리가 빠름 (장점)</b>
    - 혼합형 스레드 (그냥 참고)
      - 사용자 스레드와 커널 스레드를 섞은 것
      - 대표적인 예로 LWP(light weight process) 가 있음

        - 하나 이상의 사용자 스레드를 묶어서 커널 스레드랑 매핑시켜줌
