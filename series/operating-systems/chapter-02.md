### Q. 같은 메모리에 응용 프로그램이랑 커널이 둘 다 올라가는데, 어떻게 이걸 하드웨어 지원을 통해 분리하는가?

- cpu mode 와 user mode 를 구분해서, 사용할 수 있는 메모리 영역을 제한하고, user mode 에서 커널 영역에 접근하는 것을 차단함
  - 추가로 MMU (Memory Management Unit), 페이지 권한 설정 등도 사용해, 사용자 프로세스가 커널 영역에 접근하지 못하도록 차단!
- 각각의 모드에서 사용할 수 있는 명령어가 달라짐
  - mov cr3, eax 같은 명령어는 cpu mode 에서만 사용 가능!
- <b>Q. 근데 이러면 소프트웨어 지원 아닌가요?</b>
  - cpu mode 와 user mode 를 설정하는 부분이 cpu 내부에서 플래그(제어 비트)로 관리되어서 하드웨어 지원이라고 하는 것!

### Q. 응용 프로그램과 커널이 같은 메모리 공간에 존재하는데, 어떻게 하드웨어적으로 분리될 수 있을까?

- CPU는 <b>user mode</b>와 <b>kernel mode</b>를 구분하여, 각 모드에서 허용되는 연산과 접근 권한을 제어함
  - user mode에서는 커널 영역 메모리에 직접 접근 불가능
  - <code>mov cr3, eax</code> 같은 특권 명령어는 kernel mode 에서만 실행 가능
- MMU(Memory Management Unit) 와 페이지 테이블, 권한 비트 설정을 통해 메모리 접근을 하드웨어적으로 보호함
- 즉, 단순한 소프트웨어 규칙이 아니라, CPU 내부 플래그(제어 비트) 로 모드가 전환되고 제한이 걸리기 때문에 <b>“하드웨어 지원”</b> 이라고 함

### 시스템 호출 (sys call)

- 응용 프로그램과 커널이 만나는 곳에 시스템 호출이 있다.
- 응용 프로그램을 개발할 때 함수 호출하는 것과 큰 차이가 없다.
  - e.g. printf(), open() 등

  ![운영체제 2장 이미지 2]({{ '/series/operating-systems/assets/os-02-002.png' | relative_url }})
- 응용 프로그램에서 시스템 호출과 관련된 라이브러리 함수를 사용하면(e.g. open()), 커널 내 시스템 콜 테이블에서 해당 함수가 i 번째 함수임을 알아내서 처리를 하고, 처리 후에 다시 user mode 로 돌아가서 응용 프로그램의 다음 라인을 수행함

### 시스템 호출을 하는 방법

- 시스템 호출도 함수 호출과 동일하기 때문에 파라메터 전달이 필요하다
- <b>파라메터 전달 방법</b>
  - linux, solaris - 레지스터를 통한 주소 전달
    - 전달할 파라메터를 사용자 공간 내 x 라는 주소로 기록
    - x 라는 주소를 특정 레지스터에 로드
    - 커널에서 나중에 x 의 주소를 얻어 파라메터에 접근
  - 스택 활용
    - 스택에 파라메터 값을 push 하면 커널에서 pop
- 커널에 시스템 호출 사실을 알리는 방법
  - cpu 내의 레지스터에 담은 후 인터럽트를 거는 cpu 명령어 수행
  - 여기서 cpu 명령어를 <b>트랩(trap)</b> 또는 <b>소프트웨어 인터럽트</b> 명령어 라고 함
    - 하드웨어적 인터럽트랑은 다른 개념
    - e.g. x86 - int, arm - swi
- 응용 프로그램에서 입출력 함수를 사용하면 → 파라미터를 레지스터에 저장 → 커널에 시스템 호출 알람 → 커널에서 레지스터 값 읽음 → 해당하는 함수 실행

## 동기식 vs 비동기식

- 시스템 호출에는 동기식과 비동기식이 있음
  ![운영체제 2장 이미지 3]({{ '/series/operating-systems/assets/os-02-003.png' | relative_url }})
- 동기식 (왼쪽, 맨 위에 waiting 이 있음)
  - blocking call
  - e.g. read() 가 수행되는 동안 멈춰있다가, read() 가 끝나면 다음 로직 실행
  - <b>멈춰있는 동안 cpu 는 다른 프로세스 수행함 (프로세스 관점에서의 동기식 흐름을 말한 거임)</b>
    - 이게 가능한 이유는, 입출력 요청하면 blocked 상태로 전환되기 때문임!
    - 입출력이 완료되면 인터럽트가 들어와서 해당 프로세스를 다시 ready 상태로 전환해줌
- 비동기식 (오른쪽)
  - sysCall 하고 다음 로직 수행함
  - sysCall 이 끝나면 이벤트가 전달됨
  - 이 이벤트를 처리할 함수(callback 함수) 를 이벤트로 알려줘야 함

  ### Q. 비동기식 프로세스는 입출력 요청시 blocked 상태로 전환되지 않는가?

  - 그렇다! 전환되지 않고 바로 다음 코드가 실행됨

## 입출력 시스템

### 입출력 흐름

```kotlin
1. 응용 프로그램 (User Program)
   ↓
2. 트랩 (Trap Instruction, 예: syscall)
   ↓
3. 시스템 콜 인터페이스 (System Call Interface)
   ↓
4. 커널 모드 진입 (Privilege Level 변경)
   ↓
5. 커널의 I/O 서브시스템 → 입출력 함수 (예: sys_read, sys_write)
   ↓
6. 디바이스 드라이버 (Device Driver)
   ↓
7. 디바이스 컨트롤러 (Device Controller)
   ↓
8. 실제 장치 (Device: 예, 키보드, 디스크, NIC 등)
```

- 입출력 장치의 장치 제어기가 <b>시스템 버스</b>에 장착되어 있음
  - 물리적인 입출력 장치가 바로 버스에 접촉된 게 아니라, 장치 제어기를 통해 연결되어 있음
- 하드웨어 = 입출력 장치는 디바이스 컨트롤러와 디바이스(물리적인 장치) 로 구성됨
- 커널 내에 있는 디바이스 드라이버가 장치 제어기(디바이스 컨트롤러) 를 컨트롤 하고, 장치 제어기가 물리적 장치를 컨트롤 함
  - <b>디바이스 드라이버와 장치 제어기 사이에 있는 인터페이스가 시스템 버스임</b>
  - <b>cf) 응용 프로그램과 커널 사이에 있는 인터페이스는 시스템 호출 (syscall)</b>
- <b>디바이스 드라이버와 디바이스 컨트롤러 (장치 제어기) 가 정보를 주고 받는 것은 장치 제어기 내의 레지스터에 값을 읽거나 쓰는 것!</b>
  - 장치 제어기의 레지스터는 메인 메모리의 주소에 매핑되어 있음
  - 디바이스 드라이버는 이 주소에 값을 쓰거나 읽음으로써 장치 제어기를 컨트롤
- <b>장치 제어기 내의 레지스터</b>
  - 명령 레지스터
    - 장치에 쓰기나 읽기 등의 명령을 하기 위해 명령 코드를 적재하는 부분
  - 상태 레지스터
    - 해당 장치에 오류가 있는지, 작업이 진행 중인지, 작업이 끝났는지 플래그, 오류코드로 표현하는 부분
  - 자료 레지스터
    - 명령 레지스터를 통해 명령을 수행하면서 필요한 데이터를 저장하는 버퍼
- 인터페이스 세 가지
  - 시스템 호출
    - 응용 프로그램이 커널 함수 사용하기 위해 호출해야 함
  - 시스템 버스
    - cpu 랑 입출력 장치가 메모리에 접근하는 통로
    - 여기서 cpu 랑 입출력 장치가 동시에 메모리에 같은 부분에 접근하려 할 수 있다!
      - 입출력 장치가 독립적으로 메모리 접근 가능하게 하는 방식을 dma 라고 함
    - 이걸 해결하기 위한 방법 중에 하나가 cycle-stealing 이다!
      - cpu 에게 접근 사이클을 양보받는 것!
      - cpu 입장에서는 한 사이클만 양보하는 거기 때문에 성능에 영향을 거의 미치지 않는다
  - 커널과 인터페이스 사이에 인터페이스가 필요 → 디바이스 드라이버
    - 커널이 배포된 이후에 소스코드 변경 없이 새로운 디바이스 추가할 수 있게 하기 위함
    - 커널 안에 디바이스 드라이버가 등록되면, 디바이스 드라이버의 번호와 함수 테이블이 등록됨
    - 디바이스 드라이버는 커널 모드에서 커널과 함께 동작하기 때문에, 디바이스 드라이버가 커널 내 커널 함수나 변수를 호출할 수도 있음
      - 그래서 조심히 만들어야 함!
  - HW 인터페이스 (하드웨어 인터페이스)
    1. 접근 방식에 대한 분류
       1. 격리형(isolated I/O, I/O mapped I/O)
          1. 입출력 장치가 메모리와는 별도의 주소 공간 가짐
             1. 메모리(ram) 상의 공간이 아니라, cpu 내의 아키텍쳐에 정의된 포트에 매핑됨
             2. 그래서 ram 을 잡아먹지 않음
          2. 메모리 주소 지정 위해 사용하는 주소 지정 버스와는 다른 I/O 장치를 위한 주소 라인을 따로 사용하기 때문에 주소 값이 메모리인지, 입출력 장치인지 제어하는 제어라인을 따로 사용하는 하드웨어를 전제로 함 → 그래서 특수한 입출력 명령어 사용함
          3. 장점 : 입출력이 메모리 주소 공간의 크기나 할당에 영향을 주지 않음
          4. 단점 : 별도의 입출력 명령어를 사용하게 되어 프로그래밍 일관성이나 이식성이 떨어짐
       2. 메모리 사상형(memory mapped I/O)
          1. 격리형과 반대로, 메모리 주소 지정과 I/O 장치 위한 주소 지정을 위한 라인을 공유함.
          2. 주소 자체로 메모리 주소인지, I/O 주소인지 판단함
          3. 메모리에 할당된 주소 일부를 장치 제어기에 접근하는 주소로 사용할 수 있음
          4. <b>메모리의 논리적 주소 공간에 제어기의 레지스터를 사상(mapping)</b>
          5. 별도의 명령어 필요 없고, 기존에 메모리 접근하던 명령어 사용하면 됨
          6. 장점 : 명령어 개수를 줄일 수 있어서 프로그래밍 일관성 확보 & 이식 용이
          7. 단점 : 입출력 위해 메모리 일부를 사용해 메모리 영역이 감소함
    2. 자료 이동 방식에 대한 분류 (장치 제어기 내의 레지스터와, 메인 메모리 내의 데이터가 어떻게 이동하는가? == 레지스터 접근 방식)
       1. 직접 입출력 방식
          1. cpu 가 장치 제어기 내의 자료 레지스터와 메모리 사이의 메모리 전달을 매번 관리함
          2. 단점 : 매 입출력 시 인터럽트가 들어와 cpu 에 부담이 될 수 있음
             1. → 입출력 발생의 시간이 비교적 큰 문자장치(e.g. 키보드)에서는 문제가 되지 않지만, 디스크와 같은 블록장치(e.g. 하드디스크)에는 문제가 됨
          3. <b>블록 입출력을 위해 매 바이트마다 인터럽트 걸고 가져올 수는 없음!</b>
             1. 이거 해결하기 위한 게 DMA 임
       2. DMA(direct memory access)
          1. 직접 입출력 방식과 다르게 cpu 도움 없이 독자적으로 메모리 또는 시스템 버퍼에 다이렉트로 접근해서, 한 명령어로 블록을 입출력할 수 있도록 하는 방식
          2. 메모리 입장에서는 cpu 랑 dma 가 각각 독립적으로 접근하기 때문에 동시에 접근가능하다는 문제가있음
             1. 이를 해결하기 위해 cycle-stealing 을 도입함
             2. cpu 와 dma 가 동시에 메모리에 접근하면 dma 에 우선권을 주고, cpu 는 한 사이클을 쉬게 하는 방식 (cpu 입장에서 i/o 는 가끔 일어나기 때문에, 우선권을 dma 에게 넘겨도 cpu 성능에 문제가 없기 때문)
          3. 한 블록의 입출력 완료시 한 번만 인터럽트 발생시켜 인터럽트 발생 빈도를 줄임
    3. 제어 방식에 대한 분류 (장치 제어기의 상태를 디바이스 드라이버 or cpu 에 어떻게 전달하는가 == 제어기 상태 변화 전달 방식)
       1. 폴링
          1. cpu 가 레지스터를 반복적으로 직접 체크하면서 목표한 상태로 변화햇는지 확인하는 것
          2. 상태 변화가 있을 때까지 cpu 는 계속 확인하면서 대기
          3. 폴링 순서는 다음과 같다.
             1. 응용 프로그램으로부터 입력 요청이 오면
             2. 디바이스 드라이버가 장치 제어기의 명령 레지스터에 명령어 적재
             3. 하드웨어 적으로 장치를 가동시킴
             4. 명령에 의한 장치의 동작이 끝날 때까지 대기 : 상태 레지스터를 계속 체크(폴링) 하여 busy → done 으로 변환하는지 루프를 돌며 대기
             5. done 이 되면 제어기의 자료 레지스터 내용을 응용 프로세스 공간으로 복제
          4. 단점 : 루프를 사용하며 대기(busy-waiting) 하는 방식이기 때문에 cpu 를 낭비함
          5. 인터럽트가 없는 장치의 경우 폴링 방식을 사용해야함
       2. 인터럽트
          1. cpu 가 디바이스 드라이버의 코드를 실행하면 결국 입출력 장치의 명령어를 장치 제어기로 전송하게 됨
          2. cpu 가 다른 프로세스를 수행하고 있으면, 입출력 작업이 끝났음을 장치 제어기가 cpu 에게 알림 (인터럽트)
          3. 하드웨어가 인터럽트 처리를 전제로 하고 있음을 기반으로 함
          4. 인터럽트
             1. 단계는 아래와 같다.
                1. 중단
                   1. 현재 진행중인 프로세스 or 하위 ISR (다른 인터럽트 처리 중이엇을 수도 잇음. 기존에 처리 중이던 ISR 우선순위가 낮으면) 수행을 즉시 중단
                2. 문맥보존
                   1. 프로그램 카운터(PC) 및 cpu 레지스터 값들을 보존
                3. <b>마스크설정</b>
                   1. 현재 인터럽트에 해당하는 ISR 로 진입하기 전에, 현재 인터럽트에 해당하는 마스크 설정해 주어야 함 → 인터럽트 실행 도중 자신보다 낮은 우선순위의 인터럽트가 들어올 경우, 낮은 우선 순위의 인터럽트가 먼저 처리되지 않게 하기 위함
                4. ISR 진입
                   1. 현재 인터럽트에 해당하는 ISR 로 점프(PC 를 해당 ISR 의 첫 주소로 세팅).
                   2. ISR 주소는 인터럽트 백터 테이블에 장치번호 순서대로 기록되어있음
             2. 인터럽트 처리 후 (ISR 처리가 끝난 이후)
                1. 인터럽트 당한 프로세스 or 기존에 수행 중이던 하위 ISR 을 계속 실행시키기 위해서 보존된 레지스터 내용과 PC 를 복구
                   1. 기존에 여러 프로세스가 실행 중이었다면, 어느 걸로 복구할지는 운영체제가 결정(스케줄링의 중요 포인트 중 하나)
             3. 다수준 인터럽트와 인터럽트 마스크
                1. 여러 입출력 장치에서 인터럽트가 들어오면, 인터럽트 간의 경쟁 or 충돌이 발생할 수 있음
                2. 이를 해결하기 위해 인터럽트 우선 순위 수준이 적용되게 해둠. 수준이 다양할 수 있어서 다수준 인터럽트 라고 함.
                3. 시스템 전체적으로 모든 장치에 대해 비트(비트번호) 를 지정
                   1. 이걸로 모든 디바이스의 인터럽트 번호를 저장
                4. 인터럽트 마스크를 통해 수준 적용
                   1. 우선 순위 비교
                      1. 마스크에는 자기보다 우선적으로 동작할 수 있는 인터럽트가 담김
                      2. 새로 들어온 인터럽트와 마스크를 and 연산해서 false 가 아니면 새로 들어오는 인터럽트가 상위의 인터럽트임을 나타냄
                   2. 모든 인터럽트의 ISR 시작에 앞서 마스크를 설정하고, 끝나면 원상복구 해야함

### 보호

- 이중 모드와 모드비트
  - 커널 모드와 사용자 모드를 분리하는 것을 이중 모드라고 함
  - 메인 메모리를 사용자 공간과 커널 공간으로 나누고, cpu 가 사용자 공간을 사용할 때는 사용자 모드, 커널 공간을 사용할 때는 커널 모드를 사용하는 것
  - 한 프로그램의 에러가 다른 프로그램으로 전파될 수 있기 때문에, 커널이나 다른 프로그램의 오동작을 야기할 수 있는 소지가 잇는 명령어는 커널 내에서만 수행될 수 있도록 통제
    - 응용 프로그램이 실행하면 오동작 야기할 가능성이 잇는 명령어를 커널에 모아두고, 이를 실행할 때에는 운영체제 허가 받아서 커널 모드로 진입한 다음에 수행하도록 한다 (트랩 & 시스템 콜)
  - cpu 내의 상태 레지스터 중 1비트를 모드비트로 사용해 나타낸다.
    - 0 이면 커널 모드, 1이면 사용자 모드
    - cpu 는 모드 비트가 0 일 경우만 특권 명령어를 사용함
  - <b>시스템 콜이 호출되면 트랩 과정에서 모드 비트가 0 으로 설정됨! 해당 시스템 콜이 리턴될 때 다시 모드 비트가 1로 설정됨!</b>
  - <b>커널 모드에서는 하드웨어적인 제어나 보호를 수행하지 않기 때문에 신중하게 코드를 짜야 한다.</b>
- 보호대상
  - 불법 I/O
    - 응용 프로그램의 잘못된 입출력에 대한 보호
    - 모든 I/O 관련된 명령어를 특권 명령어로 설정하고, 시스템 호출을 통한 트랩으로만 I/O 가능하게 함
    - 메모리의 커널 영역 보호 수단과 함께 사용하면 좋음
      - ISR 영역, 시스템 버퍼 영역, 인터럽트 백터 영역 보호
  - 불법 메모리접근
    - 응용 프로그램이 다른 프로그램이나 커널 영역을 침범하지 않도록 보호
    - 특권 명령어로만 접근할 수 잇는 base 레지스터와 limit 레지스터를 사용
    - <b>메모리 관리 유닛 </b>은 이 두 레지스터를 확인해서, 특정 프로그램이 허용된 범위를 넘어가는지 체크
      - 만약 넘어간다고 하면 오류에 대한 트랩이 발동해 cpu 가 에러를 처리
    - 가상 메모리를 활용할 경우, 페이지 단위로 보호됨
  - 무한루프
    - 응용 프로그램이 무한 루프 돌지 않도록 보호
    - 타임 슬라이스 활용함
    - 타이머 인터럽트 인터벌 지정이나, 이를 최고 우선순위 인터럽트로 지정하는 것을 특권 명령어로만 수행하게 함
      - 이로써 응용 프로그램이 임의로 타임 슬라이스를 조정할 수 없게 되어, 매 타임 슬라이스마다 다른 프로세스가 실행되어 한 프로그램이 cpu 를 독점할 수 없게 함(무한루프 방지)

### 기타

- 캐시
  - cpu 내에 존재.
  - 레지스터와 메모리 사이에서 접근 속도 또는 전송량의 격차를 완화시키기 위해 존재
  - cpu 에서 메인 메모리로 접근 시 자료를 캐시에 복사해두과, 다음 번 접근 시에 캐시를 먼저 방문하여 캐시에 자료가 있으면 (캐시 히트) 바로 가져오고, 아니면 메모리 감
  - 찾는 데이터가 캐시에 있을 확률을 <b>hit ratio</b> 라고 함
    - 캐시 용량이 한정되어 있으므로, 근일 내에 다시 접근할 데이터만 선별하여 관리하는 정교한 알고리즘이 필요함
  - 캐시 개념을 확장하면 시스템 전체의 기억장치 효율이 향상됨
  - 메모리의 계층 구조
    ![운영체제 2장 이미지 4]({{ '/series/operating-systems/assets/os-02-004.png' | relative_url }})

    - 아래로 갈 수록 용량 up 속도 down
    - 레지스터와 메인 메모리 사이에서 캐시가 속도차 극복 & 용량 극복의 역할을 한다면,
    - 하드디스크와 캐시 사이의 메모리도 같은 역할을 할 수 있음
    - 이걸 확장해 계층식으로 관리하면 맨 아래 자기 테이프의 용량을 레지스터의 속도로 접근 가능(아주 이상적)
- 부트스트래핑
  - 남의 도움 없이 스스로 할 수 있는 것 이라는 뜻
  - 운영체제의 시동을 운영체제의 일부가 수행하는 것을 뜻함
  - 부팅시퀀스 (체인 로딩 방식 : 작은 프로그램에서 시작해 더 큰 걸 적재하고 거기로 점프하는 걸 반복)
    - 전원이 처음 들어오면 ROM 에 저장된 롬 로더라는 프로그램이 제일 먼저 수행됨
    - 롬 로더는 DMA 를 이용해 디스크 0번 섹터(부트 섹터) 에 존재하는 마스터 부트 레코드로부터 부트스트랩 로더 (부트로더) 의 첫번째 블록을 읽어 메인 메모리 적재
    - 적재 후 이 블록으로 시작 주소로 점프해 역할을 마침
    - 첫 번째 블록이 수행되며 부트로더의 나머지 부분이 순차적으로 적재됨
    - 이후 자신(부트로더)을 메모리의 상위 장소로 옮긴 후 커널 프로그램을 읽어 하위 기억장소에 적재
    - 커널 적재가 끝나면 약속된 장소로 점프하여 커널 시작시킴
- 모노리틱 커널 vs 마이크로 커널
  - 모노리틱 커널
    - 커널이 하나로 되어 있다.
      - 프로세스 관리, 메모리 관리, 네트워크 관리 등 모든 기능을 커널에 포함하고 있다.
    - 다른 프로그램으로의 이식성이나 확정성에서는 한계가 있음
      - 이걸 해결하기 위해 하드웨워 환경에 종속적인 부분을 계층 구조로 분리
    - 장점
      - 커널이 하나로 되어 있어 시스템 호출 속도가 빠르다
    - 단점
      - 새로운 하드웨어에 대한 이식성 떨어짐
      - 한 부분에서 발생한 에러가 전체로 전파될 수 있음
      - 구성요소 간 의존성이 높아져 디버깅이 어려움
  - 마이크로 커널
    - 프로세스간 통신, 메모리 관리 등 핵심 기능만을 커널에 포함시키고, 나머지는 서버 형태로 두어 사용자 모드의 프로세스로 수행한다.
      - 파일 시스템이나 디바이스 드라이버도 유저 모드에서 돈다
      - 인터럽트도 아주 중요한 인터럽트를 제외하고는 인터럽트 서비스 프로세스에 메세지 보내 처리한다.
    - 응용 프로그램으로 부터 I/O 요청이나 장치 드라이버 요청이 들어오면, 해당하는 서버로 메세지를 보내주는 방식
      - 그래서 유저 모드와 커널 모드를 전환하는 비용이 많이 듦
    - 장점
      - 유연성이 좋다.
      - 한 부분에서 발생한 에러가 전체로 전파되지 않는다.
      - 커널이 소형화 되어 잇어 필요한 부분만 골라서 제품 구성이 가능해 소형 내장형 시스템에 구축하기 용이
    - 단점
      - 파일 서비스 등에서 프로세스 문맥 교환 등에서 비용이 발생해 속도가 느려질 수 있다.
