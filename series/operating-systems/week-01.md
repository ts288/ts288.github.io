# 운영체제 1주차

- 의자와 컵 (자원) 중에 수량이 한정된 것을 <b>limited resource</b> 라고 한다
- 자원이 한정되어 있으면 프로세스 간의 경쟁이 일어난다
- 운영체제는 이러한 상황을 타개하기 위해 <b>정책</b>을 세운다
  - 한정된 자원으로 가급적 많은 프로세스가 자원을 이용할 수 있도록
- <b>한정된 자원에 대한 사용자 간의 경쟁이 존재함. 운영자는 그 경쟁을 조율하기 위한 정책이 필요함</b>
  - 운영자는 os, 정책은 알고리즘
- <b>역삼각형 구도가 만들어짐</b>
  - 프로세스가 제일 많고, 자원이 적음
- 운영체제는 효율성과 편의성, 일관성을 추구함
  <ul markdown="1">
  <li markdown="1">

  </li>
  <li markdown="1">

  </li>
  <li markdown="1">

  </li>
  <li markdown="1">
  효율성과 편의성은 양 극단에 존재함
  </li>
  <li markdown="1">
  운영체제는 용도에 따라 최적점을 유지해야함
  </li>
  </ul>

## 초기 일괄처리 시스템

- 어떻게 하면 효율성을 높일 수 있을까?
  - <b>주 컴퓨터와 위성 컴퓨터를 분리</b>하는 것
  - 주 컴퓨터는 계속 작업, 위성 컴퓨터는 프로그램을 적재하거나, 결과물을 출력하도록 <b>역할 분담</b>
  - 사용자가 요구하는 <b>비슷한 작업을 묶어서 배치</b>로 만듦 → 적당한 규모가 되면 카드 덱이나 카드 리더기에 적재해 자기 테이프로 저장 → <b>저장한 자기 테이프를 위성 컴퓨터에서 떼어서 주 컴퓨터로 탑재 (오프라인)</b> → 주 컴퓨터에서 프로그램 돌리는 동안 위성 컴퓨터는 또 다른 배치 만듦
  - 출력의 경우, 주 컴퓨터에서 자기 테이프 만들고, 이걸 위성 컴퓨터에 탑재해서 출력
- 이 방법이 성공하기 위해서는 <b>배치가 중요!</b>
- 효율성은 개선했지만, 운영자 (사람) 에 대한 의존도가 높다는 단점이 있음

## 일괄처리 시스템

- 초기 일괄처리 시스템의 루틴을 자동화하는 데 초점
- 사람 개입이 없어지려면 자기 테이프 수동으로 옮겨야 하는 과정이 없어야 함
  1. 문제 : 주 컴퓨터가 위성 컴퓨터 역할까지 처리하면 부담이 큼
     1. 해결을 위해서는 입출력 장치와 cpu 가 간섭 없이 동작할 수 잇어야 함
     2. 입출력 장치는 입출력 끝내고 cpu 한테 알리고<b>(인터럽트)</b>, cpu 는 다음 입출력을 입출력 장치한테 지시하면 됨
     3. <b>이 정보를 메모리 내의 버퍼에 저장함</b>
- 세 가지가 중요
  ![운영체제 1주차 이미지 1]({{ '/series/operating-systems/assets/os-01-001.png' | relative_url }})

  - 채널
    - <b>입출력 장치가 cpu 의 간섭 없이 독립적으로 메모리 특정 부분에 데이터 전송할 수 있도록 도와주는 회로</b>
    - <b>채널 덕분에 cpu 와 입출력 장치가 병렬적 수행이 가능하게 됨</b>
    - 명령어, 레지스터, 제어장치로 구성됨
    - cpu 와 채널이 아에 간섭이 없진 않음. cpu 랑 채널 둘 다 버퍼 접근함. 이 때 경쟁이 발생할 수 있음
      - 이건 cycle stilling 으로 해결함(DMA)
  - 버퍼
    - 채널이 입출력을 위해 사용하는 메모리 상의 약속된 장소이자, cpu 가 입출력 정보를 접근하는 장소
    - 버퍼 덕분에 채널과 cpu 가 어긋나지 않게 자료 공유하면서도 간섭 없이 각자의 작업 처리 가능
    - 연산을 cpu 가 하는 동안에 입출력 장치가 읽거나 쓰는 것이 가능하게 되어,<b> 입출력 대기 시간을 없애줌</b>
  - 인터럽트
    - 채널과 cpu 는 어느 정도 간섭이 잇음
      - 채널의 입출력은 cpu 에 의해 이뤄져야 하고, cpu 는 입출력 명령 이후에 작업 하다가, 채널의 입출력이 끝났으면 cpu 가 통보 받아야 버퍼 통해 자료 공유 할 수 있음
      - 이걸 위해 만들어진 게 인터럽트임
    - cpu 가 인터럽트 받으면 해당 인터럽트에 대한 처리를 해야함
    - 이게 입출력 장치마다 달라서, 메모리 특정 부분에 올려놓기로 함. 이게 ISR (interupt service routine) 임
    - 인터럽트에는 입출력의 완료, 예외 동작에 대한 동작 처리도 있음
    - cf ) 트랩
      - 소프트웨어 오류 시에 발생하는 소프트웨어 인터럽트
      - 커널 공간과 사용자 공간을 나누어 접근할 수 있는 권한 접근에 사용
- 이러한 변화는 새로운 이슈를 파생 시킴
  - <b>모니터</b>의 태동
    - 일괄처리 시스템을 사용하기 위해서는 메모리에 상주하는 프로그램이 필요했음
      - 대표적으로 ISR
      - 이 외에도 기본적으로 적재기, job sequencer, 제어 카드 번역기 등등이 필요했음 (자세히는 몰라도 돼)
      - 이것들은 컴퓨터 시작될 때부터 메모리에 탑재돼서 영구적으로 상주해야함
    - <b>이런 ‘처음부터 메모리에 상주해야 하는 프로그램을 통칭해서 상주 모니터 라고 함’</b>
      - 이 모니터가 운영체제의 원조임
      - 커널의 시조임!
  - 보호 이슈
    - 메모리에는 모니터도 있지만, 버퍼도 있고, 프로그램도 있음
    - 프로그램이 수행되는 도중에 모니터의 영역을 침범하는 경우가 빈번해짐
    - 이 때문에 상주 모니터의 보호가 필요해짐
    - 특히 입출력 과정에서 이러한 문제가 많이 발생함
    - 때문에 <b>모든 프로그램은 모니터가 제공하는 입출력 함수를 호출해서 입출력하도록 함</b>
    - <b>이게 바로 시스템 콜의 태동! (커널 내의 함수를 응용 프로그램이 사용하는 것)</b>
    - 미리 작성된 테이블에 기록된 메모리 접근 허용치 == 사용자 프로그램이 접근할 수 있는 메모리 영역을 참조해서 각 연산 수행 시에 메모리 접근 범위를 넘어가는지 체크하여 제한함
- 장점
  - 컴퓨터 효율성을 높임
  - 프로그램이 실행되면 자원을 독점하기 때문에 처리 속도 빠름
  - 수치 계산, 대용량 처리 등의 cpu-bound 작업 (입출력 적고, 계산 많은 작업) 을 쉬지 않고 수행시키기에 적함
- 단점
  - 프로그램과 사용자의 대화가 많은 프로그램을 수행시키기에는 부적합
    - e.g. 편집기
  - 한 작업, 한 작업을 <b>순차적으로 처리</b>하기 때문
    - 입출력에 소모하는 시간이 그대로 다음 작업에 영향을 미치게 됨
    - 이 문제를 해결하기 위해 <b>여러 프로그램을 동시에 처리</b>하는 다중 프로그래밍이 등장

## 다중 프로그래밍 (멀티 프로그래밍)

- 한 시점에 여러 프로그램이 메모리에 탑재됨
- 이렇게 함으로써 일괄 처리 시스템의 단점 해결
  - 한 프로그램이 모두 끝난 후에 다음 프로그램이 처리되는 순차적 처리 방식 해결
- <b>‘번갈아가며’ (병렬로) 처리하는 것으로 문제를 해결함!</b>
  - 한 프로그램에 입출력이 발생하면 인터럽트 걸어두고, 다른 프로그램을 수행하는 것
- 수행중이던 프로그램에서 입출력 발생할 때마다 다음에 실행될 프로그램 선정해야함
  - <b>이게 스케줄링임!</b>
  - 정책이 필요함 → 스케줄링 알고리즘이 필요함
- <b><span color="blue">수행 중이 프로그램에서 입출력이 발생할 때만 cpu 가 수행하는 프로그램이 전환됨(스케줄링이 발생)</span></b>
  - 수행 중인 프로그램에서 무한루프가 발생한다면, 프로그램이 전환되지 않음
  - <b><span color="blue">즉, 프로그램 간의 간섭이 발생할 수 있다.</span></b>
- <b>대부분의 프로그램은 cpu 사용 시간보다 입출력에 소요되는 시간이 더 많다!</b>
  - 다중 프로그래밍 방식이 효율적이라는 걸 뒷받침해주는 증거!
- 장점
  - 효율적 (입출력 시간 == cpu 가 노는 시간에 다른 일 처리할 수 있도록 해줌)
- 단점
  - 한 프로그램에서는 여러 번 출력이 발생할 수 있고, 이 때마다 다른 프로그램이 실행됨
  - 그래서 여러 프로그램이 산발적으로 출력을 요청함
  - 그럼 출력이 뒤죽박죽 될 수 있음
    - 이런 문제를 해결한 게 바로 spooling (simultaneous peripherial operations on-line)
      - 성격 상 원래는 순차적으로 동작해야 하는 장치를 동시에 수행되는 프로그램들이 사용할 수 있게 해주는 것
        - e.g. 산발적인 프린트 출력을 모아서 프로세스가 끝난 후에 출력하는 것
      - 디스크를 활용해서 순차적 처리 장치에 동시에 접근할 수 있도록 함
        - 디스크는 속도가 빨라서 랜덤하게 접근이 가능함
        - 각 프로그램에서 산발적으로 발생하는 출력 자료를 디스크에 모아둠으로써 동시에 접근하는 효과를 냄
          - 각 프로그램은 출력 데이터를 쌓는데, 그걸 바로 프린트로 출력하는 게 아니라 모아두는 것!
          - 각 프로그램은 출력을 한 걸로 생각하고, 우리는 출력이 엉키지 않게 모아두었다 안정적으로 처리할 수 있다.
          - 디스크는 속도가 빠르기 때문에 가능한 일!
    - 이와 유사한 해결 방법으로 buffering 도 있음
      - 입출력 시의 cpu 와 입출력 장치의 속도 차이를 해소하기 위해,하드 디스크나 메모리 버퍼 영역을 이용해 자료를 잠시 저장하는 것
        - 메모리 버퍼를 이용해 i/o 와 cpu 의 속도 차를 해소해 독립된 동작을 허용하는 것
  - job scheduling
    - 최적의 스케줄링 방식 필요
  - 메모리 경영
    - 한정된 메모리에 여러 작업을 올려야 하기 때문에 ‘어떤 작업을 올릴 것인가?’ 에 대한 알고리즘 필요

## n 개의 프로그램이 실행되는 시간을 t1, t2 t3 …이라고 할 때

- 일괄처리 시스템은 다 더해야 함 (t1 + t2 + t3 … )
- 다중처리 시스템은 대략 Max(t1, t2, t3 … )
  - 근데 이건 ‘max > 나머지 총합’ 인 이상적인 상황에서만 성립할듯?

## 시분할 시스템

- 다중 프로그래밍은 입출력이 일어날 때에만 프로그램 전환이 되기 때문에 (스케줄링이 일어나기 때문에),
  - 수행 중인 프로그램의 입출력 빈도와, 입출력에 소요되는 시간이 다른 프로그램에 영향을 주게 됨
  - 한 프로그램의 수행 시간이 다른 프로그램의 수행시간에도 영향을 줌
    ![운영체제 1주차 이미지 2]({{ '/series/operating-systems/assets/os-01-002.png' | relative_url }})

    - a 시점 이후 b 시점까지의 대기 시간이 (입출력 완료되었는데도, 현재 cpu 에서 수행중인 프로그램에서 입출력이 발생하지 않아서 대기하는 시간) 다른 프로그램의 영향을 받는다.
- 이러한 단점을 보완한 게 시분할 시스템!
  - 타임 슬라이스를 도입!
  - 입출력 때에도 스케줄링 && 타임 슬라이스 도래해도 스케줄링!
    - 이러면 위 사진에서 a \~ b 까지 프로그램이 대기하지 않아도 됨! 타임 슬라이스 도래할 때마다 입출력 완료되었는지 체크해서, 완료되었다면 전환, 완료되지 않았다면 수행하던 프로그램 그대로 수행하기 때문에, a \~ b 대기 시간이 짧아질 수 있음!
  - 타임 슬라이스는 ‘타이머 인터럽트’ 를 통해 구현함
    - 보통 10ms
- 시분할 시스템을 통해 프로그램 간의 간섭이 없어지고(다른 프로그램의 수행 시간에 영향을 받지 않게 됨), 사용자와 프로그램의 대화성이 증진됨
- 여러 사용자가 동시에 한 시스템에 연결해 사용하는 게 가능해짐!
  - 운영체제가 각 사용자 사이를 빠르게 전환하며 작업을 처리하여 사용자가 컴퓨터를 독점하고 있는 것처럼 만들어줌!
  - 실제로는 전환하는 게 아니라, 빠르게 전환하는 것!
- <b>cpu 의 효율성 증진 && 사용자에게 빠른 응답시간 추구(편의성 증진!)</b>
  - 대화형 입출력에도 적합!
- <b>가상메모리도 필요해짐! (나중에 자세히 다룸)</b>
  - 여러 프로그램이 메모리에 적재되며, 메모리가 부족해짐
  - 이를 해결하기 위해 도입된 장치
  - 실제 한정된 메모리보다 더 많은 메모리를 사용할 수 있게 함

## 실시간 시스템

- 프로그램 동작에 <b>실시간성(엄격한 deadline)</b> 이 요구되는 분야에서 사용하기 위한 목적으로 고안됨
  - 공장 생산, 실험 제어, 동영상 처리 등
- 경성 실시간성 vs 연성 실시간성
  - 경성 실시간성 (hard real-time)
    - 데드라인 위반 시 <b>재앙적인 사건이 발생하는 경우!</b>
      - e.g. 원자력 발전소
    - 데드라인 100 퍼 만족이 증명되어야 함
      - 수학적 증명, 직접 시연 등의 방식
    - 경량 os 사용 (크면 제어가 힘들어)
  - 연성 실시간성(soft real-time)
    - 데드라인 위반해도 재앙은 발생 안하는 경우
      - e.g. 동영상 플레이어
    - 데드라인 만족이 확률적으로 증명됨
      - 우선 순위 제어로 해결하려고 함
