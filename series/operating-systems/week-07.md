  - 현 프로세스로부터 강제로 cpu 회수하는 거 (spot 인스턴스 같네)

## cpu burst time

- cpu 할당 후 입출력 요구시까지의 시간
  - ‘몰렷다’ 의 뜻 보다는 cpu 할당 후 입출력 요구까지 시간을 말함
- 히스토그램은 평균적으로 hyperexponential 분포를 보임

![운영체제 7주차 이미지 1]({{ '/series/operating-systems/assets/os-07-001.png' | relative_url }})

- 꺾인 지점 (엘보우 처럼 보임) 이 있음 - 8 부분
  - 버스트 타임이 긴 게 많으면 최고점이 낮아지고, 완만해짐 (엘보우가 오른쪽으로 가고, 피크가 낮아짐)
  - 엘보우가 오른쪽으로 갈 수록 버스트 타임이 긴 프로세스가 많아지는 것
- 이걸로 프로세스 성격 파악이 가능함!
  - 피크가 높고, 엘보우가 왼쪽이면
    - 대화성이 높은 거 (i/o bound)
  - 피크가 낮고, 엘보우가 오른쪽이면
    - cpu 를 많이 사용하는 == 계산을 많이하는 프로세스 (cpu bound)

## fcfs

- 프로세스 도착 순으로 cpu 배정 (실행 중 입출력 요구하면 다음 준비 상태에서 fcfs 적용)
- 장기 스케줄러에서 사용 가능 (batch 작업 등)
- 시분할 시스템에서 타임 슬라이스 적용하지 않는 프로세스에 대해 사용 용이함 (백그라운드 또는 실시간 프로세스 등)

<b>평균 대기시간은 요청한 시점\~수행된 시점!</b>

처음 요청했을 때부터 수행 시작되기까지 얼마나 기다렸는가? 임!

<b>평균 반환시간은 요청한 시점 \~ 반환된 시점(끝난 시점)</b>

처음 요청했을 때부터 요청끝날 때까지 얼마나 걸렸는가? 임!

- 예제 1의 경우 (모두 같은 시점에 요청햇다고 가정)
  - 평균반환시간은 요청이 끝난 시간으로 계산함
    - (24 + 27 + 30)  / 3 = 27
  - 평균대기시간은 대기시간의 합
    - (0 + 24 + 27) / = 17
- 예제 2의 경우 (모두 같은 시점에 요청햇다고 가정)
  - 평균반환시간은 요청이 끝난 시간으로 계산함
    - (3 + 6 + 30) / 3 = 13
  - 평균대기시간은 대기시간의 합
    - (6 + 0 + 3) / 3 = 3
      - 작업 1부터 계산해서 그럼

### 여기서 알  수 있는 건 긴 작업이 뒤에 있으면 더 효율적이라는 것!

- 긴 작업이 앞에서 누적시키는 반환시간이랑 대기시간이 없기 때문!
- <b>그래서 이건 fcfs 의 특징이다! (긴 작업이 앞에 오면 성능이 떨어진다는 것!)</b>
  - 이걸 호위효과(convoy effect) 라고 한다.

### 최단 작업 우선 (shortest job first)

- 대기하는 작업 중 cpu 버스트 타임이 가장 작은 작업에 cpu 할당하는 기법
- <b>평균 대기시간에 있어서 최적 알고리즘</b>
- 도착 시점(언제 cpu 에 작업을 요청했는가?) 을 고려하였을 경우
  - <b>일단 도착한 프로세스를 수행하고, 수행 후에 대기하는 애들 중에 제일 짧은 거 가져옴!</b>
  - 대기하는 애들 중에 버스트 타임이 같다면 먼저 온 거 부터 처리!
    ![운영체제 7주차 이미지 3]({{ '/series/operating-systems/assets/os-07-003.png' | relative_url }})

    평균대기시간이랑 평균반환시간 계산은 위에 정의 참고!

    이 차트를 ‘간트차트’ 라고 함
    
- 문제점
  - cpu 요구 시간 (burst time) 을 미리 알 수가 없음!
    - 그래서 예측을 사용함!
    - 장기 스케줄링의 경우 작업 시간 예측치를 제출하게 함
    - 단기 스케줄링의 경우에서는 예측치 제출받는 것도 힘들어서 이 방식 사용하기가 힘듦
- 해결 방안
  <ul markdown="1">
  <li markdown="1">
  지수평균 : 차기 버스트타임은 일반적으로 이전 버스트타임의 지수적 평균으로 간주
  </li>
  <li markdown="1">
  재귀식을 사용하는 이유는 모든 버스트 타임을 기록하지 않게 하기 위함! 

  - <b>바로 직전 예측값 τ(n) 과 최근 측정값 t(n)만 있으면 돼</b>
  - <b>저장은 pcb 에 함!</b>
  </li>
  <li markdown="1">
  τ(n+1) = α × t(n) + (1 - α) × τ(n)

  - τ(n+1): 다음 CPU burst time 예측값
  - t(n): 직전 실제 CPU burst time
  - α: 0\~1 사이의 상수 (최근 기록을 얼마나 신뢰할지 조절하는 가중치)
  </li>
  <li markdown="1">
  이 식을 계속 풀면 실측치로만 구현된 식이 나옴

  - 최근으로 올 수록  많이 반영하게 됨! (1-a) 에 붙는 승 수가 작아짐

  ```kotlin
  τ(n+1) = α × t(n)
  + (1 - α) × α × t(n-1)
  + (1 - α)² × α × t(n-2)
  + ...
  + (1 - α)^n × α × t(0)
  ```

  </li>
  </ul>

### sjf 는 선점 스케줄링에도 적용 가능!

### 우선 순위 스케줄링

- 각 프로세스의 우선순위가 정해지면, 우선순위가 제일 높은 프로세스에게 cpu 할당하고, 우선순위가 같다면 fcfs 적용하는 방법
- sjf 도 일반적으로 우선순위 스케줄링 알고리즘의 특수한 한 형태
  - 우선순위가 다음 cpu 버스트 시간의 예상의 역수 (짧을 수록 우선순위가 위로 감!)
- 우선순위 설정
  - 정해진 방법은 없음!
  - 내부적 우선순위 고려 : 제한 시간, 메모리 요구량, 사용하는 파일 수 등등
  - 외부적 우선순위 고려 : 사용료, 정책적인 변수 등
  - 입출력 위주 프로세스에게 높은 우선순위, 연산 위주 프로세스에게 낮은 우선순위 주어 대화성 증진
- 문제점
  - 기아 상태 유발 : 우선순위 높은 작업이 계속 들어올 경우 우선순위 낮은 작업은 보장없이 머물게 됨
- 해결책
  - 에이징 : 시스템에 머무는 시간이 증가하면 우선순위를 조금씩 높여줌
    - 아주 낮은 우선 순위 프로세스라도 시간 지나면 점점 높아짐

### 비선점 vs 선점 스케줄링

- 선점 스케줄링
  - 타임슬라이스 소진 \|\| 인터럽트 호출 \|\| 시스템 호출 종료 시 현 프로세스보다 우선순위 높은 프로세스 할당

### 선점과 동적 우선순위

- 선점 : 현 프로세스로부터 cpu 회수해 다른 프로세스에게 할당
  - e.g. 타임 슬라이스 소진
- 동적 우선순위와 선점
  - 프로세스 실행 중, 시스템 성능, 프로세스 특성 등을 고려해 우선순위 재조정 → 결과적으로 스케줄링에 의해 선점 발생
- <b>전체적인 시스템 성능의 향상 및 프로세스 속성 고려해 커널의 여러 곳에서 우선 순위 조정하는 원칙과 기법이 필요</b>

### 선점 - 라운드 로빈 스케줄링

- 준비 큐를 원형 큐로 간주. 순환식으로 각 프로세스에게 작은 단위 (time quantum) 의 시간량 즉, 타임퀀텀 만큼씩 cpu 할당
  - 여기서 타임퀀텀 == 타임 슬라이스 라고 생각해도 된다
  - 실행상태의 프로세스가 타임퀀텀이 지나면 선점됨
  - 새로운 프로세스 부가될 때는 큐의 맨 뒤에 덧붙여짐
- 이론 상 n 개의 프로세스가 1/n 의 속도로 동시에 실행되는 셈
  - 문맥교환 시간을 고려하지 않느다면, 각 프로세스는 (n-1) \* q 시간 이내에 타임 슬라이스 받게 됨
    - n : 준비 큐에 있는 프로세스 개수
    - q : 타임퀀텀
- 단점
  - 일반적으로 평균반환시간은 sjf 보다 큼
  - 잦은 문맥교환 오버헤드로 처리율 감소할 수 있다
  - <b>타임퀀텀 크기에 성능이 큰 영향을 많이 받음</b>
    - 타임 퀀텀이 매우 크면 fcfs 랑 동일함 (왜냐면 맨 앞에 잇는 게 다 끝나고 다음 거 넘어갈 테니까)
    - 매우 작으면 문맥 교환이 너무 빈번하게 발생함
- 장점
  - 그러나 모든 프로세스가 공정하게 기회를 얻게 되어 기아상태가 발생하지는 않음
- 타임퀀텀이 증가하면 반환시간이 짧아진다. <b>그러나, 타임퀀텀이 증가한다해서 반드시 평균 반환시간이 개선된는 것은 아니다.</b>
  - 짧은 작업이 긴 작업들보다 순서상 늦게 처리되는 경우가 발생할 수 있음
  - 아래는 타임 퀀텀에 따른 평균 반환 시간이다. 타임퀀텀에 증가에 따라 평균 반환 시간이 항상 줄어들지 않는다. <b><span color="blue">툭 튀는 부분이 생김!(이게 제일 중요함)</span></b>
    ![운영체제 7주차 이미지 5]({{ '/series/operating-systems/assets/os-07-005.png' | relative_url }})
- 대부분의 프로세스들이 한 타임퀀텀 내에 하나의 cpu 버스트를 끝낸다면 평균반환시간은 개선된다
- 참고 ) 평균적으로 80% 정도는 타임 퀀텀보다 cpu 버스트 타임이 짧도록 설정하는 게 좋다. (외울 필요 x)

### 다단계 큐 스케줄링

- 준비 큐 자체를 우선순위의 다단계로 두고, 프로세스를 우선순위에 따라 큐에 넣음
- 항상 가장 높은 우선 순위 큐의 프로세스에 cpu 할당
- 각 큐는 독자적 스케줄링 가능 (fcfs, 라운드 로빈 등)
  - 근데 우선순위가 같으니까 fcfs 사용하는 게 좋을 수도?
- 이게 선점 스케줄링인 이유는
  - 한 타임 후에 우선 순위 높은 큐에 프로세스 추가되면 그게 돌기 때문!

### 다단계 피드백 큐 스케줄링

- 다단계 큐 + 프로세스 우선 순위 변화 적용
- 우선 순위에 따라서 퀀텀(타임 슬라이스) 가 달라질 수 있다.
  - 우선순위가 높으면 많이 주고,
  - 우선 순위가 낮으면 적게 주고
- 타임 슬라이스를 계속 모두 다 소진하면 하위 큐의 뒤로 삽입(우선 순위 낮춤)
  - 하위 큐로 갈 수록 cpu-bound 프로세스
- 가장 하위 큐는 fcfs 로 처리
- 맨 아래 큐에 너무 오래 대기하면 다시 상위 큐로 이동 (기아상태 방지)
- 가장 일반적인 방법이지만 적용하기에 매우 복잡한 판단을 내려야 함
  - 큐의 수
  - 각 큐에 대한 스케줄링 알고리즘
  - 언제 작업을 보다 높은 우선순위 큐로 격상시킬 건가?
  - 언제 작업을 보다 낮은 우선순위 큐로 격하시킬 건가?
  - 처음에 프로세스는 어느 큐에 들어가야 하는가?

### 동적 우선순위와 타임 슬라이스의 가변성

- 우선순위의 동적변화에 따라 타임슬라이스 양도 동적으로 변한다.
- 시분할 시스템에서 타임 슬라이스 양은 프로세스마다 다를 수 있으며, 동일 프로세스 내에서도 타임슬라이스 양은 동적으로 변할 수 있다.
- <b><span color="blue">타임 슬라이스 소진 여부는 클럭 인터럽트가 계산하여 체크한다.</span></b>
  - <b><span color="blue">클럭 인터럽트가 몇 번 들어왓는지 보고, 스케줄링이 언제 이뤄져야 하는지 체크함</span></b>

### 다중처리기 스케줄링 이슈

- 한 시스템 내에 여러 처리기의 사용이 가능하다면, 부하 공유(load sharing) 가 가능
- 그러나 스케줄링 문제는 더 복잡해짐
  - e.g. 어떤 프로세스는 특정 프로세서의 버스를 사용해야 할 수도 있음
- 최상의 해결책에 대해서는 지금도 연구 중임

### 대칭 다중 처리(symmetric multiprocessing, SMP)

![운영체제 7주차 이미지 7]({{ '/series/operating-systems/assets/os-07-007.png' | relative_url }})

- <b><span color="blue">어떤 프로세스를 어떤 cpu 에 할당할지가 이슈 중 하나 (cpu 를 이주하는 경우도 발생)</span></b>
- 각 처리기가 독자적인 스케줄링 수행
- 모든 프로세스는 <b>공동의 준비 큐 혹은 각 처리기의 준비 큐</b>에 존재
  - 먼저 온 cpu 가 공동 큐에서 빼가면 되니까 각각에 존재한다고 생각해도 괜찮음
- 여러 처리기가 동시에 공유 자료에 접근 시 신중한 스케줄링이 필요

### 처리기 친화성 (processor affinity)

- 프로세스가 다른 처리기로 이주하게 되면 <b><span color="red">각 처리기의 캐시 메모리 갱신 필요 → 비용 낭비</span></b>
  - 캐시 옮겨야 하고, 채워지는 동안 시간도 낭비돼
- 처리기 친화성 - 프로세스의 처리기 이주를 제한하고(가급적이면 안 넘기고) 같은 처리기에서 계속 실행시키려 하는 성질
  - 절대 못하게 하진 않음
  - 연성 친화성 - os 가 동일한 처리기에서 프로세스 실행시키기 위한 정책을 갖지만 <b>보장하지는 않음</b>
  - 강성 친화성 - 시스템 콜을 통해 각 프로세스가 실행될 처리기를 명시함 → <b>동일한 프로세스에서의 처리를 보장함</b>
- 시스템의 메인 메모리 구조가 처리기 친화성에 영향을 줄 수 있음
- NUMA(Non-Unifiorm Memory Access, 비균등 메모리 접근)
  - 메모리에 사용자 문맥이 들어잇음
- 특정 cpu 에 친화성을 갖는 프로세스가 존재할 수 있음
  - 해당 cpu 와 같은 보드의 메모리에 배치해 성능 향상

### 부하 균등화 (load balancing)

- SMP 시스템에서는 모든 처리기가 균등한 부하를 갖는 것이 중요함
- push - 부하 높은 cpu 가 부하 낮은 cpu 로 프로세스 이전하는 것
- pull - 부하 낮은 cpu 가 부하 높은 cpu 의 프로세스를 가져오는 것
- 부하 균등화는 처리기 친화성과 이익이 상충되는 개념으로, 절대적 규칙은 존재하지 않음

### 멀티코어 프로세서

- 멀티코어 - 하나의 프로세서 칩 내에 여러 처리기 코어가 내장
  - os 입장에서는 smp 시스템과 동일
- 메모리 멈춤 (memorry stall) - cache miss 등 여러 원인에 의해, 프로세서가 메모리 접근 시 데이터가용 시점까지 대기시간 발생
  - 이 시간 동안 프로세서는 멈춰잇음(대기시간 발생)
  - 이걸 아낄 수 없을까?! → 멀티 스레드 멀티 코어
- 멀티 스레드 멀티 코어
  - 한 코어가 2개 이상의 스레드(하드웨어의 스레드)를 실행하며, 한 스레드가 memory stall 로 멈추면 다른 스레드로 전환해 작업 지속 수행 → <b>코어의 효율성 증대</b>
- os 는 각 하드웨어 스레드를 논리 프로세서로 인식

### 멀티스레딩 방법

- 거친 멀티스레딩
  - <b>스레드가 메모리 스톨 등 긴 지연시간이 발생할 때까지 계속 실행</b>
  - 지연이 발생하면 다른 스레드로 전환
  - 명령어 파이프라인 정리를 위해 교환 비용 증가 (안외워도 됨)
- 세밀한 멀티스레딩
  - <b>명령어 사이클 경계에서 스레드 교환 발생</b>
  - 스레드 교환을 위한 회로 필요, 교환 비용 감소

### 2-레벨 스케줄링

- <b>멀티쓰레드-다중코어 프로세서는 기본적으로 두 레벨의 스케줄링이 필요</b>
  - 레벨 1)  어느 소프트웨어 스레드가 하드웨어 스레드(논리적 프로세서) 에서 실행될지 결정
  - 레벨 2) 각 코어가 어느 하드웨어 스레드를 수행할건지 결정
