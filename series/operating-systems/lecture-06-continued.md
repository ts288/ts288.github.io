## Q. 무엇이 문제인가? = 왜 동기화가 필요한가?

### 공유변수에 간섭이 발생할 수 있음

- 여러 스레드가 하나의 전역변수에 접근하게 된다면 간섭이 발생함
- 문맥교환이 일어나는 시점에 의도하지 않은 동작이 일어날 수 있음
  - 지금 접근하면 안되는 스레드가 먼저 전역변수에 접근한다던가 등
  - 이 경우는, 문맥 교환이 이뤄지는 시점에 더 높은 우선순위를 가진 프로세스가 깨어나는 경우임
    - 즉, 문맥 교환을 하기 전까지는 제일 높은 우선순위를 가지고 있던 프로세스가, 문맥교환이 이뤄지는 동안에 더 높은 우선순위를 가진 프로세스가 깨어나서 변경될 수 있다는 것
  - os 는 항상 제일 높은 우선순위의 프로세스에게 자원을 할당하므로, 충분히 가능한 일임

### 그래서 원소적 (Atomic) 실행이 필요함

- 공유변수를 통해 상호작용하는 프로세스 혹은 쓰레드 간에 문맥교환이 언제 일어나도 간섭이 없는 실행이 보장되게 하는 것
- 공유변수를 사용하는 코드 영역에 <b><span color="red">임계구역</span></b>을 설정
- 한 스레드가 먼저 임계구역에 접근한 상태에서 문맥교환이 발생해 다른 스레드에게 선점되더라도, 선점한 스레드가 해당 코드 영역(임계구역) 에 진입하는 것을 불허하고 대기하도록 함

### Q. 그러면 A 가 lock 을 건 상태에서 B 로 문맥교환이 일어났다고 할 때, B 는 자원을 사용하지 못하는데 이 상태에서는 어떻게 처리하나여?

- lock 종류에 따라 다릅니다.
- busy-waiting 같은 경우에는 while 을 돌면서 Lock 이 풀리기를 기다려요.
  - 그래서 cpu 낭비가 발생합니다.
  - 멀티 코어 환경에서만 유효한 방식입니다. (단일 코어인 시스템에서는 while 도는 동안 lock 이 안 풀려요 ㅠ 왜냐면 cpu 는 while 도는 애한테만 할당되어 있으니까)
- 아니면 바로 프로세스를 sleep 으로 돌리고 cpu 반환하는 lock 도 있어요

### Mutex

- 임계 구역을 설정할 때 사용
- <code>pthread_mutex_t lock;</code> 처럼 lock 을 선언
- <code>pthread_mutex_init(&lock, NULL);</code> 처럼 init 하고
- <code>pthread_mutex_lock(&lock)</code>, <code>pthread_mutex_unlock(&lock)</code> 처럼 사용함
  - 이 사이에 있는 코드를 ‘임계 구역’ 내부 코드라고 함
- pthread\_cond\_wait
  - pthread\_mutex\_lock 이 된 상태에서, condition 을 만족할 때까지 잠시 lock 을 풀고 대기하는 것
  - mutex\_lock 을 걸어도, 다른 스레드가 임계 구역에 접근할 수 있어야 하는 상황이 있기 때문
    - e.g. consumer 가 lock 걸었는데, consume 할 data 가 없는 경우. 이 경우에는 lock 을 잠시 풀고 producer 가 동작해 buffer 에 data 를 채울 때까지 잠시 대기해야 함

  ### Q. 그럼 condition 을 먼저 체크하고 lock 을 걸면 안되나요?

  - 안된다! 왜냐면 실행 순서를 보장할 수 없기 때문
  - 동시에 여러 스레드가 돌기 때문에, condition 을 체크할 때에는 조건이 false 였다가, 이후에 바로 true 가 될 수 있음
    - 그러면 lock 을 걸어야 하는데 lock 안 걸게 되는 상황이 발생함
  - 그래서 일단 lock 을 걸어서 잠그고, 이후에 조건을 체크해야 정확한 실행을 보장할 수 있음!

  ### 참고로 순서는 이렇게 됨

  - 스레드 a 가 lock 을 걸고, cond\_wait 으로 대기함
  - 스레드 b 가 lock 걸고 로직 수행 이후에 cond\_siganl 을 보냄
  - 스레드 b 가 unlock 함
  - 스레드 a 가 cond\_wait 에서 벗어나서 다시 lock 을 획득함
  - <b>중요 ) 현재 lock 을 건 스레드가 다른 스레드에게 signal 을 보내고 unlock 한다고 해서, signal 을 받은 스레드가 바로 lock 을 거는 건 아님! 즉, signal 은 다음에 실행할 스레드의 순서를 보장하는 것이 아님</b>
    - signal 을 받은 스레드가 바로 lock 을 잡게 구현할 수는 있음! priority 를 설정하면 됨. 일부 라이브러리는 그렇게 구현해두기도 함
    - 다만, pthread 는 가볍게 동작하는 것을 목표로 하기 때문에 이런 기능을 추가해두지 않은 것

## 프로세스 시스템

- 프로세스 시스템은 두 가지 요소, 즉 프로세스의 집합과 이들의 선행 제약으로 정의됨
  - 프로세스의 집합은 프로세스들의 집합
  - 선행 제약은 프로세스 집합의 프로세스들이 부분 순서 성질을 갖는다는 것
    - 즉, 어느 프로세스가 먼저 돌고, 그 다음에 어느 프로세스가 돌지 정해져 있다는 것
    - 다만, 일부에 대해서만 순서를 갖기 때문에 부분 순서라고 함
    - 부분 순서를 가지는 프로세스들에 대해서는 이행성을 가진다고 할 수 있음
- 프로세스 집합의 일부가 선행제약을 가지기 때문에, 선행 제약 관계가 없는 프로세스도 있음
  - 선행제약 관계가 없는 두 프로세스는 독립적이라고 함
- 온전한 프로세스 시스템은 선행 제약 관계가 있다면 비순환적이어야 함
  - 선행 그래프는 프로세스 간 선행제약 관계를 directed 그래프로 표현한 것
  - 정상적인 프로세스 시스템의 선행 그래프는 비순환적

### s/w 적 구현

- lock 을 사용하는 방식 (잘못된 구현!)
  - enter 시점에 lock 을 true, exit 시점에 lock 을 false 로 두고, lock 이 true 이면 진입 못하게 함
  - 근데 이건 <b>잘못된 구현임</b>
    - 시분할 시스템이기 때문에 lock 을 true 로 만들기 전에 다른 프로세스가 enter 할 수 있기 때문임
    - 이 경우에 임계 구역에 두 프로세스가 들어갈 수 잇음. 즉, <b>상호 배제가 보장되지 않음</b>

    1. ticket lock
       1. 이건 프로세스가 스스로 자기 번호를 비교하는 방식임. 자기 번호에 해당하면 자기가 실행됨
       2. 비유하자면, bakery 는 대표가 ‘너 나와’ 하는 거고, ticket lock 은 프로세스가 ‘어 이번엔 나야’ 하면서 나가는 것
       3. 그래서 번호를 비교하는 건 o(1) 임. 자기 번호만 비교하면 되니까
          1. 근데 모든 프로세스가 자기 번호인지 체크해야 하므로, 대기하는 시간이 발생함. 이건 모든 프로세스를  돌아야 하니까 o(n)
    2. MCS Lock
       1. 이건 queue 기반 단방향 리스트를 사용하는 거
       2. FIFO 처럼 늦게 들어온 걸 맨 뒤에 추가하고, 맨 앞에 잇는 거부터 실행함
       3. 이 경우에는 number 가 같은 경우를 고려하지 않아도 됨
       4. 단점은
          1. queue 를 저장하기 위한 추가적인 메모리 공간을 사용하게 된다는 것 o(n)
          2. lock 을 해제할 때 다음 노드로 lock 을 넘겨야 하는데, 내가 tail 일 경우에는 포인터를 null 로 바꾸는 과정이 필요함. 이 과정에서 복잡성이 발생
             
             <b>Q. 그러면 dummy node 를 리스트 맨 뒤에 항상 붙여두면 안되나요?</b>

             - 근데 이러면 pointer 가 dummy node 가리킬 때, 새로운 노드 추가하면 또 복잡성이 발생함

### test-and-set

- 가장 중요한 원리는 cpu 명령어 하나가 문맥교환 없이 원소적으로 수행된다는 것
- 각 스레드는 임계구역에 진입하기 전에 lock 값을 체크함
  - test-and-set 은 임계 구역에 진입할 때 현재 lock 값을 temp 에 저장하고, lock 을 1 로 설정함
  - <b>아래 그림에서의 과정이 하나의 cpu 명령어로 되어 잇는 거임</b>
    ![운영체제 6강(이어서) 이미지 6]({{ '/series/operating-systems/assets/os-06-006.png' | relative_url }})
  - 이 과정에서 원소적 실행이 필요 (시분할 시스템에서는 공유 변수에 여러 프로세스가 접근하는 것을 방지해야 하기 때문)
  - 그래서 현재 lock 값을 temp 에 저장하고, lock 을 1 로 설정하는 과정을 하나의 cpu 명령어로 수행
  - lock 이 1 인 경우에는 임계구역에 진입하지 못하고 대기해야 함
- 임계 구역을 빠져나올 때 lock 을 0 으로 리셋

- cf ) busy waiting 이 항상 나쁜 건 아님.
  - spinlock

    - 문맥 교환의 오버헤드 피할 수 잇어서 os 커널에서 활용

## semaphore

- 진입 불가능 시에는 대기 상태로 전환
- 임계 구역을 떠나는 프로세스가 대기 프로세스를 준비 상태로 깨워줌 (block & wakeup)
  - cf ) busy waiting 에서는 반복문 돌면서 대기해야 했는데, 얘는 운영체제가 알아서 깨워주는 거
- 세마포어는 일종의 객체
  - 내부에 정수값(value) 이랑 대기 큐 들어잇음
  - init, wait, signal 의 멤버 함수를 가지고 있음
  - S.value 는 자원 활용 현황
    - 양수이면 남아있는 자원 수를 나타냄
    - 음수이면 부족하여 대기하는 프로세스 수를 나타냄

  ![운영체제 6강(이어서) 이미지 10]({{ '/series/operating-systems/assets/os-06-010.png' | relative_url }})

  - n 값을 value 에 넣음. 이는 사용 가능한 자원이 n 개 있음을 나타냄

  ![운영체제 6강(이어서) 이미지 11]({{ '/series/operating-systems/assets/os-06-011.png' | relative_url }})

  - wait 이 호출되면 <b>무조건 자원 하나를 뺌</b>
    - 어차피 사용해야 하기 때문
  - 뺀 상태에서 value(자원) 가 음수라면 대기함
    - 여기서 사용하는 block() 은 운영체제가 제공하는 함수

  ![운영체제 6강(이어서) 이미지 12]({{ '/series/operating-systems/assets/os-06-012.png' | relative_url }})

  - signal 이 호출되면 무조건 value(자원) 하나 더함
    - 어차피 반납되기 때문
  - value 에 1을 더햇는데도 음수이다 → 이는 하나 이상의 프로세스가 자원 사용하려고 대기하고 잇엇던 것을 의미함 ⇒ list 에서 프로세스 하나 꺼내서 깨움
    - 여기서 사용하는 wakeup() 은 운영체제가 제공하는 함수

  ### 세마포어의 wait 과 signal 은 atomic 하게 이뤄져야 함.

  - 이를 위해 인터럽트를 블락함
  - 그런데 이 방식은 성능 저하를 유발함
  - 그래서 value 를 대상으로 compare\_and\_swap 등의 하드웨어적 mutex 를 사용함

  ![운영체제 6강(이어서) 이미지 13]({{ '/series/operating-systems/assets/os-06-013.png' | relative_url }})

  ### value 의 초기값 설정에 따라 다양한 목적으로 세마포어 활용 가능

  - n >1 : 자원이 여러 개 있는 경우. 자원과 대기자 동시 관리 가능
    - 양수이면 자원, 음수이면 대기자
  - n == 1 : 공유 변수에 대해 mutex 구현
    - 임계구역을 두고 다른 스레드가 경쟁하는 상황이라고 생각하면 됨
    - 단 하나의 스레드만 임계구역에 진입하고 나머지는 대기
  - n == 0 : 한 스레드가 자원 사용하면 다른 스레드는 무조건 대기해야함
    - 이를 통해 다중 스레드 상황에서 실행 순서를 보장할 수 잇음
    - 이걸 busy waiting 으로 구현하면 타임슬라이스 낭비가 발생함

## readers-writers problem

- 여러 프로세스가 공유버퍼를 대상으로 읽기 쓰기 할 경우, 쓰기 프로세스는 대기해야하나, <b>읽기 전용 프로세스들마저 대기하는 것은 성능 저하를 야기함</b>
- 쓰기 연산을 하는 프로세스는 모든 프로세스에 배타적 락을 걸고, 읽기 연산만 하는 프로세스끼리는 lock 을 공유하면 됨
  - 단, lock 을 얻기 위해 reader 모드인지 writer 모드인지 밝혀야함
  - 그리고 기아 상태 발생 가능함
    - reader 프로세스가 공유 lock 을 차지하면 writer 프로세스가 기아상태에 빠질 수 잇음
    - 이를 해결하기 위해 lock 의 대기 큐를 분리하는 방법 등이 있음

### 우선순위 역전 문제

- 높은 우선순위 프로세스가 현재 낮은 우선순위 프로세스가 자원 사용을 마칠 때까지 기다려야 하는 경우가 발생함
  - 우선순위가 낮은 프로세스가 자원을 선점하면서, 높은 우선순위의 프로세스가 실행되지 못하는 경우에는, 중간 우선순위를 가진 프로세스가 높은 우선순위 프로세스의 수행을 지연시킬 수 있음
    ![운영체제 6강(이어서) 이미지 14]({{ '/series/operating-systems/assets/os-06-014.png' | relative_url }})
  - 이 문제는 우선순위 상속 프로토콜을 사용해서 해결할 수 있음
    - 이름 그대로 우선순위를 상속시키는 것
    - 한 프로세스가 자원을 점유하면, 해당 자원을 사용하고자 하는 모든 프로세스의 우선순위 중 가장 높은 것을 골라 자원을 점유한 프로세스에게 상속하는 것
