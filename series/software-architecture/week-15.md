# 소프트웨어 아키텍처 15주차

## Event Based Implicit Invocation 아키텍처 스타일

- 이 방식에서는 메시지 큐가 없는 구조임
- 메시지 소스하고, 메시지 리스너만 존재함. 그리고 리스너가 인프라에 등록됨
- 주로 이클립스, 비주얼 스튜디오에서 사용함
- 아니면 디버깅쪽이나, 시장 마켓, 이커머스 시스템에서 사용함
- 단점으로는, 소스하고 리스너 사이에 타이트한 바인딩이 되어잇는 게 단점임
  - 메시지 큐 사용하면 루즈하게 연결이 가능한데, 이건 타이트함
  - 이 방식은 소스랑 리스너 사이의 관계가 명확할 때 사용
    - e.g. 항공모함, 비행기, JVM 에서 버튼 눌렀을 때 내부 동작
- DDS (Data Distribution Service)
  - Real Time Pub/Sub (RTPS)
    - 메시지 처리할 때 데드라인을 지킬 수 있다는 것
  - 이 위에 DDS 미들웨어가 있다
  - 그 위에는 응용 프로그램이 올라감
    - 응용 프로그램 사이의 pub/sub 을 객체 지향으로 지원하면서 RTPS 사용할 수 있게 하는 것
  - 미들웨어가 버퍼를 가지고 있지 않고, 브로드 캐스팅을 하면 가져와서 처리하는 구조임
  - 각각의 api 는 DDS Library 를 따라야 함

## Buffered Message Based Broker 아키텍처 스타일

- 큐를 사용하면서 메시지를 선언해야하고, 브로커인지, 큐인지 나누어짐
  - 브로커는 메시지의 변환 부분을 강조한 것
- 메시지라는 이벤트를 발행하는 소스와, 이 메시지를 구독하는 리스너가 있음
- 이 둘을 연결 시켜서 네트워크를 만드는 것
- 브로커는 발행자와 소비자가 서로 다른 메시지 포맷을 가지고 있는 경우에 사용함
  - e.g. xml 로 발행하는데 json 으로 받아야 하는 경우
- 메시지 브로커 내에서는 아래 동작을 함(네트워크랑 똑같음)
  1. 파싱하고
  2. 리스너가 이해할 수 있는 형태로 변환하고
  3. 보낼 곳을 파악해서 라우팅 함
- e.g. Hadoop
  - 빅데이터 처리를 위해 나옴
  - 하나의 덩어리를  2.0 이 되면서 둘로 나눠서 YARN (리소스 매니저 - 쿠버네티스랑 비슷) 을 만들고, 그 위에 배치 시퀀셜 처리하는 MR 을 끼울 수 있는 구조임
  - YARN 에 있는 storm 이라는 구조가 브로커를 연결해서 만드는 구조임
    - storm 은 spout 와 bolt 로 구성됨
    - spout 가 데이터 받고 bolt 가 연결 담당
- 메시지 발행자, 소비자, 브로커(아님 큐) 로 구성되어 있음
- 메시지 큐가 죽지 않게 두 개 구현하면 그게 분산 시스템임
- 모든 도메인에 해당 아키텍처가 사용됨
  - 특히 iot 나 msa

## Client-Server 아키텍처 스타일

- 클라이언트가 메시지 던지면 서버가 기다리다가 받아서 서비스 제공
- 주고 받는 메시지를 Request Reply 를 하게 되면 동기화가 되는 거고, 이벤트 기반은 이걸 끊는 것
- e.g. DB Server
  - 인터넷을 사용하면서부터 클라이언트 - 서버 구조가 나타남

## Broker 아키텍처

- 서로 독립적으로 작동하는 이질적인 시스템을 연결하려고 할 때 사용하는 구조
- 기본적으로 클라이언트의 리퀘스트가 브로커로 들어가고, 브로커가 요청을 보고 서버에 요청 전달함
- Q. 메시징 큐랑 똑같네?
  - 맞음
  - 메시지 전달의 측면에서 메시징 큐도 브로커라고 할 수 있음
  - 다만, 브로커는 앞서 설명했듯이 파싱 후 변환 같은 다양한 기능을 추가로 사용할 수 있는 것
- 스프링은 CORBA 를 보고 만들어짐
  - Injection 같은 게 예시임
- RPC
  - Lazy Binding 이라고도 함
  - 필요할 때 서버기 뜨게할 수 있음
    - 평상시에 사용하지 않는 서버가 죽어있다가 요청 들어올 때 바인딩 되면서 살아나게 하는 게 가능

## Load Balancer 아키텍처

- 서버가 여러 개 있을 때 클라이언트가 여러 개 접속하면, 부하를 고르게 분산해야함
- 그 때 사용하는 게 로드밸런서(디스패처)
- 여기서 나타나는 문제는 나누는 알고리즘임. 한 7개 정도가 있음
  - 서버의 부하나 리소스를 모니터링 하면서 분산을 하면? → 실제로는 안됨
    - 왜냐면 자바를 사용하면 Heap 을 사용하기 때문에 실제 사용하는 메모리랑 다름
  - 그래서 ping 을 보내고 response 주는 시간을 바탕으로 부하를 분산함
  - 근데 할당하는 작업이 얼마나 자원을 사용하는가? 가 또 중요함
  - L3 랑 L4 차이가 있는데, 요점은 어디까지 메시지를 까서 보는가? 임

## Master-Slave 아키텍처

- 하둡에서 이 구조 사용함
  - 하나는 Db, 다른 건 실제 처리하는 어플리케이션
  - 야후에서 웹 서버 뒤에 존재하는 페이지들을 데이터 노드들로 분산 db 를 만들고, 요청을 처리하는 TaskTracker 를 둬서 처리하는 구조를 만듬
  - 이 데이터 구조를 관리하는 걸 네이밍 서버라고 함
  - 데이터가 들어오면 네이밍 서버가 각 데이터 노드에 던져서 처리를 하게 함
  - 그래서 이 구조에서는 빅데이터 처리가 가능함
    - 네이밍 서버가 각 데이터를 분산하고 JobTracker 가 해당 데이터를 가지고 있는 서버에 코드를 넘겨서 작업을 수행하게 함
  - 하둡 2.0 에서는 마스터를 2개 만들고, 파이프앤필터 구조 적용함

## P2P 아키텍처

- peer to peer
- 센터에 메타 정보를 가지고, 그걸 조회해서 각 peer 가 직접 연결
- 하둡에서 데이터 노드에 쌓인 데이터를 네임 노드가 메타데이터를 가지고 있고, jobTracker 가 네임노드에게 질의해서 실제 데이터를 가지고 있는 노드에 접근하는 것과 비슷함
- pure p2p 는 이 중앙 구조를 없애고자 함
- p2p 는 절대 죽지 않음
- 인터넷 상에 존재하지 않는 라우팅을 하고 있음
  - peer 의 응용 단에서 라우팅을 하고 있음
  - 이걸 overlay 네트워크라고 함
    - 물리적인 라우팅이 아니라 응용 프로그램 단에서 라우팅을 하는 것
- distributed 해시테이블을 사용함
  - 이건 블록체인에서도 사용함

## Service Oriented 아키텍처

- 에이전트는 능동적이고, 서비스는 수동적인 것
- 지금은 Service Oriented 에서 agent oriented 로 변하는 추세
  - 어플리케이션이 미들웨어(툴) 을 사용하려고 하다 보니까 Mcp 가 필요해짐
  - 분산된 서비스에서 서로 다른 에이전트가 소통하기 위해서 mcp 를 사용하는 것
- XML Based 웹서비스, BPEL 등이 이 구조임

## MSA

- 핵심은 모든 모듈이 서비스이고, 앞에 게이트웨이라는 api 서버가 있어서 요청 받고 처리하는 것
- active 하게 동작하게 하려면 어떻게 해야할까? 가 문제임

## Presentation abstraction control 아키텍처

- agent 사용할 때 이 구조 사용
  - 각 agent 가 mvc 로 구성됨
  - 서로 동등한 입장임
  - 맨 위에 있는 게 전체 시스템에 대한 abstraction 정보를 가지고 있음
  - 비유하자면 맨 위에 있는 건 유인체이고, 아래 있는 건 드론임
  - 그래서 아래 있는 게 처리해서 위로 보내면, 위에서 그 정보를 종합해서 사용
