# 소프트웨어 아키텍처 14주차

## 패턴

- 패턴이 뭐냐?
  - 런타임에 유저 인터페이스 변화를 어떻게 쉽게 할 것이낙?
  - 요구 사항에 따라 변경하는 게 어플리케이션 핵심 부분을 건들면 안된다
  - 변형 가능성이 크면 어떻게 하나? → 변형되는 부분을 로컬라이징
  - 인풋 아웃풋을 분리시키고, 각각 변형 가능하게 하기
  - 런타임에 프레젠테이션을 바꾸고, 데이터를 추가할 수 있도록.
  - 들어오는 인풋 데이터에 따라 반영이 되도록
- 이걸 해결하는 방법이 MVC 임 (이게 패턴의 일종)
  - 컨트롤러의 handleEvent 가 호출되면 모델의 core data 가 변경됨
  - 모델에서 코어 데이터가 변경되면 notify 를 호출
    - 그러면 내부적으로 view 의 update 가 호출됨
  - 모델에 있는 코어 데이터랑 옵저버를 attach 로 붙여
    - 옵저버는 프레젠테이션에 나타나는 데이터 형태들
- 패턴은 좋은 디자인 == 소프트아키텍처를 문서화한 것
  - 소프트웨어의 복잡성을 해결하는 방법
  - 컴포넌트, 메서드, 관계 를 보여주는 게 패턴임
- 컨텍스트
  - 디자인 stuation
- 문제
  - 아키텍처 driver(동인)
- 해결책
  - 클래스 다이어그램과 시퀀스 다이어그램으로 표현되는 아키텍처
- 어느 단계에서 패턴을 사용하느냐에 따라 아키텍처 패턴, 디자인 패턴 등으로 분화됨

### 아키텍처 패턴

- 소프트웨서 시스템의 구조적인 스키마(아키텍처)
  - 큰 시스템을 작은 시스템으로 세분화하고
  - 메서드를 정의하고
  - 각각의 관계를 정의하고 연결을 구조화함
- 이거에 대한 템플릿을 제공함
- 문제를 정의하고 해결 방법을 생각해야함
  - e.g. 분산 시스템에서 문제는? → 프로토콜, os 가 다름
- e.g.
  - layered architecture
    - mud to structure, network systems 에서 사용
  - broker architecture
    - 중개 시스템에서 사용

### 디자인 패턴

- 아키텍처 패턴은 전체 시스템에 대한 패턴
- 이건 좀 더 작은 단위(컴포넌트 등) 에 대한 패턴
- 비유하자면, 아키텍처 패턴은 컴퓨터, 디자인 패턴은 cpu 나 메모리
- e.g.
  - pub sub 구조 vs 이벤트 브로커 구조
    - 이 둘의 차이점은 큐가 있냐 없냐ㅑ
  - 싱글톤
  - object pool
  - abstract factory
  - compotsite
    - 폴더 트리 구조 만들 때 사용
  - idiom
    - 저수준 패턴
    - 이펙티브 자바 → 효율적인 프로그래밍(e.g. 자바 프로그램 속도 빠르게)

### 아키텍처 패턴 vs 아키텍처 스타일

- 스타이과 패턴은 동의어다!

### 레이어드 아키텍처

- 각 계층은 여러 개의 클래스로 구성되어있다.
- 각 계층은 separation of concerns 로 나누는데, 각 계측은 하나의 책임만 가져야함
- 각 계층은 독립적이어함
- 유지보수와 변형 가능성을 향상할 수 있음
  - 해당하는 계층만 바꾸면 되니까.
- close 구조
  - 네트워크처럼 상 하가 분명한 구조
  - 인접한 데만 접근 가능
- open 구조
  - 바로 아래 계층이 아니라 자기 아래에 있는 모든 계층에 접근 가능
- 안드로이드가 레이어드 아키텍처임
  - os(C) 와 어플리케이션(java) 간의 연동을 가능하게 하는 게 안드로이드 가상화 머신임
  - 그래서 우리는 자바라고 생각하게 됨

### 파티셔닝

- 레이어로 나누는 게 아니라, 높은 응집력, 낮은 결합력을 원칙으로 나눠라
- 마이크로 서비스가 이거 예시임

## Data Flow

- 전체 시스템을 연결해서 들어오는 데이터 셋을 어떻게 transformation 을 잘 할 수 있게 할까? 를 고민한 거
  - 그래서 방송 시스템, 이메일 시스템, ai 등에 사용할 수 있음
  - 왜냐면 계속해서 정해진 순서대로 데이터를 변형하면서 처리해야하니까
- 사이클이 있을 수도 있고, 트리 구조를 가질 수도 있고, 버퍼를 가질 수도 있고 …
- 변형가능성과 재사용성이 중요함

### Batch Sequential

- 전통적인 예제
  - cobol
- 흘러가는 데이터가 배치임(데이터의 묶음)
- 이걸 validate - sort - update - report 함
- e.g.
  - 성적관리 시스템
  - 어떤 데이터 묶음(배치)이 들어오면 판단 - 정렬 - 업데이트 - 보고 하는 일련의 트랜잭션을 거침
- 처리 - 저장 이 반복됨
- 데이터를 한 덩어리 (배치) 로 본다
- 논리적으로는 같은 다녀야 하는 데이터를 묶은 것인데, 현대에는 리소스의 효율적인 사용을 위해 배치 단위로 데이터를 처리하기도 함
  - e.g. GPU 효율을 위해서 배치 단위로 데이터 처리

### Pipe and Filter

- 배치랑 비슷함
- 들어온 데이터를 필터하고 보내고 필터하고 보내고 …
- 차이점은 들어오는 데이터임
  - 여기서는 데이터가 stream 형식임
  - 이 데이터와 다음 데이터가 관련이 있을 수도 있고 없을 수도 있음
- 버퍼가 fifo 구조임
  - 먼저 온 게 먼저 나가야함
- 데이터 크기 제한은 없음. 데이터가 순서대로 들어오고 순서대로 처리되어서 나가면 됨
  - 음성, 이미지, 텍스트, 바이트 다 됨
- 들어오는 데이터 스트림을 변형시키는 독립적인 걸 필터라고 함
- 파이프는 데이터 스트림을 다음 필터로 옮기는 것
- 파이프는 두 개의 필터 사이에 존재함
- 컴파일러에 사용됨
- push / pull 방식이 있음
  - 필터가 데이터를 가져오면 필터가 active 한 거임
  - 그리고 파이프로 데이터 넘기면 파이프가 passive 한 거임
  - 파이프는 공통의 저장소가 될 수 있음
    - 리눅스에 파이프
    - 데이터는 os 에 저장됨

### Implicit Asynchronous

- async 하고 sync 를 이해해야함
  - 전화는 sync
  - 카톡은 async
- 비동기가 가능하려면 요청 받는 쪽에 버퍼가 있어야하고, 호출하는 쪽에 콜백이 있어야함
- 이걸 미리 만들어둔 게 미들웨어임
- explict vs implicit invocation
  - 명백한 거는 보내는 쪽이 보내는 걸 받는 쪽이 알고 있음
  - 불분명한 건 보내는 쪽이 보내는 걸 받는 쪽이 모르고 있음
    - 항공모함에서 이거 사용함
    - 브로드캐스팅으로 데이터를 뿌리면 리스너가 처리함
    - DDS 라는 프로토콜이 있음
- 시스템을 두 파트로 나눔
  - 한 쪽은 퍼블리셔, 다른 쪽은 서브스크라이버
- 메시지 큐는 one2one
- 메시지 토픽은 one2many
- 요즘엔 언어차원에서 이거 지원함
  - 자바는 JVM 이 버퍼 역할을 하고, 파이썬에서는 인터프리터가 버퍼 역할을 함
