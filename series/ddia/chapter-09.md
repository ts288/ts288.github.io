# DDIA 9장

## 일관성과 합의

## 선형성

- 실제로 복사본은 여러 개일 수 있지만, 외부에서 시스템을 봤을 때 시스템에 데이터 복사본이 하나만 있고, 그 데이터를 대상으로 수행하는 모든 연산이 어느 한 순간에 원자적으로 적용된 것처럼 보이게 만드는 것
  - 클라이언트가 쓰기를 성공적으로 완료하자마자 해당 데이터베이스를 읽는 모든 클라이언트는 방금 쓰여진 값을 볼 수 있어야 함
  - 최신성 보장이라고 이해하면 됨

### 시스템에 선형성을 부여하는 것은 무엇인가?

- 클라이언트 관점에서는 요청 - 응답이라고 생각하지만, 이 사이에는 DB 에서 논리적 읽기나 쓰기가 확정되는 “특정 순간” 이 있음
  - 연산의 요청 - 응답 시간을 막대로 표현하면, 그 내부에 연산이 실행된 시점이 수직선으로 표시되어 있음
- 이 “특정 순간” 을 기준으로 수행되는 읽기, 쓰기, CAS(Compare And Set) 등이 확정된다고 생각하면 됨

#### 선형성 vs 직렬성

- 둘 다 순차적인 순서로 배열되는 것을 의미함
- 다만 직렬성은 트랜잭션 수준, 선형성은 레지스터(개별 객체) 수준에 적용된다는 차이가 있음
- 또한 직렬성은 실제 시간 순서를 반드시 보존하지 않아도 되지만, 선형성은 실제 시간 순서를 보존해야 함!
  - 직렬성은 여러 트랜잭션이 동시에 실행되더라도 그 결과가 어떤 순서로 하나씩 실행된 것과 같기만 하면 됨
  - 선형성은 각 연산이 실행 구간 안의 어느 한 순간에 원자적으로 수행된 것처럼 보여야 하며, 이미 완료된 연산은 그 이후 시작된 연산보다 앞선 순서로 배치되어야 함

### 선형성에 기대기

- 쓰기가 이후 발생하는 모든 읽기에 즉시 반영되어야 하는 경우가 있음

#### 잠금과 리더 선출

- 단일 리더 복제 환경에서는 리더가 하나만 선출되어야 함
- 이 때 락을 사용할 수 있음
  - 락을 획득한 노드가 리더가 되는 방식
  - 모든 노드는 어느 노드가 락을 소유하는지에 대해 동의해야함
- 분산 락과 리더 선출을 구현하기 위해 아파치 주키퍼나 etcd 같은 코디네이션 서비스를 사용함
  - 합의 알고리즘을 사용해 선형성 연산을 내결함성이 있는 방식으로 구현해줌
  - 알고리즘은 후반에 설명

#### 제약 조건과 유일성 보장

- 제약 조건이나 유일성을 강제하기 위해서는 선형성이 필요함
- 특정 제약 조건(전역 유일성, 중복 생성 방지, 동일 자원에 대한 단일 소유권 등) 은 모든 노드가 동의하는 하나의 최신 값(선형성) 을 요구함
  - 모든 서비스에서 필요한 건 아님. 데이터 민감한 데에서만 사용하면 됨

#### 채널 간 타이밍 의존성

- 선형성의 경쟁 조건은 서로 다른 두 채널을 이용해 같은 사실을 전파할 때에 발견된다
  - 특정 채널의 동작이 먼저 수행된 다음, 다른 채널의 동작이 수행되어야 하는데 선형성이 지켜지지 않으면 경쟁 조건이 발생함!

  ```lua
  e.g.
  1. API 서버가 DB 에 사진 정보를 기록한다.
  2. 메시지 큐에 “이 사진 리사이즈해라” 이벤트를 보낸다.
  3. 워커가 메시지를 받고 DB 에서 사진 정보를 읽는다.
  ```

### 선형성 시스템 구현하기

- 선형성은 데이터 복사본이 하나만 잇는 것처럼 동작하고, 모든 연산이 원자적이기만 하면 됨
- 따라서 가장 간단하게는 데이터 복사본 하나만 사용하면 됨
  - 근데 이건 장애 발생에 취약해지는 문제가 있음
  - 그래서 복제를 사용함
- 복제 방식 중, 선형적으로 만들 수 있는 것만 추려보자!
  - 단일 리더 복제(선형적이 될 가능성 있음)
    - 리더나 동기적으로 갱신된 노드에서 실행한 읽기는 선형적이 될 가능성이 있음
      - 그러나 이 경우에는 누가 리더인지 확실하다고 가정해야함
      - 왜냐면 리더가 아닌 노드가 자신이 리더라고 생각할 수도 있기 때문(GC 로 장기간 멈춘 경우 등)
    - 모든 단일 리더 복제가 선형적인 것은 아님
      - 설계, 동시성 버그 등등
      - <b>Q. 구체적으로 어떻길래 선형적인 게 아님?</b>
        - 복제가 느려서 팔로워가 최신 데이터를 유지하지 못할 때 읽거나,
        - stale leader 문제가 발생하면 선형성이 깨질 수 있음
  - 합의 알고리즘(선형적)
    - 후반부에서 설명
    - 단일 리더 복제와 비슷하나, 스플릿 브레인과 복제본이 뒤쳐지는 문제를 막을 수단이 포함되기 때문에 선형성 저장소를 안전하게 구현 가능함
    - e.g. 주키퍼, etcd
  - 다중 리더 복제(비선형적)
    - 여러 노드에서 동시에 r/w && 비동기 복제하기 때문에 충동 가능성 높음
  - 리더 없는 복제(아마도 비선형적)
    - 정족수를 요구하기 때문에 엄격한 일관성 가능하다고 보기도 하지만, 정족수 설정과 엄격한 일관성의 정의에 따라 주장이 완전한 진실은 아님

#### 선형성과 정족수

- 직관적으로 다이나모 스타일(리더 없는 복제) 에서 엄격한 정족수를 사용한 읽기 쓰기는 선형적인 것처럼 보임
- 그러나 네트워크 지연의 변동이 심하면 경쟁 조건이 생길 수 있음
  - 지연이 길어져 정족수 이하의 노드에만 쓰기가 반영된 시점에 읽기를 수행하는 경우, 선형성을 충족할 수 없음
- 성능이 떨어지는 비용을 지불하고 선형성 획득이 가능하긴 함
  - 읽기 수행하는 클라이언트는 읽기 복구(병렬 조회 후 가장 높은 버전의 값을 신뢰, 이후 이전 버전을 가진 노드 업데이트) 를 동기식으로 수행하고
  - 쓰기 수행하는 클라이언트는 요청 보내기 전에 노드들의 정족수로부터 최신 상태를 읽으면 됨
  - 근데 이 방식으로는 선형성 읽기/쓰기만 구현 가능하고, 선형성 compare-and-set 은 안됨
    - <b>Q. 왜? compare and set 은 원자적으로 수행되어야 하는데, 이건 읽기 쓰기가 별개의 동작처럼 수행되어서 그런가?</b>
      - ㅇㅇ. compare-and-set 은 원자적으로 읽기/쓰기가 수행되어야 하는데, 이 방식에서는 읽기 따로 쓰기 따로잖음

### 선형성의 비용

- 데이터센터가 분산되어 있는 경우에 네트워크 분단이 발생한다면, 선형성은 챙길 수 없지만 가용성을 챙길 수 있다
- 반면에 단일 리더 복제를 선택하면 선형성은 챙길 수 있지만, 리더가 데이터센터 중 하나에 잇어야 하며, 모든 쓰기와 선형성 읽기는 리더로 보내져야함
  - 그래서 네트워크 분단이 발생하면 팔로워 데이터센터로 접속한 클라이언트들은 리더로 연결이 안되어 쓰기, 선형성 읽기 모두 불가능함

#### CAP 정리

- 위 문제는 어떤 선형성 데이터베이스라도 구현과 관계없이 발생할 수 있는 문제임
- 신뢰성이 없는 네트워크나, 한 데이터센터 내에서도 발생할 수 있는 문제임
  - <b>Q. 한 데이터센터 내에서 발생하는 네트워크 분단은 어떤 거임?</b>
    - 리더-팔로워 네트워크 장애
    - 스위치 장애
    - GC pause or STW(stop the world) 등등
- 트레이드 오프는 아래와 같음
  - 애플리케이션에서 선형성 요구하는 경우, 네트워크 문제로 복제 서버와 연결이 끊기면 장애가 복구될 동안은 요청을 처리할 수 없음(가용성이 없음)
  - 애플리케이션에서 선형성 요구하지 않는 경우, 네트워크 문제로 복제 서버와 연결이 끊기더라도 독립적으로 요청 처리는 가능함. 그러나 선형적이지 않음
- 따라서 선형성이 필요 없는 애플리케이션은 네트워크 문제에 더 강인함
  - 제약이 하나 줄기 때문
- 이걸 정리한 게 CAP 정리임
  - 근데 범위가 매우 좁음
  - 하나의 일관성 모델(선형성) 과 한 종류의 결함(네트워크 분단 or 노드가 살아있으나 연결이 끊긴 상황) 만 고려함
  - 그래서 시스템 설계 시에 실용적 가치는 거의 없음

#### 선형성과 네트워크 지연

- 선형성은 유용하나, 실제로 선형적인 시스템은 드물다
  - 성능을 중시하기 때문에 선형성을 버리는 것
- 다중 코어 CPU 의 RAM 조차 선형적이지 않다!
  - 하나의 CPU 코어에서 실행 중인 스레드가 메모리 주소에 쓴 후, 곧 다른 CPU 코어에서 실행되는 스레드가 같은 주소를 읽어도 첫 번째 스레드가 쓴 값을 읽을 것이라고 보장되지 않음
    - <b>Q. 왜? 그 사이에 값이 변경된다는 가정이 있는 거임?</b>
      - 값이 변경되는 건 아니고, 이런 이유 때문임

      ```lua
      코어 1에서 실행 중인 스레드가 쓰고, 이어서 코어 2의 스레드가 읽는 경우:

      코어 1의 쓰기가 store buffer에 머물러 있을 수 있음
      코어 2는 자기 cache에 있던 오래된 값을 읽을 수 있음
      CPU가 성능을 위해 메모리 연산 순서를 재배치할 수 있음
      컴파일러도 동기화가 없다면 일부 순서를 최적화할 수 있음
      ```
    - 메모리 배리어나 펜스를 사용하면 보장 가능함
      - <b>Q. 이게 뭔데?</b>
        - cpu 하고 컴파일러한테 제약 거는 장치임
          - 이 지점을 기준으로 특정 메모리 연산들이 앞뒤로 재배치되지 않게 하라
          - 그리고 이전 쓰기가 다른 코어에 관찰 가능해지도록 필요한 동기화를 수행하라.
  - 이건 모든 CPU 코어가 각각 메모리 캐시와 저장 버퍼를 갖기 때문인데, 메모리 접근은 기본적으로 캐시로 먼저 가고, 변경은 메인 메모리에 비동기로 기록됨
    - 캐시 접근이 훨씬 빠르기 때문에 이렇게 함
    - 비동기 복제이기 때문에 선형성 손실됨
  - 이렇게 하는 이유는 성능을 중시하기 때문!
  - 여러 분산 데이터베이스에서도 성능을 중시하기 때문에 선형성을 보장하지 않음
  - 선형성을 원하면 읽기와 쓰기 요청의 응답 시간이 적어도 네트워크 지연의 불확실성에 비례해야 하나, 대부분 컴퓨터 네트워크는 지연 변동이 심하기 때문에 지연 시간에 민감한 시스템에서는 선형성을 버림

## 순서화 보장

### 순서화와 인과성

- 순서화는 인과성을 보장하는데 도움을 줌
- 시스템이 인과성에 의해 부과된 순서를 지키면 시스템이 인과적으로 일관적이라고 함
  - e.g. 스냅숏 격리

#### 인과적 순서가 전체 순서는 아니다

- 전체 순서
  - 항상 어떤 것이 더 크거나 작다는 것을 말할 수 있는 것
  - e.g. 자연수 비교
- 부분 순서
  - 항상 어떤 것이 더 크거나 작다는 비교가 가능하지 않은 것
  - e.g. 집합 비교
- 선형성 시스템에서는 연산의 전체 순서를 정할 수 있음
  - 데이터 복사본이 하나만 있는 것처럼 동작하기 때문에, 모든 연산이 원자적이면 어떤 두 연산 중 하나가 먼저 실행됐다고 할 수 있음
  - 따라서 선형성 데이터스토어에는 동시적 연산이 없음
    - 모든 연산은 하나의 타임라인 위에 있고, 해당 타임라인을 따라 전체 순서가 정해짐
    - 다수의 요청이 있을 수 있지만, 데이터스토어는 타임라인을 따라 단일 데이터 복사본에 연산을 실행해 모든 요청이 한 시점에 원자적으로 처리되도록 보장함
- 인과성에서는 연산의 전체 순서를 항상 정할 수는 없음
  - 동시에 두 연산이 실행되는 경우, 어느 연산이 더 먼저 수행된 것인지 비교할 수 없기 때문
  - 이건 git 같은 거임
    - 한 시점에 여러 브랜치가 있을 수 있음

#### 선형성은 인과적 일관성보다 강하다

- 선형성은 인과성을 내포한다
  - 선형적인 모든 시스템은 인과성도 올바르게 유지한다
- 그런데 성능 상의 이유로 선형성을 버리기도 한다
- 대신 절충이 가능하다
  - 선형적으로 만드는 성능 손해를 유발하지 않고 인과적 일관성을 만족시킬 수 있다
    - <b>Q. 오잉 어케하는 거임?</b>
      - 선형성에서는 모든 연산이 순서가 있어야 하지만, 인과적 일관성에서는 인과 관계 있는 것만 순서를 지키면 된다는 아이디어에서 출발
      - 원인-결과 관계가 있는 연산의 순서만 지키고, 서로 무관한 동시 연산은 순서를 강제로 정하지 않음

      ```lua
      1. 각 쓰기에 버전 정보 또는 dependency metadata를 붙임
      2. 클라이언트가 읽은 버전 정보를 기억함
      3. 클라이언트가 나중에 쓰기를 보낼 때 “나는 이 버전들을 본 상태에서 이 쓰기를 만든다”는 정보를 함께 보냄
      4. 복제본은 후속 쓰기를 적용하기 전에, 그 쓰기의 선행 의존성이 먼저 반영되어 있는지 확인함
      5. 선행 의존성이 있으면 기다림
      ```
  - 인과적 일관성은 네트워크 지연의 영향을 받지 않고, 네트워크 장애 발생에도 가용하다
- <b>Q. 최신 데이터베이스 연구는 어떻게 되고 있나?</b>
  1. 버전 벡터 / dependency vector 기반 causal consistency
     - 각 객체나 세션에 대해 “어떤 노드의 몇 번째 쓰기까지 봤는지” 를 기록
     - 쓰기 요청에 클라이언트가 읽은 버전 정보를 함께 전달
     - 복제본은 쓰기를 적용하기 전에 그 쓰기가 의존하는 선행 버전들이 먼저 도착했는지 확인
     - 인과성을 정확히 추적할 수 있으나, 메타데이터가 커질 수 있음
  2. 세션 보장(session guarantees) 방식
     - 완전한 전역 causal consistency 보다 약하지만 실용적
     - 대표 보장은 아래와 같음
       - read-your-writes
         - 내가 쓴 값은 내가 다시 읽을 수 있어야 함
       - monotonic reads
         - 한 번 본 값보다 더 오래된 상태로 되돌아가지 않아야 함
       - monotonic writes
         - 같은 클라이언트의 쓰기는 순서대로 반영되어야 함
       - writes-follow-reads
         - 내가 읽은 값을 기반으로 한 쓰기는 그 읽기 이후에 반영되어야 함
     - 요청을 보낼 때 lastSeenVersion 을 같이 보내고, 적어도 lastSeenVersion 이상을 반영한 replica 에서 읽게 하는 방식으로 구현. 쓰기도 마찬가지로 version 을 보내서 해당 version 을 따라잡은 뒤에 반영되도록 구현

     ```lua
     1. 클라이언트가 읽기/쓰기 응답에서 version 또는 timestamp를 받음
     2. 클라이언트는 세션 컨텍스트에 최신 version을 저장함
     3. 다음 요청에 이 세션 컨텍스트를 함께 보냄
     4. 서버는 해당 context를 만족하는 replica에서 처리함
     5. 만족하지 못하면 대기, 리더 라우팅, 다른 replica 선택, 재시도 등을 수행함
     ```

     - 많은 실무 시스템은 완전한 선형성 대신 이런 세션 보장을 제공함. 왜냐면 사용자가 체감하는 일관성 문제 상당수는 전역 선형성보다 세션 보장으로 해결되기 때문

#### 인과적 의존성 담기

- 인과성을 유지하기 위해서는 어떤 연산이 다른 연산보다 먼저 실행됐는지 알아야 함
- 한 연산이 다른 연산보다 먼저 실행됐다면 모든 복제 서버에서 그 순서로 처리되어야 함
  - 따라서 복제 서버가 연산을 처리할 때 인과적으로 앞서는 모든 연산이 이미 처리됐음을 보장할 수 있어야 함
  - 만일 선행 연산 중 누락된 게 있으면 후속 연산은 선행 연산이 완료될 때까지 기다려야함
- 어떤 연산이 다른 연산보다 먼저 실행됐는지 결정하려면 전체 데이터베이스에 걸친 인과적 의존성을 추적해야함
  - 이를 위해 버전 벡터를 일반화할 수 있음
  - <b>Q. 버전 벡터?</b>
    - 분산 시스템에서 각 노드가 어느 버전까지 알고 있는지 기록한 메타데이터
    - e.g. \{ A: 3, B: 2, …\} 이렇게 되어있으면 A 에서 발생한 3번째 업데이트까지 반영, B 에서 발생한 2번째 업데이트까지 반영 … 이런 식임
- 인과적 순서를 결정하기 위해 데이터베이스는 애플리케이션이 데이터의 어떤 버전을 읽었는지 알아야 함
  - 이건 SSI(직렬성 스냅숏 격리 에서 설명한 SSI 충돌 검출 방식과 비슷한데, 트랜잭션이 커밋을 원할 때 데이터베이스가 해당 트랜잭션이 읽은 데이터의 버전이 여전히 최신 버전인지 확인하는 거임
  - 이를 목적으로 데이터베이스는 어떤 데이터를 어떤 트랜잭션이 읽었는지 추적함

### 일련번호 순서화

- 모든 인과적 의존성을 추적하는 것은 실용성이 떨어짐
- 그래서 일련번호나 타임스탬프를 사용해 이벤트의 순서를 정함
  - 크기가 작고 인과성에 일관적인 전체 순서를 제공한다는 장점이 있음
- 단일 리더 복제 데이터베이스에서는 복제 로그가 인과성에 일관적인 쓰기 연산의 전체 순서를 정의함
  - 이거 바탕으로 팔로워가 쓰기 적용하면 리더에 뒤쳐지더라도 인과성에 일관적일 수 있음

#### 비인과적 일련번호 생성기

- 단일 리더 방식이 아니라 다중 리더 or 리더 없는 데이터베이스를 사용한다면 연산에 사용할 일련번호를 생성하는 방법이 명확해보이지 않음 ㅜ.ㅜ
  - 왜냐면 발행 주체가 여럿인데, 이들을 동기화하기가 까다롭기 때문
- 현실에서는 이렇게 함. 근데 이렇게 생성한 일련번호가 인과성에 일관적이지 않음
  - 각 노드가 독립적인 일련번호 집합을 생성하게 하기
    - e.g. A 는 홀수만, B 는 짝수만 생성하게 하는 식으로
    - 노드마다 초당 연산수가 달라 홀짝이 번갈아 나오지 않을 수 있음
      - 이 경우 인과적으로 어떤 게 먼저인지 알 수 없음
  - 각 연산에 일 기준 시계(물리적 시계) 에서 얻은 타임스탬프 붙이기
    - 해상도가 높다면 실용적
    - 물리적 시계에서 얻은 타임스탬프는 시계 스큐에 종속적임
      - 그래서 인과적으로 나중에 실행된 연산이 더 낮은 타임스탬프를 배정받을 수도 있음
  - 일련번호 블록을 미리 할당하기
    - A 는 1\~1000, B 는 1001\~2000 이렇게 범위 정해두고 범위 내에서 배정하기
    - B 노드에서 먼저 일련번호 받고, A 노드에서 받으면 일련번호가 인과성에 일관적이지 않게 됨

#### 램포트 타임스탬프

- 인과성에 일관적인 일련번호를 생성하는 간단한 방법이 잇음
- 램포트 타임스탬프를 사용하면 됨
  - (카운터, 노드 ID) 의 쌍으로 표현됨
  - 카운터 값은 처리한 연산의 개수임
  - 특정 노드가 자신의 카운터 값보다 더 큰 카운터를 가진 요청이나 응답을 받으면 자신의 카운터를 해당 값 + 1으로 설정함
  - 카운터 값이 같은 경우, 노드 ID 가 큰 것이 타임스탬프가 크다고 판정
- 즉, 모든 연산에 최대 카운터 값이 따라다니게 하는 방법임
- 버전 벡터랑 혼동될 수 있음
  - 참고로 버전 벡터는 각 노드가 해당 데이터 key 에 대해 몇 번째 버전까지 생성/반영했는지를 기록한 메타데이터임. 예전에 나왓음
  - 버전 벡터를 사용하면 두 연산이 동시적인지, 혹은 인과적으로 의존하는지 알 수 있지만, 램포트 타임스탬프는 항상 저체 순서화를 강제함
  - 램포트 타임스탬프의 전체 순서화로는 두 연산이 동시적인지 혹은 인과적으로 의존하는지 알 수 없음
    - 그냥 앞서서 연산이 있었다\~ 를 아는 거지 인과적인지 동시적인지 이런 건 모른다는 거임
  - 버전 벡터는 레코드/객체 버전 관리 쪽에서 적용되고, 램포트 타임스탬프는 분산 이벤트 순서화 쪽 개념임. 둘이 다루는 영역이 다름
  - 그리고 램포트 타임스탬프가 크기가 더 작음

#### 타임스탬프 순서화로는 충분하지 않다

- 전체 순서는 모든 연산을 모아야 드러남
  - 예를 들어, 두 명의 사용자가 같은 아이디로 회원 가입을 하는 상황이라면, 한 명만 성공해야함
  - 근데 두 사용자가 각각 다른 노드에 쓰기를 진행한다면, 쓰는 시점에는 각 요청 중 어떤 것이 성공해야하고 실패해야하는지 알 수 없음
    - 왜냐면 다른 노드에서 동일한 아이디로 쓰는 중인지, 그 노드의 타임스탬프가 어떤 상태인지 모르니까
- 그래서 유일성 제약 조건 같은 건 전체 순서만으로 충분하지 않음
  - 언제 그 순서가 확정되는지도 알  수 있어야 함

### 전체 순서 브로드캐스트

- 방금 본 것처럼, 다중 노드 환경에서는 전체 순서를 확정하는 시점이 중요함
- 이를 가능하게 하는 게 전체 순서 브로드캐스트임
  - 노드 사이에 메시지를 교환하는 프로토콜로 기술되며, 두 가지 안전성 속성을 항상 만족해야함
    1. 신뢰성 있는 전달
       1. 어느 메시지도 손실되면 안되고, 메시지가 한 노드에 전달되면 모든 노드에 전달되어야 함
    2. 전체 순서가 정해진 전달
       1. 메시지는 모든 노드에 같은 순서로 전달되어야 함
- 노드나 네트워크에 결함이 있더라도 신뢰성과 순서화 속성이 항상 만족되도록 보장해야함
  - 네트워크 장애가 발생햇다면, 복구 이후에 메시지가 올바른 순서로 전달되게 해야함

#### 전체 순서 브로드캐스트 사용하기

- 상태 기계 복제
  - 모든 메시지가 데이터베이스에 쓰기를 나타내고, 모든 복제 서버가 같은 쓰기 연산을 같은 순서로 처리하면 복제 서버들은 서로 일관성 있는 상태를 유지한다는 것
  - 11장에서 다시 살펴볼 예정!
- 전체 순서 브로드캐스트는 직렬성 트랜잭션 구현에도 사용할 수 있음
- 전체 순서 브로드캐스트에서는 메시지가 전달되는 시점에 순서가 고정됨
  - 후속 메시지가 전달됏다면 그 순서의 앞에 메시지를 끼워넣지 못함
  - 그래서 타임스탬프 순서화보다 강함
    - <b>Q. 타임스탬프 순서화에서는 병합 과정에서 순서 조정이 되어서 그런 건가?</b>
      - 대충 맞는데 좀 더 보완하면 이렇게 됨

      > 타임스탬프 순서화는 각 이벤트에 순서값을 붙이지만, 그 순서가 언제 최종 확정되는지 보장하지 못한다. 반면 전체 순서 브로드캐스트는 메시지가 전달되는 순간, 그 앞에 어떤 메시지도 나중에 끼어들 수 없도록 순서를 확정한다.
- 전체 순서 브로드캐스트로 로그를 만들 수도 있고, 펜싱 토큰의 역할도 하게 할 수 있음

#### 전체 순서 브로드캐스트를 사용해 선형성 저장소 구현하기

- 전체 순서 브로드캐스트는 비동기식임
  - 그래서 메시지가 고정된 순서로 신뢰성 있게 전달되는 것은 보장되지만, 언제 전달될지는 보장되지 않음
- 선형성은 최신성 보장이 됨
  - 읽기가 최근에 쓰여진 값을 보는 것이 보장됨
- 선형성을 보장하기 위해서는 순서를 확정하는 시점이 중요했음(앞서 살펴본 아이디 생성 문제)
  - 이를 전체 순서 브로드캐스트로 해결할 수 있음
  - 사용 가능한 아이디마다 원자적 cas(compare and set) 연산이 구현된 선형성 저장소가 있다고 하면, 아이디를 생성하는 시점에 레지스터 값이 null 이라면 cas 연산을 수행해 아이디를 설정하게 할 수 있음
  - 만일 동시에 여러 사용자가 같은 아이디를 가지려 한다면 cas 연산 중 하나만 성공함
    - 다른 연산은 선형성 때문에 null 이 아닌 값을 보게 되기 때문
- 구현은 전체 순서 브로드캐스트를 append-only 로그로 사용해 할 수 있음
  - 첫 번째 요청이라면 수락하고 이전에 다른 요청이 있었다면 어보트 시킴으로써 구현 가능함
  - 로그는 모든 노드에 같은 순서로 전달되므로, 여러 개의 쓰기가 동시에 실행되면 모든 노드가 어떤 쓰기가 먼저 실행된 것인지 동의함
  - 로그 기반 직렬성 다중 객체 트랜잭션 구현도 이와 비슷하게 할 수 있음
- 근데 이건 선형성 쓰기만 보장하지, 선형성 읽기는 보장하지 않음
  - 비동기 갱신이기 때문에, 로그가 느릴 수 있음
  - 이를 해결하기 위해서 선택할 수 있는 선택지는 아래와 같음
    1. 로그에서 최신 로그 메시지의 위치를 선형적으로 얻고, 해당 위치까지의 모든 항목이 전달되기를 기다린 후에 읽기 수행
    2. 쓰기 실행 시에 동기적으로 갱신 보장하는 복제 서버에서 읽기

#### 선형성 저장소를 사용해 전체 순서 브로드캐스트 구현하기

- 전체 순서 브로드캐스트를 통해 보내고 싶은 모든 메시지에 선형성 정수로 increment-and-get 연산 수행하고, 레지스터에서 얻은 값을 일련번호로 메시지에 붙여서 모든 노드에 전송
- 후에 수신자들은 일련번호 순서대로 메시지를 전달하면 됨
- 예를 들어, 어떤 노드가 메시지 4를 전달하고 메시지 6을 받았다면, 메시지 6을 전달하기 전에 메시지 5를 기다리면 되는 거임
  - 램포트 타임스탬프에서는 이렇게 안 함. 거기서는 그냥 자기가 보내는 다음 메시지를 7로 설정함
  - 이게 전체 순서 브로드캐스트와 타임스탬프 순서화의 차이임

## 분산 트랜잭션과 합의

- 여러 노드들이 뭔가에 동의하게 만드는 것(비공식적 정의)
- 리더 선출, 원자적 커밋 등에서 사용

### 원자적 커밋과 2단계 커밋(2PC)

- 원자성은 중간 상태를 노출시키는 것을 방지해줌
  - 트랜잭션이 항상 성공하거나 실패한 상태로 남게 해줌
  - 다중 객체 트랜잭션과 보조 색인 유지에 중요함

#### 단일 노드에서 분산 원자적 커밋으로

- 단일 노드에서 실행되는 트랜잭션의 원자성은 저장소 엔진에서 구현됨
- 트랜잭션 커밋 요청 → DB 가 트랜잭션의 쓰기가 지속성 있게 함 → 디스크에 있는 로그에 커밋 레코드 추가
  - <b>Q. 쓰기가 지속성 있게 한다는 게 머임?</b>
    - 변경 기록을 WAL 로그에 남겨서 장애 발생해도 복구 가능하게 한다는 거임
    - ‘로그에 커밋 레코드 추가’ 는 트랜잭션이 최종적으로 commit 되었음을 WAL 로그에 표기하는 것
  - DB 가 죽으면 노드가 재시작 될 때 노드로부터 복구
- 단일 노드에서 트랜잭션 커밋은 데이터가 디스크에 지속성 있게 쓰여지는 순서에 결정적으로 의존함
- 트랜잭션이 커밋되거나 어보트되는지를 결정하는 시점은 디스크기 커밋 레코들 쓰기를 마치는 시점임
  - 이 시점 전에는 db 가 죽어서 커밋이 어보트 될 가능성이 잇지만, 이 시점 후에는 db 가 죽더라도 커밋된 상태임
- 근데 트랜잭션에 여러 노드가 관여한다면?
  - 다중 객체 트랜잭션을 사용하거나, 보조색인을 사용하거나
  - 이 경우에는 특정 노드에서만 성공할 수 잇기 때문에 원자성 보장을 위반하기 쉬움
    - <b>Q. 같은 데이터를 다루는데 왜 특정 노드에서만 성공할 수 있지? 네트워크 장애로 인한 상황이나 특정 노드가 죽은 상황 제외하고</b>
      - 각 노드가 가진 로컬 상태와 제약 조건이 다를 수 있기 때문
      - 모든 노드에 같은 트랜잭션을 수행하는 게 아니라는 걸 생각해야함

      ```lua
      A 노드: 주문 row insert 성공
      B 노드: 결제 row insert 실패
      ```
- 트랜잭션에 참여하는 다른 노드들도 커밋될 것이라고 확신할 때에만 커밋이 되어야 함
- 커밋된 트랜잭션을 되돌리는 것을 허옹하면 커밋 후 읽기의 보장이 깨지게 됨
  - 따라서 커밋 이후에 어보트 하는 것은 허용되지 않음
  - 되돌리는 트랜잭션을 발행해서 커밋시켜야함(보상 트랜잭션)

#### 2단계 커밋(2PC) 소개

- 여러 노드에 걸친 원자적 트랜잭션을 달성하는, 즉 모든 노드가 커밋되거나 모든 노드가 어보트되도록 보장하는 알고리즘
  - 코디네이터(coordinator) 라고도 함
- 커밋/어보트 과정이 두 단계로 나뉘어서 2단계 커밋임
- cf) 2단계 잠금(2PL) 과 혼동하면 안됨
  - 2PC 는 분산 데이터베이스에서 원자적 커밋을 제공하는 것
  - 2PL 은 직렬성 격리를 제공하는 것
- 애플리케이션이 커밋할 준비가 되면 코디네이터가 1단계를 시작함
  - 각 노드에 준비 요청을 보내서 커밋할 수 있는지 물어보고, 응답을 추적함
    - 모든 참여자가 ok 라고 응답하면 2단계에서 커밋 요청을 보내고 커밋이 실제로 일어남
    - 참여자 중 누구라도 no 라고 응답하면 2단게에서 모든 노드에게 어보트 요청을 보냄
    - <b>Q. 참여자는 그럼 ok 라고 응답하고 다른 커밋 요청을 어보트 시키나? 현 상태를 유지해야 하니까</b>
      - 무조건 abort 는 아니고, row 에 락 잡고 해당 row 에 쓰려는 다른 트랜잭션을 abort 하거나 대기시킴
    - <b>Q. 1단계에서 준비 요청만 보내고 아직 실제 요청을 보내지 않은 상태아님? 왜 no 라고 응답 받으면 모든 노드에게 어보트 요청을 보냄?</b>
      - 실제 요청(SQL)은 미리 전달 됨
      - 준비 요청은 이미 전달된 트랜잭션을 확정하기 위한 준비를 하라는 요청임
      - 그래서 no 라고 응답을 받으면 어보트 요청을 보내서 트랜잭션을 롤백시킴

#### 약속에 관한 시스템

- 준비 요청과 커밋 요청은 2단계 경우에서 쉽게 손실될 수 있는데, 왜 2PC 는 다를까?
  1. 애플리케이션은 분산 트랜잭션을 시작하기 원할 때 코디네이터에게 트랜잭션 ID 를 요청함
     1. 이 트랜잭션 ID 는 전역적으로 유일함
  2. 애플리케이션은 각 참여자에서 단일 노드 트랜잭션을 시작하고, 단일 노드 트랜잭션에 트랜잭션 ID 를 붙임
     1. 모든 읽기/쓰기는 단일 노드 트랜잭션 중 하나에서 실행됨
     2. 노드가 죽거나 타임아웃 발생하면 코디네이터나 참여자 중 누군가 어보트할 수 있음
  3. 애플리케이션이 커밋할 준비가 되면 코디네이터가 모든 참여자에게 전역 트랜잭션 ID 로 태깅된 준비 요청을 보냄
     1. 요청 중 실패하거나 타임아웃 발생하면 코디네이터는 모든 참여자에게 해당 트랜잭션 ID 로 어보트 요청 보냄
  4. 참여자가 준비 요청 받으면 트랜잭션 커밋 가능한지 확인함
     1. 트랜잭션 데이터를 디스크에 쓰는 데 용량이 충분한지, 충돌이나 제약 조건 위반 안하는지 등등 체크하고 yes/no 응답 보냄
  5. 코디네이터가 모든 준비 요청에 대해 응답을 받으면 커밋/어보트에 대한 최종 결정을 함
     1. 모든 참여자들이 yes 라고 하면 커밋, 아니면 어보트
     2. 이 결정을 트랜잭션 로그에 남김(커밋 포인트)
  6. 결정이 로그로 작성되면 모든 참여자에게 커밋이나 어보트 요청이 전송됨
     1. 이 요청이 실패하거나 타임아웃 발생하면 코디네이터는 성공할 때까지 재시도해야함
     2. <b>Q. 근데 결정을 로그로 작성하고 커밋/어보트 요청 보내면, 코디네이터가 죽고 재시작 하는 경우에 해당 요청이 커밋/어보트 되었는지 확인 못하는 거 아님? 순서가 커밋/어보트 하고 로그 작성해야 재시작해도 확신 가능한 거 아님?</b>
        1. 만약 커밋/어보트 확인 이후에 로그 작성한다면, 로그 작성 전에 죽은 경우 기존에 내린 결정을 알 수 없는 문제가 발생하게 됨
        2. 그래서 결정을 로그로 먼저 작성함. 이러면 재시작 됐을 때 같은 결정을 노드에게 다시 내려 원자성을 보장할 수 있음
- 이 프로토콜에는 돌아갈 수 없는 지점이 두 개 있음
  1. 참여자가 yes 라고 응답하는 시점
  2. 코디네이터가 커밋/어보트 결정하는 시점
- 이러한 약속이 2PC 의 원자성을 보장함

#### 코디네이터 장애

- 코디네이터가 준비 요청을 보내기 전에 장애가 발생하면 참여자가 안전하게 트랜잭션 어보트 가능함
- 근데 참여자가 준비 요청 받고 yes 라고 투표하면 일방적으로 어보트할 수 없음
  - 코디네이터로부터 트랜잭션이 커밋됏는지 어보트됐는지 회신 받을 때까지 기다려야함
  - 이 때 코디네이터가 죽거나 네트워크 장애 발생하면 참여자는 기다려야함
    - 이 상태에 있는 참여자의 트랜잭션을 의심스럽다 또는 불확실하다 고 함
  - 참고로 타임아웃도 도움이 되지 앟음
    - 특정 노드만 타임아웃으로 어보트하고, 다른 참여자만 커밋할 수 있기 때문
    - 각 노드 간의 데이터 정합성 보장이 되지 않을 수 있기 때문에, 다른 신호가 아닌 코디네이터의 응답으로만 결정을 내려야 함
- 이론상으로는 참여자끼리 통신해서 각 참여자의 투표 여부를 알아낸 후 합의가 가능하지만, 이건 2PC 프로토콜의 일부가 아님
- 그래서 코디네이터는 참여자들에게 커밋이나 어보트 요청을 보내기 전에 트랜잭션 로그에 결정을 씀(커밋 포인트 작성)
  - 코디네이터가 복구될 때 트랜잭션 로그를 읽어서 모든 의심스러운 트랜잭션의 상태를 결정하기 때문
  - 코디네이터의 로그에 커밋 레코드가 없는 트랜잭션들은 어보트됨

  <b>Q. 그럼 코디네이터는 재시작하자마자 모든 커밋 포인트를 검사해서 의심스러운 트랜잭션 상태를 결정해야함? 리소스 많이 들 거 같은데? 그리고 모든 참여자의 트랜잭션 상태를 코디네이터가 어떻게 확인함?</b>

  - 모든 커밋 포인트 검사하지 않음. 코디네이터 로그에는 이런 정보가 남음

  ```lua
  T1 시작됨
  참여자: A, B, C
  prepare 진행됨
  최종 결정: commit 또는 abort
  T1: decision = COMMIT, completed = false
  T2: decision = ABORT, completed = false
  T3: decision 없음
  T4: completed = true
  ```

  - 이 로그를 보고 의심스러운 트랜잭션을 가진 노드에게 커밋/어보트 요청을 다시 보내는 것

#### 3단계 커밋

- 지연에 제한이 있는 네트워크와 응답 시간에 제한이 있는 노드를 가정하기 때문에, 실용적 시스템에서 원자성을 보장하지 못함
- 완벽한 장애 감지기가 필요하나, 불가능하기 때문에, 블로킹 가능성이 있는 2PC 를 계속 사용함

### 현실의 분산 트랜잭션

- 분산 트랜잭션이 안정성 보장을 제공하기는 하나, 운영상 문제 때문에 사용하지 않기도 함
  - MySQL 의 분산 트랜잭션은 단일 노드 트랜잭션보다 10배 느리다고 보고됨
  - 2단계 커밋에 내장된 성능 비용의 많은 부분은 장애 복구를 위해 필요한 부가적인 디스크 강제 쓰기와 부가적인 네트워크 왕복 시간 때문임
    - <b>Q. 여기서 부가적인 디스크 강제 쓰기는 커밋 포인트가 맞나?</b>
      - 맞는데 더 잇음
        - 참여자의 준비 로그 기록
        - 커밋 포인트 기록
        - 참여자의 커밋/어보트 결과 기록
        - 코디네이터의 완료 상태 기록
- 분산 트랜잭션은 두 가지 종류임
  - 데이터베이스 내부 분산 트랜잭션
    - 데이터베이스 노드 사이에 내부 트랜잭션을 지원하는 경우가 있음
      - e.g. Mysql, vaultDB
    - 트랜잭션에 참여하는 모든 노드가 동일한 데이터베이스 소프트웨어 실행함
      - 그래서 호환성에 대한 부담이 적고, 아무 프로토콜이나 사용할 수 잇음
      - 특정 기술에 특화된 최적화를 사용할 수도 잇음
  - 이종 분산 트랜잭션
    - 이종 트랜잭션에서 참여자들은 둘 이상의 다른 기술임
      - 두 가지 서로 다른 벤더의 데이터베이스 혹은 메시지 브로커처럼 비데이터베이스 시스템일 수도 있음
    - 서로 다른 시스템에 걸친 분산 트랜잭션은 시스템 내부가 완전히 다르더라도 원자적 커밋을 보장해야 함

#### 정확히 한 번 메시지 처리

- 분산 트랜잭션이 지원되면 메시지 브로커와 데이터베이스가 서로 다른 장비에서 실행되는 두 가지 무관한 기술이더라도 원자적 커밋이 가능함
- 메시지 전달이나 데이터베이스 트랜잭션 중 하나가 실패하면 둘 다 어보트되고 메시지 브로커는 나중에 메시지를 안전하게 다시 전달할 수 잇음
- 메시지와 그 처리 과정의 부수 효과를 원자적으로 커밋함으로써 메시지가 결과적으로 정확히 한 번 처리되도록 보장이 가능함
  - 성공까지 몇 번의 재시도가 발생할 수는 잇음
- 근데 이게 가능하려면 트랜잭션 영향을 받는 모든 시스템이 동일한 원자적 커밋 프로토콜 사용이 가능해야함
  - 예를 들어 메시지 처리의 부수 효과를 처리할 때 2단계 커밋을 지원하지 않으면, 메시지 처리가 실패해 재시도 되는 경우 부수 효과가 두 번 이상 나타날 수 있음
  - 2단계 커밋 지원하면 실패하는 경우 부수 효과가 롤백되어 결과적으로 한 번만 처리됨

#### XA 트랜잭션

- 이종 기술에 걸친 2단계 커밋을 구현하는 표준
  - Postgresql, Mysql 등등 전통적인 관계형 DB 와 메시지 브로커에서 지원됨
- 네트워크 프로토콜이 아니라, 트랜잭션 코디네이터와 연결되는 인터페이스를 제공하는 C API 임
  - <b>Q. C API 가 머임?</b>
    - C 언어로 만들어진 API 라는 뜻임
    - 즉, XA 는 HTTP, TCP 기반의 네트워크 프로토콜이라기보다, C 언어 함수 호출 형태로 정의된 표준 인터페이스라는 것임
  - 자바에서는 JTA(자바 트랜잭션 API) 를 사용해 구현되며, 이는 JDBC 를 사용하는 DB 용 드라이버 다수와 JMS(자바 메시지 서비스) API 를 사용하는 메시지 브로커용 드라이버에서 지원됨
- 드라이버가 XA 를 지원한다는 것은 연산이 분산 트랜잭션의 일부가 되어야 하는지 알아내기 위해 XA API 를 호출한다는 것을 뜻함
  - 만약 그렇다면 드라이버는 데이터베이스 서버로 필요한 정보를 보냄
  - 드라이버는 코디네이터가 참여자에게 준비, 커밋, 어보트를 요청할 수 있는 콜백도 제공함
    - <b>Q. 이게 왜 콜백 제공임?</b>
      - 콜백이라고 적으면 헷갈릴 수 있음
      - 정확히는 드라이버가 코디네이터에게 호출할 수 있는 표준 제어 인터페이스를 제공한다는 뜻임

      ```lua
      prepare 호출 지점
      commit 호출 지점
      rollback 호출 지점
      recover 호출 지점
      ```
- 트랜잭션 코디네이터는 XA API 를 구현함
  - 트랜잭션을 시작하는 애플리케이션과 같은 프로세스에 로딩디는 라이브러리임
  - 트랜잭션의 참여자를 추적하고, 참여자들에게 드라이버가 제공한 콜백을 통해주니 요청 보낸 후, 응답을 수집하고 각 트랜잭션에 대한 커밋/어보트 결정을 추적하기 위해 로컬 디스크에 있는 로그를 사용함
    - <b>Q. 여기서 로컬 디스크의 로그는 커밋 포인트가 맞나?</b>
      - ㅇㅇ 마즘
- 애플리케이션 프로세스가 죽거나, 애플리케이션이 실행 중인 장비가 죽으면 코디네이터가 사라지고, 준비됐지만 커밋되지 않은 트랜잭션을 가진 참여자들은 의심스러운 상태에 빠짐
  - 커밋 포인트는 애플리케이션 서버의 로컬 디스크에 있으므로 해당 서버가 재시작 되어야 커밋/어보트 결과 판정이 가능함

#### 의심스러운 상태에 있는 동안 잠금을 유지하는 문제

- 의심스러운 상태에 있는 동안 로우에 대한 잠금을 획득하기 때문에, 의심스러운 트랜잭션을 무시할 수 없음
  - 2단계 잠금을 사용하면 읽은 로우에도 공유잠금이 걸려서, 해당 잠금이 풀릴 때까지 쓰기가 불가능함
- 이 잠금이 유지되는 동안 다른 트랜잭션은 해당 로우를 변경하거나, 심지어 읽을 수 없기도 함

#### 코디네이터 장애에서 복구하기

- 이론상으로는 코디네이터가 재시작하면 상태를 깨끗하게 복구하고 의심스러운 트랜잭션을 해소해야 함
- 그러나 현실에서는 고아가 된 의심스러운 트랜잭션이 발생할 수 있음
  - 어떤 이유로 결과를 결정할 수 없는 트랜잭션이 생길 수 잇다는 것
  - e.g. 트랜잭션 로그 손실, 소프트웨어 버그로 인한 오염 등
- 이러한 트랜잭션은 자동으로 해소될 수 없어 락을 점유하고 다른 트랜잭션을 차단하게 됨
- 이를 해결하기 위해서는 관리자가 수동으로 개입해야함
  - 의심스러운 트랜잭션의 참여자를 조사해서 커밋/어보트 결과를 확인하고 동일한 결과를 다른 참여자들에게도 적용해야함
- 너무 오래 대기하는 것은 리스크가 크기 때문에, XA 구현에는 참여자가 코디네이터로부터 확정적 결정을 얻지 않고 의심스러운 트랜잭션을 결정할 수 잇도록 하는 경험적 결정을 구현해 둠
  - <b>Q. 어떻게 동작함? 다른 참여자 조사하나?</b>
    ```lua
    관리자가 강제로 commit
    관리자가 강제로 rollback
    리소스 매니저가 timeout 정책에 따라 heuristic rollback
    ```

    - 근데 코디네이터 기반 의사 결정이 아니라 원자성이 깨질 수 잇음
    - 경험적이라는 말은 2단계 커밋의 원자성 보장을 위반할 수 있다는 뜻임

#### 분산 트랜잭션의 제약

- XA 트랜잭션도 운영상 문제가 잇음
  - 핵심 구현은 트랜잭션 코디네이터 자체가 트랜잭션 결과를 저장할 수 있는 일종의 데이터베이스여야 한다는 점이고, 다른 중요한 데이터베이스와 동일하게 신경 써서 접근해야함
    - 코디네이터가 복제되지 않으면 SPOF(단일 장애 지점) 이 될 수 있음
    - 서버 사이드 애플리케이션은 영속 상태를 DB 에 저장하고, 상태 비저장 모드로 개발되나, 코디네이터가 애플리케이션 서버의 일부가 되면 배포 특성이 바뀌어 로그가 지속적인 시스템의 중대한 부분이 됨
      - 이러면 더 이상 상태 비 저장 모드가 아니게 됨
      - <b>Q. 그럼 커밋 포인트 저장을 DB 에 하면 해결할 수 있는 문제 아님?</b>
        - 완전한 해결은 아니나, 애플리케이션은 stateless 하게 만들 수잇음
        - 상태를 저장소로 이동한 것이기 때문에 시스템 전체적으로는 여전히 코디네이터의 state 가 존재함

### 내결함성을 지닌 합의

- 하나 이상의 노드들이 값을 제안할 수 있고 합의 알고리즘이 그 값 중 하나를 결정하는 방식으로 합의 문제가 형식화 됨
- 이 때 합의 알고리즘은 이런 속성을 만족해야 함
  - 균일한 동의
    - 어떤 두 노드도 다르게 결정하지 않는다
  - 무결성
    - 어떤 노드도 두 번 결정하지 않는다
  - 유효성
    - 한 노드가 값 v 를 결정한다면, v 는 어떤 노드에서 제안된 것이다
  - 종료
    - 죽지 않은 모든 노드는 결국 어떤 값을 결정한다
- 합의 시스템 모델은 노드가 죽으면 돌아오지 않는다고 가정함
  - 노드가 복구되기를 기다리는 알고리즘은 종료 속성을 만족할 수 없음
  - 2PC 는 코디네이터가 돌아와 결정을 내린다고 가정하기 때문에 종료 속성을 만족하지 않음
- 종료 속성은 죽거나 연결할 수 없는 노드 개수가 절반 미만이라는 가정에 종속적임
  - 그러나 대부분의 합의 구현은 과반수의 노드에 장애가 나거나 심각한 네트워크 문제가 잇더라도 안정성 속성(동의, 무결성, 유효성) 을 항상 만족함
  - 따라서 대규모 중단이 발생하면 시스템이 요청을 처리할 수 없게 될 수 있지만 유효하지 않은 결정을 내려서 합의 시스템을 오염시키지는 않음

#### 합의 알고리즘과 전체 순서 브로드캐스트

- 내결함성을 지닌 합의 알고리즘 중 대다수는 위에서 설명한 합의 알고리즘의 속성을 직접 사용하지 않음
- 대신 값의 순차열(sequence) 에 대해 결정해서 전체 순서 브로드캐스트 알고리즘을 만듦
  - 전체 순서 브로드캐스트는 모든 노드에게 메시지가 정확히 한 번, 같은 순서로 전달되어야 함
  - 이걸 바꿔 생각하면 합의를 여러 번 하는 거임
    - 각 회마다 특정 노드가 다음에 보낼 메시지를 제안하고 결정하는 것
    - <b>Q. 근데 전체 순서 브로드캐스트에서는 wal 로그 그대로 공유하는 거 아니엇음?</b>
      - WAL 로그 자체를 전달하는 게 아니라, 모든 노드가 같은 순서로 로그를 작성하게 메시지를 전달하는 거임
      - 최종적으로는 논리적인 WAL 로그가 다 같아지게 됨
        - 저장 포맷이나 체크포인트, 스냅샷/로그 압축 등이 있을 수 있으므로, 물리적으로 WAL 파일 바이트가 완전히 동일하다는 뜻은 아님

#### 단일 리더 복제와 합의

- 단일 리더 복제에서 하는 것은 쓰기 요청을 리더에게 전달하고, 쓰기를 같은 순서로 팔로워에 적용하는 거엿음
- 이건 넓게 보면 전체 순서 브로드캐스트인데, 왜 합의에 대해 걱정을 하지 않았을까?
  - 리더를 선택하는 방식에 따라 답이 달라짐
    - 수동으로 리더를 선택햇다면 독재자 방식의 합의 알고리즘을 사용한 것임
    - 자동 선출하는 것은 내결함성을 지닌 전체 순서 브로드캐스트에 가까워지는 것이고, 합의에 가까운 방식임
  - 리더를 선출하려면 합의가 필요함. 근데 합의 알고리즘이 사실 전체 순서 브로드캐스트 알고리즘이라면 전체 순서 브로드캐스트는 단일 리더 복제와 같아 리더가 필요함
    - 전체 순서 브로드캐스트를 하려면 리더가 필요한데, 리더가 없는 상황에서 리더 선출을 하는 알고리즘으로 사용한다면 리더 선출을 위해 리더가 필요한 것처럼 보인다는 거임

#### 에포크 번호 붙이기와 정족수

- 합의 프로토콜은 내부적으로 리더를 사용하지만, 리더가 유일하다고 보장하지는 않음
- 합의 프로토콜들은 에포크 번호를 정의하고 각 에포크 내에서는 리더가 유일하다고 보장함
- 현재 리더가 죽었다고 생각될 때마다 리더 선출을 함
  - 이 선출은 에포크 번호를 증가시킴. 따라서 에포크 번호는 전체 순서가 있고 단조 증가함
- 두 가지 다른 에포크에 있는 두 가지 다른 리더 사이에 충돌이 발생하면 에포크 번호가 높은 리더가 이김
  - 그래서 리더의 결정을 허용하기 전에 해당 리더보다 에포크 번호가 높은 다른 리더가 있는지 먼저 확인해야함
- 그래서 두 번의 투표가 있음
  - 리더 선출 투표
  - 리더의 제안에 투표
  - 두 번의 투표를 하는 정족수가 겹쳐야 함
    - 리더 제안에 대한 투표가 성공하면, 투표한 노드 중 최소 하나는 리더 선출에도 참여했어야 함
    - <b>Q. 왜 리더 선출에 참여하지 않은 노드만으로 구성되면 안됨?</b>
      - 두 가지 문제가 있음
        1. 이전 에포크에서의 값을 새 리더가 모르고 제안할 수 있음
           - 합의에서 말하는 값은 DB 에 반영된 값이 아니라, 복제 로그에 기록된 값임
             - 로그 항목이 충분히 복제되어 커밋되면 DB 에 적용되는 것
           - 그래서 모든 노드가 값을 알지 못하는 상태에서 리더 교체가 발생할 수 잇음
           - 근데 합의에서는 정족수 이상의 노드에 반영이 되엇으면 합의가 되엇다고 봄
             - 즉, 특정 값이 정족수 이상의 노드에 잇으면 합의된 값임
           - 리더가 선출될 때, 참여 노드는 리더 노드에게 자기가 알고 잇는 최신 로그 정보를 제공함
             - 그래서 리더 선출에 참여한 노드가 리더 제안에 투표해야함
           - 만일 리더 선출에 참여하지 않은 노드만으로 리더 제안 투표가 성공햇다면, 최신 값이 아닌 상태에서 제안이 승인될 수 잇음
        2. 이전 리더의 제안이 더 높은 에포크를 무시하고 승인될 수 있음
           - 리더 선출에 참여하지 않은 노드가 리더 제안에 투표하면, 리더 선출에 참여하지 않았기 때문에 현재 제안한 노드가 최신 에포크의 노드인지 알 수 없음

#### 합의의 제약

- 합의 알고리즘을 모든 곳에 사용하지는 않음. 제약이 따르기 때문
  - 리더의 제안에 노드가 투표하는 것은 일종의 동기식 복제임
  - 합의 시스템은 항상 엄격한 과반수가 동작하기를 요구함
  - 대부분의 합의 알고맂므은 투표에 참여하는 노드 집합이 고정돼있다고 가정함
    - 따라서 클러스터에 노드를 그냥 추가하거나 제거할 수 없음
    - 합의 알고리즘의 동적 멤버십 확장은 클러스터에 있는 노드 집합이 시간이 지남에 따라 바뀌는 것을 허용하기도 함
  - 합의 시스템은 장애 노드를 감지하기 위해 일반적으로 타임아웃에 의존함
    - 네트워크 지연 변동이 심하면 리더 선출에 많은 리소스를 사용하게 될 수 잇음
