# DDIA 11장

- 데이터는 연속적으로 생성되기 때문에, 일괄 처리 프로세스는 인위적으로 일정 기간씩 데이터 청크를 나눠야 함
- 그런데 처리하는 시점을 특정 시간 단위로 고정하면 UX 가 나빠질 수 있음
  - 바로바로 처리되지 못하니까
- 그래서 고정된 시간마다 처리하는 방식보다는, 이벤트가 발생할 때마다 처리해야함
- 이걸 스트림 처리라고 함

## 이벤트 스트림 전송

- 입력이 파일(바이트의 연속) 이면 파일을 분석해 레코드의 연속으로 바꿈
  - 레코드는 보통 이벤트라고 함
    - e.g. 웹 페이지 접속, 상품 구입 등 사용자 액션이 이벤트가 될 수 잇음
- 이벤트는 텍스트 문자열이나 JSON, 이진 형태 등으로 부호화됨
- 이렇게 기록된 파일은 여러 작업에서 읽을 수 잇음
  - 생성자가 이벤트 만들면 복수의 소비자가 처리 가능함
  - 스트림 시스템에서는 토픽이나 스트림으로 관련 이벤트를 묶음
- 근데 이벤트 처리할 때 폴링은 오버헤드가 큼
  - 트리거가 대안이 될 수 잇으나, 기능이 제한적임

### 메시징 시스템

- 그래서 일반적으로 메시징 시스템 사용함
- 간단하게는 생산자 - 소비자 사이에 유닉스 파이프나 TCP 연결과 같은 직접 통신 채널을 사용해 구현할 수 있음
  - 근데 다수의 소비자에게 전달되어야 할 필요가 있어서 여기서 확장해 사용함
- 메시지 생성 속도가 소비 속도보다 빠르다면?
  1. 메시지 버림
  2. 메시지를 큐에 버퍼링함
     1. <b>Q. 큐 크기가 메모리 크기보다 커지면 무슨 일이 생기나?</b>
  3. 배압(backpressure, 흐름제어) 함
     1. 유닉스 파이프랑 TCP 는 이거 사용함
- 노드가 죽거나 일시적으로 오프라인이 된다면? 손실되는 메시지가 있나?
  - 지속성 갖추려면 복제하거나 디스크 기록해야하는데 비용 발생함
  - 그래서 메시지 유실 허용해도 된다면 처리량 높이면서 지연 시간 낮출 수 있음

#### 생산자에서 소비자로 메시지 직접 전달하기

- 보통 중간 노드 없이 생산자 - 소비자를 네트워크로 직접 통신함
  - 이 방식은 메시지 유실 가능성을 고려해 애플리케이션 코드를 작성해야함
  - 근데 허용 가능한 결함은 제한적임
  - <b>Q. 왜 이 방식은 유실 가능성 고려해야한다고 하지? 다른 방식도 유실 가능성은 고려해야하지 않나? 얘만 콕 집어서 말한 이유는?</b>

#### 메시지 브로커

- 직접 메시징 대안으로 메시지 브로커(메시지 큐) 를 사용함
- 이건 메시지 스트림을 처리하느데 최적화된 데이터베이스라고 생각하면 됨
- 생산자와 소비자가 브로커에 클라이언트로 붙기 때문에, 시스템은 클라이언트의 상태 변경에 쉽게 대처할 수 잇음
  - 지속성 문제가 생산자와 소비자에서 브로커로 옮겨갔기 때문
- 브로커는 장애 시 메시지 유실을 방지하기 위해 디스크에 메시지 기록함
- 큐 대기 시에 소비자는 비동기로 동작함

#### 메시지 브로커와 데이터베이스의 비교

- 어떤 메시지 브로커는 2단계 커밋을 수행하기도 함
  - <b>Q. 왜 하는 거임? 모든 수신자가 전달 받았는지 확인하려고 하나?</b>
- DB 는 데이터 삭제될 때까지 보관하나, 메시지 브로커는 전달 후 삭젷마
- 클라이언트가 데이터에서 필요한 부분을 선택하게 하기 위해 DB 는 보조 색인이나 검색을 지원하지만, 메시지 브로커는 특정 패턴과 부합하는 토픽의 부분집합을 구독하는 방식을 지원함
  - <b>Q. 특정 패턴과 부합하는 토픽의 부분집합이 머임?</b>

### 복수 소비자

- 복수 소비자가 같은 토픽에서 메시지를 읽을 때 사용하는 주요 패턴 두 가지
  1. 로드 밸런싱
     1. 메시지가 소비자 중 하나로 전달됨
     2. 소비자는 브로커에 의해 임의로 지정됨
     3. 메시지 처리를 병렬화할 때 유용함
  2. 팬 아웃
     1. 메시지를 모든 소비자에게 전달함
     2. 같은 파일을 여러 다른 작업에서 사용할 때에 사용
- 이 두 가지 패턴은 함께 사용 가능함
  - 두 개의 소비자 그룹에서 하나의 토픽을 구독하고, 각 그룹은 모든 메시지를 받으나, 그룹 내에서는 하나의 노드만 메시지를 받게 함

#### 확인 응답과 재전송

- 소비자에게는 언제든지 장애가 발생할 수 있고 이 때문에 메시지가 유실될 수 있음
- 이를 방지하기 위해 메시지 브로커는 소비자가 메시지 처리 이후 확인 응답을 보내게 함
  - 확인 응답 받기 전에 소비자 연결이 닫히거나 타임아웃되면 브로커는 메시지가 처리되지 않앗다고 가정하고 다른 소비자에게 다시 전송함
  - 참고로 메시지가 정상 처리되엇음에도 네트워크 문제로 확인 응답을 받지 못할 수도 있음. 이 때문에 원자적 커밋 프로토콜이 필요함
    - <b>Q. 원자적 커밋 프로토콜? 머엿더라</b>
- 메시지가 재전송되어 처리 순서가 밀릴 가능성이 있기 때문에, 메시지 발행 순서와 실제 처리 순서는 상이할 수 있음
- 이에 대한 해결 방법은 후반부에서 설명

### 파티셔닝된 로그

- 메시지 브로커 사용 시, 브로커가 확인 응답을 받으면 메시지를 삭제하기 때문에 이미 받은 메시지는 복구할 수 없음
- 이 때문에 소비자를 다시 실행해도 동일한 결과를 받지 못함
  - 메시지가 없으니께 ㅜ.ㅜ
- 그럼 DB 의 지속성 있는 저장과, 메시징 시스템의 지연 짧은 알림 기능을 조합할 수 있을까? → 이게 로그 기반 메시지 브로커임

#### 로그를 사용한 메시지 저장소

- 로그는 단순히 디스크에 저장된 append-only 레코드의 연속임
- 메시지 브로커 구현 시에도, 생산자가 보낸 메시지를 로그 끝에 추가하고 소비자가 로그를 순차적으로 읽는 방식으로 메시지를 전달함
- 처리량을 높이기 위해 로그를 파티셔닝함
  - 서로 다른 파티션은 서로 다른 장비에서 서비스할 수 있음
  - 즉, 각 파티션은 다른 파티션과 독립적으로 읽기/쓰기가 가능한 로그임
- 각 파티션마다 브로커는 모든 메시지에 오프셋을 부여하여 관리함

#### 로그 방식과 전통적인 메시징 방식의 비교

- 로그 기반 접근법은 팬 아웃 메시징 방식 제공함
  - 소비자가 서로 영향 없이 독립적으로 로그 읽을 수 잇고, 읽어도 삭제되지 않기 때문
- 각 클라이언트는 할당된 파티션의 메시지를 모두 소비하며, 이렇게 소비자에게 로그 파티션이 할당되면 소비자는 단일 스레드로 파티션에서 순차적으로 메시지를 읽음
  - 이 방식은 단점이 있음
    - 토픽을 처리하는 최대 노드 수는, 토픽의 로그 파티션 수로 제한됨
      - 같은 파티션 내의 메시지가 같은 노드로 전달되기 때문
    - 특정 메시지 처리가 느리면 파티션 내 후속 메시지 처리가 지연됨
- 메시지 처리 비용이 비싸고, 병렬처리가 가능하나 순서가 중요하지 않으면 JMS/AMQP 방식의 메시지 브로커가 적합
- 반면 처리량이 많고 메시지 처리 속도가 빠르지만 순서가 중요하다면 로그 기반 접근법이 효과적

#### 소비자 오프셋

- 파티션 하나를 순서대로 처리하면 메시지를 어디까지 처리햇는지 알기 쉬움
- 그래서 브로커는 개별 메시지마다 확인 응답을 추적하지 않고, 주기적으로 소비자 오프셋을 기록함
- 이러면 추가적인 오버헤드가 감소하고 일괄 처리와 파이프라이닝을 수행할 수 있는 기회를 제공해 로그 기반 시스템의 처리량을 늘릴 수 잇음
- 메시지 오프셋은 단일 리더 데이터베이스 복제에서 사용되는 로그 순차 번호와 상당히 유사함
- 소비자 노드에 장애 발생 시, 소비자 그룹 내 다른 노드에게 장애 발생한 노드가 처리하던 파티션 할당하고, 마지막으로 기록된 오프셋부터 처리 이어함
  - 이 과정에서 오프셋 기록이 누락되엇다면 특정 메시지가 두 번 처리될 수 잇는 문제가 발생함
  - 이는 후반부에서 자세히 다룰 예정

### 디스크 공간 사용

- 소비자 처리 속도가 느려 생산 속도를 따라잡지 못한다면, 이미 삭제된 메시지를 처리하려고 할 수 있음
- 로그는 크기가 제한된 버퍼로 구현하고, 버퍼가 가득 차면 오래된 메시지 순서대로 버림
  - 이걸 원형 버퍼나 링 버퍼라고 함
  - 버퍼가 디스크 상에 잇다면 상당히 커질 수 있음

#### 소비자가 생산자를 따라갈 수 없을 때

- 일전에 메시지 버리기, 버퍼링, 배압 적용 세 가지 선택지가 있다고 햇음
- 로그 기반 방식에서는 이 중에 버퍼링을 사용함
- 어차피 소비자가 뒤쳐져서 디스크가 보유한 메시지보다 오래된 메시지를 읽으려 하면 못 읽기 때문에, 브로커는 버퍼 크기를 넘는 오래된 메시지를 버림
  - 소비자 오프셋을 모니터링해 미리 경고할 수 있음
- 특정 소비자의 처리 속도가 늦어지더라도, 다른 소비자의 서비스에는 영향을 주지 않음
  - 전통적인 메시지 브로커와 대조적임
    - 전통적인 메시지 브로커에서는 소비자가 중단되면 해당 소비자가 사용하던 큐를 삭제해야 큐에 불필요한 메시지가 누적되지 않음
      - <b>Q. 근데 굳이 큐 삭제해야하나? 그대로 냅두고 처리하는 노드만 변경하면 되는 거 아님?</b>

## 데이터베이스와 스트림

### 시스템 동기화 유지하기

- 주기적으로 데이터베이스 전체를 덤프하는 작업이 느리면, 대안으로 이중 기록(dual-write) 를 사용할 수도 있음
  - 데이터 변경 시에 애플리케이션에서 두 시스템에 기록하는 방식임
- 근데 몇 가지 문제가 잇음
  1. 경쟁 조건이 발생할 수 있음
  2. 한 쪽만 성공할 수 있음

### 변경 데이터 캡쳐(CDC)

- 데이터베이스에 기록하는 모든 데이터 변화를 다른 시스템으로 복제할 수 있는 형태로 추출하는 과정

#### 변경 데이터 캡처의 구현

- CDC 는 본질적으로 변경 사항 캡처할 때 데이터베이스 하나를 리더로 하고 다른 걸 팔로워로 함
  - 로그 기반 메시지 브로커는 메시지 순서를 유지하기 때문에 변경 이벤트 전송하기에 적합함
- 트리거를 사용해 CDC를 구현하기도 함
  - 이 방식은 성능 오버헤드가 상당함
    - <b>Q. 와이??</b>
  - 그래서 복제 로그 파싱 방식을 사용(얘도 스키마 변경 등 해결할 문제가 많지만 그래도 트리거 방식보다는 나음)
- CDC 는 비동기 방식으로 동작함

#### 초기 스냅숏

- 데이터베이스에서 발생한 모든 변경 로그를 가지고 있다면, 로그를 재현해 데이터베이스의 전체 상태를 재구축할 수 있음
- 그러나 로그가 디스크 공간을 너무 많이 차지하고, 로그 재생하는 것도 오래 걸림
  - 그래서 적당히 잘라서 가지고 잇는게 중요함
- 데이터베이스 스냅숏은 변경 로그 위치나 오프셋에 대응되어야 함
  - 그래야 스냅숏 이후에 변경 사항을 적용할 시점을 알 수 잇음

#### 로그 컴팩션

- 새로운 파생 데이터 시스템 만들 때마다 스냅숏 만들지 않고, 로그 컴팩션을 사용하는 방법도 잇음
- 로그 컴팩션은 해시 색인 부분에서 다룬 내용인데, 같은 키의 로그를 찾아서 중복 제거하고, 가장 최근에 갱신된 내용만 유지하는 방식임
  - 컴팩션과 병합 과정을 백그라운드로 실행됨
- CDC 맥락에서도, 모든 변경에 기본키가 포함되게 하고 키의 모든 갱신이 해당 키의 이전 값을 교체한다면 키에 대해 최신 쓰기만 유지하는 방식으로 복제를 가능하게 할 수 잇음
- 파생 데이터 시스템 재구축할 때마다 새로운 소비자는 컴팩션된 로그 토픽의 오프셋 0부터 시작해서 순차적으로 데이터베이스의 모든 키를 스캔하면 됨
  - 로그에 데이터베이스의 최신 키 값이 존재하는 것이 보장됨(컴팩션 중인 경우 이전 값도 약간 존재 가능하긴 함)
  - CDC 원본 데이터베이스의 스냅숏을 만들지 않고 콘텐츠 전체의 복사본을 얻을 수 잇는 것!

### 이벤트 소싱

- 도메인 주도 설계 커뮤니티에서 개발한 기법
- 이벤트 소싱은 CDC 와 비슷하게 애플리케이션 상태 변화를 모두 변경 이벤트 로그로 저장함
  - CDC 와 가장 큰 차이점은 아이디어 적용하는 추상화 레벨이 다르다는 점임
    - CDC 에서는 변경 로그를 데이터베이스에서 저수준으로 추출하나, 이벤트 소싱에서 이벤트는 애플리케이션 수준에서 발생한 일을 반영하게 설계됨
- 이벤트 소싱은 데이터 모델링에 쓸 수 있는 강력한 기법임
  - 애플리케이션 관점에서 사용자의 행동을 불변 이벤트로 기록하는 방식은, 변경 가능한 데이터베이스 상에서 사용자의 행동에 따른 효과를 기록하는 방식보다 훨씬 유의미함
  - 이벤트 소싱을 사용하면 애플리케이션을 지속해서 개선하기 유리함
- Q. 이벤트 소싱이랑 append-only 로그는 뭐가 다른 거임?
  - 이벤트 소싱은 이벤트 로그 자체가 DB 가 되는 거고, append-olny 로그는 DB 에 기록한 내용을 기록한 거임

#### 이벤트 로그에서 현재 상태 파싱하기

- 이벤트 로그는 그 자체로 유용하지 않음. 사용자는 시스템의 현재 상태를 보기 원하지 수정 히스토리를 보기 원하는 게 아니기 때문
- 그래서 이벤트 소싱 사용하면 시스템에 기록한 데이터를 표현한 이벤트 로그를 가져와서 사용자에게 보여주기 적당한 상태로 변환해야함
- CDC 와 마찬가지로 이벤트 로그를 재현함년 현재 시스템 상태를 재구성할 수 있음
- 근데 컴팩션은 다르게 처리해야함
  - 이벤트 소싱에서 이벤트는 결과(e.g. 잔액: 1000) 가 아니라 의도(e.g. 출금: 500)를 표현하기 때문에, 뒤에 발생한 이벤트가 앞선 이벤트를 덮어쓰지 않음
  - 그래서 컴팩션이 불가능함 ㅜ.ㅜ
- 이벤트 로그에서 파생된 현재 상태의 스냅숏을 저장하는 매커니즘이 있어서, 메번 전체 로그를 재처리해서 현재 상태를 얻지 않아도 되긴 함
  - 근데 이건 장애 발생 시 복구 성능을 높여주는 최적화에 불과함
  - 이벤트 소싱 시스템에는 모든 이벤트를 영원히 저장하고 필요 시 모든 이벤트를 재처리할 수 있어야 한다는 의도가 있음

#### 명령과 이벤트

- 이벤트 소싱 철학은 이벤트와 명령을 구분함
- 명령
  - 사용자의 요청이 처음 도착했을 때 이 요청은 명령임
  - 이 시점에서 명령이 실패할 수도 잇음
  - 애플리케이션은 명령이 실행 가능한지 확인하고, 승인 가능하면 명령은 지속성 있는 불변 이벤트가 되는 것
- 이벤트
  - 생성 시점에 사실이 됨
  - 이벤트 스트림 소비자는 이벤트를 거절하지 못함
  - 그래서 명령의 유효성은 이벤트가 되기 전에 동기식으로 검증해야함(e.g. 직렬성 트랜잭션 사용해 원자적으로 명령 검증)
- 하나의 사용자 요청을 두 개의 이벤트로 분리하여(e.g. 예약이라면, 가예약 → 확정) 비동기 처리로 유효성 검사를 할 수도 있음
