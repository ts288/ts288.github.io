# Outbox 패턴

- db 에 저장을 하고 rabbitmq 에 이벤트를 발행해야 하는 트랜잭션이 있다고 해보자.
- 이 때 두 가지 문제가 발생할 수 있따.

1. db 에 저장은 됏는데 이벤트 발행이 정상적으로 안됨
2. db 에 저장이 안됏는데 이벤트 발행이 정상적으로 됨

- 이 두 경우 모두 db 의 상태와 이벤트 간의 정합성이 불일치하는 문제가 발생할 수 있따.
  - 왜냐면 db 에 사용하는 커넥터와, 이벤트 발행에 사용하는 커넥터가 다르기 때문에, 둘 중에 하나에서 문제가 발생할 수 있는 것!
- 이를 해결하기 위해서 아웃박스 패턴을 사용한다.
  - 그래서 하나의 리소스로 묶기 위해서 사용하는 패턴이다.
  - 이를 통해서 둘 다 성공하거나 둘 다 실패하게 할 수 있음

### 아웃박스 패턴이란?

- 아웃박스 패턴은 동일 db 트랜잭션 안에서, 도메인도 저장하고, 아웃박스 테이블을 함께 저장하는 방식이다.
- 즉, db 를 기록할 때에 아웃박스라는 공간에도 해당 커밋이 성공적으로 수행되었음을 함께 기록하고, 아웃박스 워커(혹은 프로세스) 가 아웃박스의 데이터를 읽고 이에 따라 이벤트를 발행하는 것!
- 이를 통해 db 트랜잭션과 이벤트 발행 간의 정합성을 일치시킬 수 있따.
- 예를 들어, mysql 에 데이터를 저장해야한다면
  1. 저장할 데이터와 관련된 쿼리를 작성
  2. 바로 아래에 아웃박스에 저장하는 쿼리를 작성
  3. 묶어서! 커밋
  4. 아웃박스 워커가 아웃박스 읽고 처리
     1. 이 과정은 폴링이나 CDC 로 처리할 수 있음

이런 방식으로 수행이 된다.

### Q. 근데 이거 꼭 필요한가요?

예를 들어, a 서버가 이벤트 발행, b 서버가 컨슘. b 서버는 db 기록하고 이벤트 발행 해야할 때, RabbitMQ 는 재시도 지원하니까, db 기록이나 이벤트 발행 둘 중에 문제가 생겨도 해결 가능한 거 아닌가요?

- 맞는 말이긴 함! 근데 이게 가능하기 위해서는 모든 경우에 대한 예외 처리를 해줘야함.
  - db 에 기록이 되고 이벤트가 발행이 되지 않은 경우, 재시도 했을 때의 처리
  - db 에 기록이 안되었을 때의 재시도 처리

  등등
  
- 이 모든 예외를 고려하기 보다는 그냥 아웃박스 패턴 사용하는 게 안정적이라고 할 수 있음

## 아웃박스 워커의 처리 방식

### 1. CDC(Change Data Capture)란?

<b>데이터베이스에서 “무슨 변경이 일어났는지”를 실시간으로 감지해서,<br />그 변경을 다른 시스템(예: Kafka, RabbitMQ, ElasticSearch, etc.)으로 흘려보내는 기술.</b>

즉, \*\*DB 로그(binlog)\*\*를 읽어서 “INSERT/UPDATE/DELETE 이벤트”를 <b>데이터 파이프라인</b>으로 전달하는 구조예요.

### 2. 폴링

주기적으로 데이터 요청해서 읽어오는 방식

CDC 에 비해 성능 트레이드 오프가 큼
